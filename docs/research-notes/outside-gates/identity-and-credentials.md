# Identity, access and credential controls as outside gates for coding agents

State as of 2026-10-07. All sources below were fetched on 2026-10-07 and the quotes checked against the fetched text. Vendor features (AWS, GCP, Azure/Entra, GitHub, Vault) are examples of platform-neutral concepts. Date-sensitive items are flagged inline. New domains not yet in `docs/sources.md` trusted table: `docs.aws.amazon.com`, `docs.cloud.google.com`, `learn.microsoft.com`, `developer.hashicorp.com`, `nccoe.nist.gov` (all primary vendor/standards-body sources under the "Assessing a new domain" rule 1).

Core framing used throughout **[Inference]**: a harness permission rule is enforced by the agent's own process and configuration, which the agent (or a PR) may change. An identity control is enforced by the system that holds the resource (cloud API, forge, secret store, MCP server). It holds even if the agent is mistaken or hijacked, because the agent never had the authority in the first place.

## 1. Least privilege for agents: separate identity, scoped short-lived tokens, OIDC federation, JIT elevation, boundaries and org guardrails

### Takeaway
Authoritative guidance converges on: give the agent its own, distinct, narrowly scoped identity with short-lived credentials (not the user's broad session or a long-lived secret), cap it with a ceiling that the agent's own admins cannot lift (permission boundaries / org policies), and make elevation time-bound and approval-gated. These are enforced by the resource owner, so they are true outside gates.

### Cited Findings

Agent identity vs acting as the user
- OWASP's agentic Top 10 says sharing user-centric identity breaks least privilege: "Without a distinct, governed identity of its own, an agent operates in an attribution gap that makes enforcing true least privilege impossible." Identity includes "any authentication material (API keys, OAuth tokens, delegated user sessions) that represent it." — [OWASP Top 10 for Agentic Applications 2026, ASI03 (PDF, Dec 2025)](https://genai.owasp.org/download/52117/?tmstv=1765059207); resource page: [genai.owasp.org](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) (publication date December 9, 2025).
- OWASP ASI03 mitigation 1: "Issue short-lived, narrowly scoped tokens per task and cap rights with permission boundaries - using per-agent identities and short-lived credentials (e.g., mTLS certificates or scoped tokens) - to limit blast radius". Mitigation 7: "Bind permissions to subject, resource, purpose, and duration. Require re-authentication on context switch." Mitigation 6 names agent identity platforms: "Microsoft Entra, AWS Bedrock Agents, Salesforce Agentforce, Workday's Agentic System of Record (ASOR) model, and similar emerging patterns in Google Vertex AI." — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- OWASP ASI03 lists "Identity Sharing. An agent gains access to systems on behalf of a user, often their maker. It then allows other users to leverage that identity implicitly by invoking its tools as that identity." — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- OWASP LLM06 (Excessive Agency) gives the "on behalf of" counterpart: "Track user authorization and security scope to ensure actions taken on behalf of a user are executed on downstream systems in the context of that specific user." and "Limit the permissions that LLM extensions are granted to other systems to the minimum necessary". — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- OWASP introduces "Least-Agency": "This captures our advice to organizations to avoid unnecessary autonomy; deploying agentic behavior where it is not needed expands the attack surface without adding value." — [OWASP Agentic Top 10 PDF, p.6](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- OWASP ASI02 recommends expressing tool limits outside the model: "Where possible, express these profiles as IAM or authorization policy stanzas attached to each tool, rather than relying on ad-hoc conventions." and a "Policy Enforcement Middleware ('Intent Gate'). Treat LLM or planner outputs as untrusted. A pre-execution Policy Enforcement Point (PEP/PDP) validates intent and arguments, enforces schemas and rate limits, issues short-lived credentials, and revokes or audits on drift." — [OWASP Agentic Top 10 PDF, ASI02](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- Forge example (GitHub Apps as a separate non-human identity): "GitHub Apps can act independently of a user. This is beneficial for automations that do not require user input."; "the user or organization owner who installed the app can decide what repositories the app can access."; "GitHub Apps use short lived tokens. If the token is leaked, the token will be valid for a shorter amount of time." — [GitHub Docs: Deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)
- Installation tokens: "The installation access token will expire after 1 hour." They can be narrowed per request: "you can use the `repositories` or `repository_ids` body parameters to specify individual repositories" and "use the `permissions` body parameter to specify the permissions that the installation access token should have." — [GitHub Docs: Generating an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app) (1-hour figure is date-sensitive)
- CI default token: "By default, when you create a new repository in your personal account, `GITHUB_TOKEN` only has read access for the `contents` and `packages` scopes." — [GitHub Docs: Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)

OIDC workload federation instead of stored secrets
- "You won't need to duplicate your cloud credentials as long-lived GitHub secrets." "Your cloud provider issues a short-lived access token that is only valid for a single job, and then automatically expires." "You have more granular control over how workflows can use credentials, using your cloud provider's authentication and authorization tools to control access to cloud resources." — [GitHub Docs: OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect)

Dynamic secrets
- Vault database engine: services "no longer need to hardcode credentials: they can request them from Vault"; "Since every service is accessing the database with unique credentials, it makes auditing much easier when questionable data access is discovered."; "Vault makes use of its own internal revocation system to ensure that users become invalid within a reasonable time of the lease expiring." — [HashiCorp Vault: Database secrets engine](https://developer.hashicorp.com/vault/docs/secrets/databases)

Just-in-time / approval-gated elevation
- Entra PIM "provides time-based and approval-based role activation to mitigate the risks of excessive, unnecessary, or misused access permissions"; features include "**just-in-time** privileged access", "**time-bound** access to resources using start and end dates", "Require **approval** to activate privileged roles", "Use **justification** to understand why users activate", "Get **notifications** when privileged roles are activated", "Download **audit history**". JIT defined as "A model in which users receive temporary permissions to perform privileged tasks, which prevents malicious or unauthorized users from gaining access after the permissions expire." Roles can be assigned to "users, groups, service principals, or managed identities." — [Microsoft Learn: What is Privileged Identity Management? (ms.date 2026-04-23)](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-configure)
- MCP progressive scopes are the protocol-level analogue: "Minimal initial scope set (e.g., `mcp:tools-basic`) containing only low-risk discovery/read operations" and "Incremental elevation via targeted `WWW-Authenticate` `scope="..."` challenges when privileged operations are first attempted". Common mistakes include "Using wildcard or omnibus scopes (`*`, `all`, `full-access`)" and "Treating claimed scopes in token as sufficient without server-side authorization logic". — [MCP Security Best Practices: Scope Minimization](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices) (spec version 2025-11-25; the 2025-06-18 URL serves the same content with 2025-11-25 links)
- MCP authorization step-up: "Clients acting on behalf of a user **SHOULD** attempt the step-up authorization flow. Clients acting on their own behalf (`client_credentials` clients) **MAY** attempt the step-up authorization flow or abort the request immediately." — [MCP Authorization 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

Permission boundaries and org-level guardrails that admins cannot exceed
- AWS permissions boundary: "a managed policy to set the maximum permissions that an identity-based policy can grant to an IAM entity"; "it limits the user's permissions but does not provide permissions on its own." Delegation pattern: a delegated admin may create users only "if he uses the `XCompanyBoundaries` policy to set the permissions boundary", with explicit denies so he cannot edit or delete boundaries. Caveat: "implicit denies in permissions boundaries do not limit resource-based policies." — [AWS IAM: Permissions boundaries](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)
- AWS SCPs: "SCPs offer central control over the maximum available permissions for the IAM users and IAM roles in your organization." "No permissions are granted by an SCP." A blocked permission cannot be used "even if the account administrator attaches the `AdministratorAccess` IAM policy with \*/\* permissions to the user." "SCPs affect all users and roles in attached accounts, ***including the root user***." Limits: "SCPs don't affect users or roles in the management account"; "SCPs ***do not*** affect any service-linked role"; they "don't affect resource-based policies directly" or principals from outside the organization. "If both a permissions boundary (an advanced IAM feature) and an SCP are present, then the boundary, the SCP, and the identity-based policy must all allow the action." — [AWS Organizations: SCPs](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)
- GCP org policy: "Identity and Access Management focuses on _who_ ... Organization Policy focuses on _what_, and lets the administrator set restrictions on specific resources to determine how they can be configured." "When an organization policy is set on a resource, all descendants of that resource inherit the organization policy by default." — [Google Cloud: Organization Policy overview](https://docs.cloud.google.com/resource-manager/docs/organization-policy/overview)

Standards bodies
- NIST NCCoE concept paper (DRAFT, February 2026; comment period "February 5th, 2026 – April 2nd, 2026") asks rather than prescribes, e.g. "How do we establish 'least privilege' for an agent, especially when its required actions might not be fully predictable when deployed?" and "How do we handle delegation of authority for 'on behalf of' scenarios?". Areas of interest include identifying agents "such that access management systems can distinguish between agent and human identities" and "Access Delegation. Link specific user identities to AI agents or software systems to support effective delegation controls and maintain accountability". Standards considered: MCP, "OAuth 2.0/2.1 and extensions", OpenID Connect, "SPIFFE/SPIRE", SCIM ("a potential way to create, update and revoke agent identities across systems"), NGAC; plus "SP 800-207 Zero Trust Architecture, SP800-63-4 Digital Identity Guidelines, NISTIR 8587 Protecting Tokens and Assertions from Forgery, Theft, and Misuse". — [NCCoE concept paper PDF](https://www.nccoe.nist.gov/sites/default/files/2026-02/accelerating-the-adoption-of-software-and-ai-agent-identity-and-authorization-concept-paper.pdf)

### Inferences
- **[Inference]** For a coding agent, "separate identity" concretely means: a GitHub App / bot account for forge writes, a dedicated cloud role assumed via OIDC for CI or deploy steps, and per-service dynamic credentials, rather than the developer's personal token, SSO session or `~/.aws` profile being visible to the agent process.
- **[Inference]** Boundaries and org policies are the only listed controls that stay in force when the agent's own account has admin rights, which matters if an agent can edit IaC or IAM in a sub-account. SCP exemptions (management account, service-linked roles, resource-based policies) mean the agent should never run in the management account.
- **[Inference]** "Acting as the user" is appropriate only where the downstream system must enforce that user's own authorization (OWASP LLM06); it still should use a delegated, scoped, short-lived token rather than the user's full session.

### Gaps
- NIST has not published final guidance on agent identity as of 2026-10-07 that I could fetch; the NCCoE item is a concept paper with questions. I did not check whether a project description followed the April 2026 comment period.
- Azure Policy deny effects and Azure RBAC deny assignments were not fetched; Entra PIM stands in for Azure JIT. GCP permission-boundary equivalents (e.g. Principal Access Boundary) not fetched.

## 2. Separation of duties: agent proposes, a human approves and deploys; break-glass

### Takeaway
The forge and deployment system can enforce "agent may propose, may not approve or deploy" independently of the harness: required independent review, requester cannot approve the agent's PR, workflows don't run until approved, and environment secrets are released only after protection rules pass. Break-glass must be a separate, monitored, rarely used path, never the agent's normal route.

### Cited Findings
- GitHub's own coding agent implements SoD outside the model: "Only users with write access to the repository can trigger Copilot cloud agent to work."; "Copilot cloud agent only has the ability to push to a single branch" (a `copilot/` branch); it "Prevents the user who asked Copilot cloud agent to create a pull request from approving it."; "By default, workflows are not triggered until Copilot cloud agent's code is reviewed and a user with write access to the repository clicks the **Approve and run workflows** button."; "It cannot directly run `git push` or other Git commands." — [GitHub Docs: Copilot coding agent risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations) (product now named "Copilot cloud agent" on that page; date-sensitive)
- Repository default: "By default, when you create a new repository in your personal account, workflows are not allowed to create or approve pull requests." The setting "Allow GitHub Actions to create and approve pull requests" changes this. — [GitHub Docs: Managing GitHub Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- Deployment environments: required reviewers "must approve workflow jobs that use this environment"; "Prevent self-review" stops "users from approving workflows runs that they triggered"; environment secrets are only accessible after protection rules such as required approvals pass; deployment branches can be restricted. — [GitHub Docs: Managing environments for deployment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
- OWASP: "Utilise human-in-the-loop control to require a human to approve high-impact actions before they are taken." — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/). ASI03 mitigation 4: "Require human approval for high-privilege or irreversible actions". — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- Entra PIM: approvers are distinct roles ("Approve or reject requests for role elevation"); extend/renew "require an approval from a Global Administrator or Privileged Role Administrator". — [Microsoft Learn: PIM](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-configure)
- Break-glass (AWS Well-Architected SEC03-BP03): anti-patterns include "Your emergency access processes are used in non-emergency situations. For example, your users frequently misuse emergency access processes as they find it easier to make changes directly than submit changes through a pipeline." and processes that "do not generate sufficient logs to audit the processes, or the logs are not monitored". Guidance: "The emergency access account should only be accessed during emergencies, as break-glass procedures can be considered a backdoor."; "Upon returning to normal operations, automatically rotate the emergency access credentials"; use SCPs "to deny the deletion and modification of the cross-account IAM roles"; alert "when the emergency access account is used during normal operations"; require "approvals from the user's peers or management as appropriate". — [AWS Well-Architected SEC03-BP03](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_permissions_emergency_process.html)

### Inferences
- **[Inference]** The agent's identity should hold "propose" rights (push to its own branch, open PR) but not "approve", "merge to protected branch", "deploy to production environment" or "read production secrets". Each of those is enforced by forge rulesets/branch protection and environment protection, not by agent instructions.
- **[Inference]** If the human who prompts the agent can also approve the agent's PR, SoD collapses to one person plus a machine; GitHub's "requester cannot approve" rule is the pattern to copy for any agent bot account.
- **[Inference]** Break-glass credentials must never be reachable from the agent's environment, since the AWS text characterises them as a backdoor; their use should alert.

### Gaps
- GitHub branch-protection/ruleset text on "require approval of the most recent reviewable push" and on bypass lists was not fetched in this pass.

## 3. Audit logging, attribution, and anomaly alerts (detective, not preventive)

### Takeaway
Attribution requires that agent actions run under an identifiable non-human identity (or are explicitly marked "on behalf of"); shared or passed-through credentials destroy the audit trail. Logs and anomaly alerts detect and support response; sources explicitly say they do not prevent.

### Cited Findings
- OWASP agentic: "strong observability becomes non-negotiable: without clear visibility into what agents are doing, why they are doing it, and which tools they are invoking, unnecessary autonomy can quietly expand the attack surface". ASI03 detection items: "Monitor when an agent gains new permissions indirectly through delegation chains" and detect "device-code style phishing flows by monitoring when agents request new scopes or reuse tokens outside their original, signed intent." Mitigation 7 also calls for "automated revocation on idle or anomaly." — [OWASP Agentic Top 10 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- GitHub Apps: "GitHub Apps indicate that the action was performed by the app on behalf of the user". Copilot agent: "commits are authored by Copilot, with the developer who assigned the issue...marked as the co-author." — [GitHub Docs: GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app); [GitHub Docs: Copilot coding agent risks](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)
- Unique credentials make audit possible: with Vault dynamic DB credentials "it makes auditing much easier when questionable data access is discovered." — [Vault database engine](https://developer.hashicorp.com/vault/docs/secrets/databases)
- MCP on token passthrough: "The MCP Server will be unable to identify or distinguish between MCP Clients"; "The downstream Resource Server's logs may show requests that appear to come from a different source with a different identity"; "Both factors make incident investigation, controls, and auditing more difficult." Scope guidance: "Log elevation events (scope requested, granted subset) with correlation IDs". — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- NIST NCCoE questions: "How can we ensure that agents log their actions and intent in a tamper-proof and verifiable manner?" and "How do we ensure non-repudiation for agent actions and binding back to human authorization?"; area of interest "Logging and Transparency. Link specific AI agent and software systems actions to the identity of the non-human entity". — [NCCoE concept paper](https://www.nccoe.nist.gov/sites/default/files/2026-02/accelerating-the-adoption-of-software-and-ai-agent-identity-and-authorization-concept-paper.pdf)
- AWS Security blog's Agentic AI Security Scoping Matrix lists, for higher-autonomy scopes, controls including "Agent authentication", "Comprehensive action logging", "Reasoning chain capture", "Continuous behavioral logging" and "Behavioral baselines for normal agent operations". — [AWS Security Blog: The Agentic AI Security Scoping Matrix](https://aws.amazon.com/blogs/security/the-agentic-ai-security-scoping-matrix-a-framework-for-securing-autonomous-ai-systems/)
- AWS break-glass: "Monitor the emergency access account for activity by creating EventBridge rules ... Send notifications to your security operations center when activity happens outside of an ongoing emergency event". — [AWS SEC03-BP03](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_permissions_emergency_process.html)
- PIM: "Get **notifications** when privileged roles are activated" and "Download **audit history**". — [Microsoft Learn: PIM](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-configure)

### Inferences
- **[Inference]** Audit logs live in the resource owner's system (forge audit log, cloud trail, Vault audit), outside the agent's reach, so they survive agent compromise, unlike harness transcripts the agent process can write. They only become a gate when paired with automated revocation (OWASP "automated revocation on idle or anomaly").
- **[Inference]** For harness-forge, "audit" recommendations should be labelled detective; they never satisfy a "must hold" rule on their own.

### Gaps
- Specific forge/cloud log fields that mark an action as agent-originated (e.g. GitHub audit log actor types for apps vs users) were not fetched.

## 4. What each control achieves against honest mistakes vs a compromised / prompt-injected agent; limits

### Takeaway
Identity controls cap blast radius equally for mistakes and attacks, because they do not depend on the agent's judgement. They do not stop misuse of authority the agent legitimately holds (a hijacked agent can still do anything its token allows), they do not stop exfiltration through allowed channels, and they can be bypassed by confused-deputy designs and token passthrough. Short lifetimes shrink, not eliminate, the value of stolen tokens.

### Cited Findings
- Authorization must sit downstream, not in the model: "Implement authorization in downstream systems rather than relying on an LLM to decide if an action is allowed or not." — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- Prompt injection is the usual lever for identity abuse: ASI03 "often leverages Prompt Injection (LLM01:2025), and because of agent permissions, tool integrations, and multi-agent systems, the impact can amplify". — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- Limit: legitimately granted privilege is ASI02, distinct from ASI03: ASI02 is "an unintended or unsafe use of already granted privilege by a principal misusing its own tools." — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- Confused deputy among agents: "A compromised low-privilege agent can relay valid-looking instructions to a high-privilege agent, which executes them without re-checking the original user's intent". Un-scoped inheritance: "A narrow worker then receives excessive rights." TOCTOU: "Permissions may be validated at the start of a workflow but change or expire before execution." — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- OAuth confused deputy in MCP proxies: possible when the proxy "uses a **static client ID**", allows dynamic registration, the third-party AS sets a consent cookie, and the proxy lacks per-client consent; result: "The attacker now has access to the third-party API as the compromised user". Mitigation: "MCP proxy servers **MUST** implement per-client consent". — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Token passthrough/audience: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." Risk: "If the token is accepted by multiple services without proper validation, an attacker compromising one service can use the token to access other connected services." Spec: "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience"; clients "**MUST** implement Resource Indicators for OAuth 2.0 as defined in RFC 8707"; "The MCP server **MUST NOT** pass through the token it received from the MCP client." — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices); [MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- Token theft: "Attackers who obtain tokens stored by the client, or tokens cached or logged on the server can access protected resources with requests that appear legitimate to resource servers." "Authorization servers **SHOULD** issue short-lived access tokens to reduce the impact of leaked tokens." — [MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- Broad scopes amplify theft: a stolen token "carrying broad scopes (`files:*`, `db:*`, `admin:*`)" enables "lateral data access, privilege chaining, and difficult revocation". — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Cloud metadata as a credential source an agent-run client can be tricked into reaching: "URLs targeting `http://169.254.169.254/` (AWS/GCP/Azure metadata service) can exfiltrate cloud credentials". — [MCP Security Best Practices: SSRF](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Scope of MCP authorization: "Authorization is **OPTIONAL** for MCP implementations"; STDIO implementations "**SHOULD NOT** follow this specification, and instead retrieve credentials from the environment." — [MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- Short-lived ≠ unusable: a GitHub installation token is valid for 1 hour; OIDC cloud tokens are valid "for a single job". — [GitHub installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app); [GitHub OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect)
- Guardrail limits: SCPs do not restrict the management account, service-linked roles, or resource-based-policy grants to outside principals; boundaries' implicit denies "do not limit resource-based policies". — [AWS SCPs](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html); [AWS permissions boundaries](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)
- Human approval for elevation must be bound to intent: ASI03 "Define Intent: Bind OAuth tokens to a signed intent that includes subject, audience, purpose, and session. Reject any token use where the bound intent doesn't match the current request." — [OWASP ASI03 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)

### Inferences
- **[Inference]** Honest mistake (wrong command, wrong account, over-eager cleanup): scoped identity, boundaries/org policy and required review prevent most damage outright; JIT approval adds a human checkpoint; audit gives quick diagnosis.
- **[Inference]** Compromised / injected agent: the same caps hold, but the attacker inherits whatever the token can do for its lifetime, including exfiltration through any allowed read path plus any allowed outbound channel. Identity controls must therefore be paired with egress limits and with keeping secrets out of the agent's environment (env vars, metadata endpoint, credential files); a short TTL bounds but does not prevent a session-length attack.
- **[Inference]** An approval gate defends only if the approver sees the real action (OWASP's dry-run/diff and signed-intent advice); an approver rubber-stamping agent-written summaries is vulnerable to the same injected content (ties to OWASP ASI09 human-agent trust exploitation, not detailed here).
- **[Inference]** For stdio MCP servers and local CLIs, credentials come from the environment, so the identity gate is whichever credential the developer placed there; harness-forge should recommend placing agent-specific scoped credentials, not the developer's personal ones.

### Gaps
- No fetched primary source quantifies how often short TTLs actually defeat token theft in agent incidents.
- Concrete published incidents of agent token exfiltration were outside this pass; the repo's `docs/guide/security.md` and `research-notes/agent-harness-security.md` already cover CI prompt-injection credential extraction.

## 5. Guidance specific to AI agents from authoritative bodies

### Takeaway
As of October 2026: OWASP (LLM06:2025 Excessive Agency; Top 10 for Agentic Applications 2026, especially ASI03) and the MCP specification (2025-11-25 authorization + security best practices) are the concrete, normative sources. NIST's NCCoE is at concept-paper stage. AWS has published an agentic scoping matrix. No CISA agent-specific identity guidance was verified in this pass.

### Cited Findings
- OWASP LLM06:2025 Excessive Agency root causes: "excessive functionality", "excessive permissions", "excessive autonomy"; mitigations quoted in sections 1–4. — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- OWASP Top 10 for Agentic Applications 2026, published December 9, 2025 ("Version 2026, December 2025" on the PDF); ASI03 "Identity and Privilege Abuse" "maps one-to-one to T3: Privilege Compromise" in OWASP's Agentic Threats and Mitigations and "Identity & Privilege Abuse is the agentic evolution of Excessive Agency (LLM06:2025)". — [OWASP resource page](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/); [PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- MCP authorization (spec 2025-11-25) is OAuth 2.1-based; requires PKCE ("MCP clients **MUST** implement PKCE"), audience binding via RFC 8707, "Access tokens **MUST NOT** be included in the URI query string", and no token passthrough. — [MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

## 6. When identity controls complement a harness permission rule vs replace building anything in the harness

### Takeaway
Use an identity gate alone when the rule is about what the agent may do to an external system and the system supports scoping (the agent simply lacks the credential). Use both when the identity system is coarser than the rule, when the harness gives earlier, cheaper feedback, or when the resource is local (files, shell) where the identity is the developer's own. Use the harness alone only for local, low-stakes rules where an outside gate does not exist.

### Cited Findings
- The authoritative pattern is to put authorization in the downstream system: "Implement authorization in downstream systems rather than relying on an LLM to decide if an action is allowed or not." — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- OWASP recommends expressing tool limits "as IAM or authorization policy stanzas attached to each tool, rather than relying on ad-hoc conventions", while still running "tool or code execution in isolated sandboxes" with "outbound allowlists" (i.e. both layers). — [OWASP ASI02 in Agentic Top 10 PDF](https://genai.owasp.org/download/52117/?tmstv=1765059207)
- GitHub's own agent combines layers: forge-side rules (requester cannot approve, workflows wait for approval, single branch) plus environment-side restriction ("restricts Copilot cloud agent's access to the internet"). — [GitHub Docs: Copilot coding agent risks](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)
- MCP local servers fall back to environment credentials ("retrieve credentials from the environment"), and the spec advises clients to "Warn that MCP servers run with the same privileges as the client" and to "Execute MCP server commands in a sandboxed environment with minimal default privileges". — [MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization); [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Repo context: the knowledge base already states "Any committed agent config can be changed by a pull request" and routes secrets to "a secret manager or short-lived tokens". — `docs/overview.md` in this repository (lines on configuration and automation).

### Inferences
- **[Inference]** Decision heuristics for harness-forge:
  - **Outside gate replaces harness work**: "agent must never deploy to prod / merge to main / delete cloud resources / read prod secrets" when the agent's identity can be denied those rights (forge rulesets, environment protection, IAM/SCP, Vault policy). A harness deny rule adds little security there, only earlier feedback.
  - **Both**: rules where the outside system cannot express the nuance (e.g. "only run migrations against the dev DB" when one credential reaches both), where the credential is the developer's own (local CLI with personal cloud profile), or where cost/latency of a failed external call matters. The harness rule gives fast, friendly refusal; the identity gate is the backstop.
  - **Harness only**: local file and shell behaviour with no external authority involved (formatting, test conventions); no outside identity control exists, though OS sandboxing remains a separate gate covered by other research.
  - **Nothing extra**: read-only, public data where the agent identity already lacks write rights.
- **[Inference]** Always recommend an outside gate when the rule must survive prompt injection, because harness permissions run inside the process an injected agent influences and are changeable by PR; identity controls are enforced by a different principal.
- **[Inference]** An identity gate is weakened if the agent's environment also holds a broader credential (developer token, metadata endpoint, cached SSO). Harness-forge should pair "give the agent identity X" with "ensure no broader credential is reachable", which the harness sandbox/env-scrubbing can support.

### Gaps
- No primary source gives an explicit decision table for "identity vs harness"; the heuristics above are inference from the cited principles.
