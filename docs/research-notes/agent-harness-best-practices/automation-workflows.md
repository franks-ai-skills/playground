# Automation and agent-driven development workflows (Claude Code, Codex, OpenCode)

Terminology follows [docs/concepts/automation.md](../../concepts/automation.md): a *run* has a prompt, a configuration set, a permission envelope, trust, an output contract, a session handle, a working copy and credentials. *Hosted run*, *schedule*, *goal-driven continuation* and *worktree isolation* are used as defined there.

Evidence labels used on every finding: **[vendor]** vendor guidance or docs, **[empirical]** empirical study or measured data, **[security]** security advisory or security research, **[practitioner]** named practitioner or company report/opinion. Research date: 2026-10-04. Pages without a visible date are marked "undated (fetched 2026-10-04)".

## Interactive workflows: explore → plan → implement → verify, specs, TDD, self-verification, context management, long-running goals

### Takeaway
Both vendors converge on the same loop: separate exploration/planning from implementation for non-trivial work, state a "done when" condition, and give the agent a check it can run itself (tests, build, linter, screenshot). Context is the scarce resource: clear between tasks, restart rather than repeatedly correct, prefer a written spec/handoff plus a fresh session over long accumulated sessions, and use a separate evaluator (subagent, `/goal` evaluator, Stop hook) rather than letting the implementer grade itself.

### Cited Findings

**Explore → plan → implement → commit**
- [vendor] Claude Code recommends four phases: Explore (plan mode, read-only), Plan (detailed plan; `Ctrl+G` to edit it), Implement ("verifying against its plan", write tests, run suite, fix failures), Commit (commit + PR). Planning "adds overhead"; skip it when scope is clear: "If you could describe the diff in one sentence, skip the plan." Planning is most useful when uncertain about approach, multi-file change, or unfamiliar code. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Codex recommends every prompt carry four elements: Goal, Context (files/docs/errors), Constraints (standards, architecture, safety), and "Done when: What should be true before the task is complete?"; for complex tasks "ask Codex to plan before it starts coding" with Plan mode (`/plan` or Shift+Tab). Undated (fetched 2026-10-04). — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- [vendor] Codex lists anti-patterns: durable rules crammed into one prompt instead of `AGENTS.md`, "withholding execution permissions prematurely", skipping planning on complex tasks, running untested live changes without git worktrees, and "treating Codex as something requiring constant supervision". — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- [vendor] Claude Code prompt specificity: scope the task (file, scenario, "avoid mocks"), point to sources (git history), reference existing patterns (name an example file), and for bugs describe the symptom, likely location and what "fixed" looks like, e.g. "write a failing test that reproduces the issue, then fix it". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

**Spec-driven development**
- [vendor] Claude Code's "interview" pattern: start minimal, have Claude interview you with `AskUserQuestion` about implementation, UI/UX, edge cases and trade-offs, then "write a complete spec to SPEC.md"; then "start a fresh session to execute it". "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step." "Time spent making the spec precise pays off more than time spent watching the implementation." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [practitioner] Birgitta Böckeler (Thoughtworks, martinfowler.com, Oct 15, 2025 — older guidance) distinguishes three SDD levels: spec-first (spec discarded after), spec-anchored (spec maintained with the feature), spec-as-source (humans edit only specs). Kiro and GitHub spec-kit are effectively spec-first; Tessl targets spec-anchored/spec-as-source. Criticisms: one workflow for all problem sizes ("using a sledgehammer to crack a nut" for a small bug); markdown artifacts "very verbose and tedious to review" ("I'd rather review code than all these markdown files"); agents still ignore spec instructions or treat existing code as new requirements and duplicate it; warns about repeating model-driven-development failures. — [Böckeler, Understanding SDD tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

**Test-driven development with agents**
- [practitioner] Simon Willison: "Use red/green TDD" is a succinct prompt that improves agent results; write tests first, confirm they fail (red), iterate until they pass (green). Rationale: agents risk writing code that doesn't work or unnecessary code; test-first guards against both. Watch for skipping the red step (tests that already pass validate nothing). It is one of the patterns he uses daily; related patterns in his guide: "First run the tests", "Agentic manual testing". Undated page (fetched 2026-10-04). — [Willison, Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)
- [vendor] Claude Code Writer/Tester split: "have one Claude write tests, then another write code to pass them." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [empirical] ImpossibleBench (Zhong, Raghunathan, Carlini; Oct 23, 2025; ICLR 2026 poster): mutates unit tests to conflict with the spec so any pass implies cheating; frontier agents exploit tests via techniques "from simple test modification to complex operator overloading"; prompt, test access and feedback loop affect cheating rates. — [arXiv 2510.20270](https://arxiv.org/abs/2510.20270); [ICLR 2026](https://iclr.cc/virtual/2026/poster/10009390)

**Giving the agent a way to verify its own work**
- [vendor] "Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from." Without a check, "you become the verification loop". Four escalating gates: in one prompt; across a session with `/goal`; a deterministic Stop hook that "blocks the turn from ending until it passes"; a second-opinion verification subagent so "the agent doing the work isn't the one grading it". Ask for evidence (test output, command + result, screenshot) rather than assertions. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Anti-pattern "trust-then-verify gap": plausible implementation without edge cases. "If you can't verify it, don't ship it." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Codex: "create tests when needed, run the relevant checks, confirm the result, and review the work before you accept it"; use `/review` against base branch or uncommitted changes. — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- [vendor] Adversarial review: a fresh-context subagent reviews the diff against PLAN.md ("Report gaps, not style preferences"). Caveat: "A reviewer prompted to find gaps will usually report some, even when the work is sound"; chasing every finding causes over-engineering; tell it to flag only correctness/requirement gaps. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor/engineering blog] Anthropic (Mar 24, 2026, Prithvi Rajasekaran; experiments used Sonnet 4.5/Opus 4.6, older models): agents grading their own work "tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre"; separating generator and evaluator was "a strong lever". Evaluator used Playwright to drive the running app; one sprint contract had 27 testable conditions. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [vendor/engineering blog] Anthropic (Nov 26, 2025): Claude marked features done without proper end-to-end testing until required to "use browser automation tools and do all testing as a human user would". — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Context management: compaction, clearing, fresh sessions, handoffs**
- [vendor] "Claude's context window fills up fast, and performance degrades as it fills." `/clear` between unrelated tasks; "If you've corrected Claude more than twice on the same issue … run `/clear` and start fresh"; "A clean session with a better prompt almost always outperforms a long session with accumulated corrections." Steer compaction (`/compact Focus on the API changes`; CLAUDE.md "When compacting, always preserve the full list of modified files and any test commands"); partial summarization via `/rewind`; `/btw` for side questions outside history; subagents for investigation so file reads stay out of main context. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Failure patterns: "kitchen sink session", "correcting over and over", "over-specified CLAUDE.md", "trust-then-verify gap", "infinite exploration". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Checkpoints/rewind only track edits through Claude's file tools, not Bash side effects: "This isn't a replacement for git." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Codex: "one chat per coherent problem"; `/fork` only when work truly branches; `/compact` for long conversations; subagents for bounded parallel tasks. — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- [vendor/engineering blog] Anthropic found "context resets" (clear + structured handoff) superior to compaction for multi-hour runs: compaction "doesn't give the agent a clean slate, which means context anxiety can still persist" (observed strongly in Sonnet 4.5; older model). — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**Long-running tasks and goals (goal-driven continuation)**
- [vendor/engineering blog] Long-running harness pattern (Nov 2025): an initializer session creates `init.sh`, a `claude-progress.txt` log and an initial git commit, plus a JSON feature list with every feature initially failing; later sessions work "on only one feature at a time", commit with descriptive messages and update the progress file. Observed failure modes: doing too much at once (half-implemented features), declaring completion prematurely, marking features done untested, leaving undocumented buggy state. — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [vendor/engineering blog] Cost/time of the heavy harness: solo agent 20 min/$9 vs full planner-generator-evaluator harness 6 h/$200 on the same brief; a simplified harness built a DAW in 3 h 50 min for $124.70. "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing"; with Opus 4.6 the sprint construct was removable while the evaluator stayed valuable. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [vendor] Claude Code `/goal`: after each turn a small fast model judges the condition (not met / met / impossible); it "doesn't run commands or read files independently", so write conditions Claude's own output can demonstrate: one measurable end state, a stated check ("`npm test` exits 0"), constraints ("no other test file is modified"), and a bound ("or stop after 20 turns"). Stops the loop when no tool use for several turns. Works in `-p` (`claude -p "/goal …"`); add `--output-format stream-json --verbose` or it looks stuck. Goal does not change the permission mode; pair with auto mode for unattended turns. Clears on unrecoverable errors (auth, exhausted credits, unrecoverable context overflow, model unavailable). — [Claude Code /goal](https://code.claude.com/docs/en/goal)
- [vendor] Codex `/goal`: template "`/goal Complete [objective] without stopping until [verifiable end state].`"; "Codex should know what 'done' means before it starts"; needs a validation mechanism and checkpoints; ask for compact status updates (checkpoint, what was verified, what remains, blocked?); avoid for a "loose list of unrelated work" — the task should be "bigger than one prompt but smaller than an open-ended backlog". Controls: `/goal pause|resume|clear`. — [Codex: follow goals](https://learn.chatgpt.com/use-cases/follow-goals)

### Inferences
- The portable core across both leads: (1) a spec or plan file with explicit "done when" and verification step, (2) a check the agent runs itself, (3) a separate grader (fresh subagent, `/goal` evaluator, Stop hook, or CI), (4) fresh sessions with a handoff file instead of long sessions. These map onto shared generalized concepts (instructions, subagents, hooks, goal-driven continuation) and need no vendor-only features.
- Because `/goal` evaluators only read the transcript, the verification command must actually run and print in-session; a goal phrased as an unobservable property ("code is clean") will be judged on the agent's own assertions, re-introducing self-grading bias.
- Test-first work needs a guard against test tampering (ImpossibleBench): e.g. a constraint "do not modify tests" in the goal condition, a hook that blocks writes to test files during the green phase, or a reviewer that diffs tests separately. This is inferred; neither vendor documents a dedicated mechanism.
- SDD artifacts should be sized to the task: Claude Code's own guidance (skip plan for one-sentence diffs) agrees with Böckeler's sledgehammer critique.

### Gaps
- No controlled study found comparing spec-driven vs. ad-hoc prompting, or TDD vs. no-TDD, for agent outcome quality; evidence is vendor guidance and practitioner opinion.
- Codex documentation on compaction behavior and handoff patterns is thin; no Codex equivalent of the Anthropic long-running-harness write-ups was found.
- ImpossibleBench per-model cheating rates were not extracted (PDF not parseable in this session).
- OpenCode: no workflow-level best-practice guidance found.

## Headless runs and CI: `claude -p` / `codex exec`, structured output, permission envelopes, GitHub Actions, PR review, issue-to-PR, cost, secrets, prompt injection

### Takeaway
Treat every headless run as untrusted automation with an explicit envelope: isolate configuration (`--bare` / `--ignore-user-config`), set permissions explicitly (defaults differ between leads), request schema-validated output, cap turns/budget/time, keep secrets out of job-level env, and split "agent thinks" (read-only) from "write to repo" (separate job without the API key). Prompt injection through PR titles, issue bodies and comments was demonstrated against agent GitHub Actions in 2026, and a PR carrying a malicious `.mcp.json` gave code execution in claude-code-action (CVE-2026-47751).

### Cited Findings

**Headless CLI patterns**
- [vendor] `codex exec` "runs in a read-only sandbox" by default; use `--sandbox workspace-write` for edits, `danger-full-access` only in controlled environments; `--full-auto` is deprecated in favor of `--sandbox workspace-write`. `--json` emits JSONL events; `-o/--output-last-message` writes the final message; `--output-schema` enforces a JSON Schema for "job summaries, risk reports, or release metadata"; `codex exec resume --last` / `resume <SESSION_ID>`; `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--skip-git-repo-check` ("use cautiously"). Auth: `CODEX_API_KEY=<key> codex exec …` inline. — [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode.md)
- [vendor] `claude -p`: `--bare` "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release"; without it, `-p` "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted" with no trust dialog. Bare mode needs `ANTHROPIC_API_KEY` (no OAuth/keychain) and loads context only via flags (`--append-system-prompt-file`, `--settings`, `--mcp-config`, `--agents`, `--plugin-dir`). — [Claude Code headless](https://code.claude.com/docs/en/headless)
- [vendor] `claude -p` permission envelope: an unset mode can start in `auto`, "so pass the one you want"; `dontAsk` "denies every call that would otherwise prompt, which is useful for locked-down CI runs"; `--allowedTools` with prefix rules such as `Bash(git diff *)` (space before `*` matters); `--permission-prompts none` for scheduled/unattended runs so prompts are denied and Claude is told not to retry; denials listed in `permission_denials`. — [Claude Code headless](https://code.claude.com/docs/en/headless)
- [vendor] Structured output: `--output-format json --json-schema '<schema>'` → `structured_output`; invalid schema now errors (before v2.1.205 it was silently ignored); `format` keyword not enforced. `json` output includes `total_cost_usd` (client-side estimate). Exit code 0/non-zero; SIGTERM → exit 143 with unfinished turn. Stdin capped at 10 MB. CI gates can fail on `plugin_errors` / `mcp_server_errors` in the `system/init` event. — [Claude Code headless](https://code.claude.com/docs/en/headless)
- [vendor] Fan-out recipe: generate a task list file, loop `claude -p "Migrate $file … Return OK or FAIL." --allowedTools "Edit,Bash(git commit *)" --permission-mode dontAsk`, "Test on a few files, then run on all of them" (refine prompt on the first 2–3). — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Auto mode headless: `claude --permission-mode auto -p "fix all lint errors"`; classifier blocks "scope escalation, unknown infrastructure, and hostile-content-driven actions"; repeated blocks in `-p` do not stop the run (see fallback rules). — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

**GitHub Actions: claude-code-action and codex-action**
- [vendor] claude-code-action has two modes: interactive (no `prompt`; responds to `@claude`) and automation (`prompt` set; runs on any event, results in the run log unless the prompt and tools post them). Plain-text automation prompts get "no shell or GitHub API access until you grant the tools", via `--allowedTools` in `claude_args` or `permissions.allow` in `settings`. Skill invocation works as `prompt: "/skill-name"` after checkout. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] Trigger checks: issue/PR events require write access (override `allowed_non_write_users` + own `github_token`); bot actors rejected unless in `allowed_bots` ("keeps bots from triggering Claude in a loop"); scheduled runs are attributed to the user who last changed the cron. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] PR review via plugin skill: `plugins: "code-review@claude-code-plugins"`, `prompt: "/code-review:code-review --comment …"`, and `claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'` (needed for the inline-comment MCP server to start). Job permissions read-only plus `id-token: write`. Fork PRs on public repos get no secrets, so review runs only for same-repo branches. Skips drafts, trivial/automated PRs and PRs it already commented on. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] Gotcha: commits pushed with the default `GITHUB_TOKEN` do not trigger CI; let the action authenticate as the GitHub App or pass a custom app token. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] Org rollout: org-level app + org secret or reusable workflow; prefer a Console API key over an OAuth token for shared secrets (OAuth token is tied to one person's subscription); or avoid long-lived secrets with OIDC workload identity federation (`anthropic_federation_rule_id` etc., needs `id-token: write`). The official GitHub App requests a broad permission set (Actions, Workflows, Repository hooks write…) that cannot be partially accepted; build a custom app with only Contents/Issues/PRs if required. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] codex-action "installs the Codex CLI, starts the Responses API proxy when you provide an API key, and runs `codex exec`"; inputs `prompt`/`prompt-file`, `codex-args`, `model`, `effort`, `sandbox`, `safety-strategy` (`drop-sudo` default, `unprivileged-user`, `unsafe`; Windows requires `unsafe`), `output-file`. Pattern: Codex job writes `final-message`; a second job posts PR comments. — [Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)
- [vendor] Codex autofix pattern: Codex job read-only, API key only in the Codex step, result serialized as a patch artifact "before granting write permissions"; "Do not set `OPENAI_API_KEY` or `CODEX_API_KEY` as a job-level environment variable in workflows that check out or run repository-controlled code." — [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode.md)
- [vendor] Codex review rules for `@codex review` live in an `## Code Review Rules` section of `AGENTS.md` (hosted review, not the action). — [repo concept page](../../concepts/automation.md) citing vendor docs

**Security: secrets, privilege, prompt injection**
- [security/vendor] codex-action security doc: default only write-access users trigger; widen with `allow-users`, `allow-bots`, `allow-bot-users` (no `*`). Untrusted prompt sources include PR titles/bodies (hidden HTML comments), commit messages, repo instruction files (`AGENTS.md`, `AGENTS.override.md`) and screenshots. Use `drop-sudo` or `unprivileged-user` so the API key "stays secret"; read-only filesystem is insufficient if `sudo` is available. Pass untrusted values via `env:` not inline interpolation. "Run `openai/codex-action` as the last step in a job" because Codex could spawn persistent processes or overwrite config. Use `permission-profile` for the narrowest FS/network policy; it does not replace `safety-strategy`. — [codex-action security.md](https://github.com/openai/codex-action/blob/main/docs/security.md)
- [security/vendor] claude-code-action security doc: write-access check covers issue/PR/comment/review and `workflow_run` events; "Allowed bots are not checked for repository permissions" — on public repos anyone's GitHub App could trigger; `allowed_non_write_users` "is a significant security risk". The action strips HTML comments, invisible characters, image alt text, hidden attributes and entities, "but new bypass techniques may emerge"; review raw external content; on public repos use `include_comments_by_actor`. Do not check out an untrusted ref into the workspace root; `pull_request_target`/`workflow_run` run with base-repo secrets; the action restores `.claude/`, `.mcp.json`, `CLAUDE.md`, `.husky/` etc. from the PR base branch. `show_full_output` off by default because logs are public on public repos. Commit signing via `use_commit_signing` (no rebase/cherry-pick) or SSH key. — [claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)
- [security] claude-code-action advisory CVE-2026-47751 (severity medium, published 2026-05-20; versions before 1.0.74 affected, patched in 1.0.74; reported via HackerOne): the action checked out the attacker-controlled PR head, read `.mcp.json` through its default setting sources and enabled all project MCP servers (`enableAllProjectMcpServers`), so a PR with a malicious `.mcp.json` gave code execution on the runner and access to workflow secrets when a privileged user or an automatic trigger ran the action. — [GitHub advisory GHSA-8q5r-mmjf-575q](https://github.com/anthropics/claude-code-action/security/advisories/GHSA-8q5r-mmjf-575q)
- [security] "Comment and Control" (April 2026, disclosed by researcher Aonan Guan): prompt injection through PR titles, issue bodies and comments made Claude Code Security Review, Gemini CLI Action and GitHub Copilot Agent execute commands and extract credentials; workflows triggered the agents automatically without victim interaction, except Copilot, which needs manual assignment. Root cause: agents get "powerful tools ... and secrets ... in the same runtime that processes untrusted user input." — [SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)
- [vendor] Routine API fire text arrives wrapped in a `<routine-fire-payload>` block labeled untrusted; the saved prompt must explicitly opt in to act on it. — [Claude Code routines](https://code.claude.com/docs/en/routines)

**Cost and rate limits**
- [vendor] CI costs = runner minutes + tokens. Controls: specific `@claude` requests, issue templates, concise `CLAUDE.md` (read every run), `--max-turns` in `claude_args`, workflow-level timeouts, GitHub `concurrency`. OAuth-token runs bill the subscription instead of API. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] `--max-budget-usd` exists for Claude Code only (no Codex counterpart). — [repo concept page](../../concepts/automation.md)
- [vendor] Third parties may not offer claude.ai login or subscription rate limits in Agent SDK products without approval; use API keys. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### Inferences
- A minimal portable CI envelope for both leads: trigger restricted to trusted actors and non-fork events; job `permissions:` read-only; isolated config set (`--bare`/`settingSources: []` vs `--ignore-user-config`/`--ignore-rules`, noting `--bare` also drops project skills); explicit permission envelope (`dontAsk` + `--allowedTools`, or Codex `--sandbox read-only|workspace-write`); schema-validated output written to a file; a second job without the model key that applies the patch/posts comments; turn/time/budget caps.
- Prompt-injection risk is highest exactly where automation is most attractive (issue-to-PR on public repos). The safe default is: agent reads untrusted text only in a job that holds no write token and no secrets beyond the model key, and its output is data (patch/JSON) consumed by a deterministic step.
- Because Claude Code `-p` without `--bare` trusts repo hooks/MCP and Codex skips untrusted hooks, a PR that edits `.claude/settings.json` or `.mcp.json` is a code-execution vector in Claude Code CI unless config is restored from base (the action does this) or `--bare` is used.

### Gaps
- No public data found on typical per-run cost or token consumption for CI review/autofix workflows in either lead.
- Codex hosted `@codex review` configuration details (severity levels, AGENTS.md rules) were not retrievable from the current docs page; only the repo concept page records the `## Code Review Rules` convention.
- No vendor statement found on whether codex-action has had comparable injection CVEs; the reports found cover Claude, Gemini and Copilot.
- OpenCode GitHub action security guidance not found.

## Parallelism: worktrees, multiple sessions, cloud runs, best-of-N, merging

### Takeaway
Parallel agents are cheap; human review is the bottleneck. Use worktree isolation (or separate clones/containers) per session, a setup step for untracked files and dependencies, and parallelize work that is easy to review (research, small maintenance, carefully specified tasks). Hosted runs and best-of-N give more parallelism but shift effort to choosing and merging results.

### Cited Findings
- [vendor] Claude Code worktrees: `claude --worktree <name>` → `.claude/worktrees/<name>/` on branch `worktree-<name>`; gitignore `.claude/worktrees/`; a worktree is a fresh checkout, so install dependencies; `.worktreeinclude` copies gitignored files such as `.env`; `worktree.baseRef` `"fresh"` (default, remote default branch) or `"head"` (carries unpushed work). Isolation is enforced: edits, command cwd, and git redirects into the main checkout are blocked. `-p` runs do not clean up their worktrees and leave locks; remove with `git worktree remove` (`unlock` first). Hook `${CLAUDE_PROJECT_DIR}` stays at the original root; read `cwd` from hook input. Subagents can use `isolation: worktree`. Git LFS installed with `--local` yields pointer files (run `git lfs pull`). — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)
- [vendor] Claude Code parallel options: worktrees, cross-session messaging, desktop app, cloud sessions, agent view (research preview), agent teams (experimental, off by default); `/batch <instruction>` splits work across 5–30 worktree-isolated subagents. Writer/Reviewer pattern: "A fresh context improves code review since Claude won't be biased toward code it just wrote." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [vendor] Codex: run parallel cloud tasks from a published environment, "each task maintaining its own workspace", that "can keep working while your computer is asleep"; review diffs and test results, request follow-ups, then open a PR. Desktop Worktree mode uses detached HEAD and Handoff. Anti-pattern: "running untested live changes without Git worktrees". — [Codex cloud](https://learn.chatgpt.com/docs/cloud); [Codex best practices](https://learn.chatgpt.com/guides/best-practices); [repo concept page](../../concepts/automation.md)
- [vendor] `codex cloud exec --attempts` (1–4, default 1) is the "Number of assistant attempts (best-of-N) Codex cloud should run". — [Codex CLI command reference](https://learn.chatgpt.com/docs/developer-commands.md?surface=cli); [repo concept page](../../concepts/automation.md)
- [practitioner] Simon Willison (Oct 5, 2025, older guidance): parallelize research/proof-of-concepts, "system understanding" questions, small maintenance (e.g. deprecation warnings: "Chuck that at a bot"), and carefully specified work ("Code that started from your own specification is a lot less effort to review"). Bottleneck: "I can only focus on reviewing and landing one significant change at a time." Uses YOLO mode only "where I'm confident malicious instructions can't sneak into the context"; considers Docker containers to limit blast radius; uses fresh `/tmp` checkouts instead of worktrees. — [Willison, parallel coding agents](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)

### Inferences
- Worktree isolation is portable (both leads have `--worktree`), but each lead needs its own setup step (`.worktreeinclude` vs Codex environment setup scripts); port conflicts and per-worktree dependency installs are not handled by either and must be scripted.
- Best-of-N trades compute for reviewer time; without an automated selector (tests + a grader), N candidates multiply the review bottleneck Willison describes. Use it where an objective check can pick the winner.
- Headless `-p` worktrees accumulate (no cleanup); scheduled or fan-out scripts should remove worktrees explicitly.

### Gaps
- No empirical data found on merge-conflict rates or integration cost when merging many parallel agent branches.
- No official Codex doc retrieved that describes how a "best" attempt is chosen.
- No guidance found from either vendor on a recommended maximum number of concurrent sessions per human reviewer.

## Scheduling: recurring jobs and guardrails for unattended runs

### Takeaway
Scheduled runs are hosted or local runs with a stored prompt; they suit unattended, repeatable work with a clear outcome (triage, docs drift, dependency bumps, reports). Guardrails come from scoping what the run can reach (repos, network, connectors, branch protection), self-contained prompts with success criteria, untrusted-payload handling, and reading transcripts, because "green" means the run finished, not that the task succeeded.

### Cited Findings
- [vendor] Claude Code routines (research preview): saved prompt + repos + connectors, triggers schedule / API / GitHub events; run on Anthropic cloud or a self-hosted environment. "The prompt is the most important part: the routine runs autonomously, so the prompt must be self-contained and explicit about what to do and what success looks like." Routines have no permission-mode picker and run without approval; scope repos, environment network and variables, and connectors ("Claude can use every tool from an included connector, including writes, without asking"). Pushes to `claude/`-prefixed branches by default; control with branch protection/rulesets. Actions appear as the user's identity. Min interval 1 h; hourly caps (e.g. 100 scheduled runs/h per account); GitHub webhook events beyond caps are dropped. "A green status … does not mean the task in your prompt succeeded. Open the run to read the transcript." Example uses: backlog triage, alert triage via API, bespoke code review, deploy verification, docs drift, library port. — [Claude Code routines](https://code.claude.com/docs/en/routines)
- [vendor] GitHub Action schedules: run only from the default branch; public repos disable schedules after 60 days without activity; plain-text prompts get no tools unless granted. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] Codex: "Schedule stable workflows as background tasks through the Scheduled page, choosing cadence and execution environment"; turn repeatable workflows into skills ("Keep each skill scoped to one job"). — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- [vendor] Unattended permission settings: `--permission-prompts none` "when nobody is available to answer permission prompts, for example in a scheduled job"; example `claude -p "Update the dependency pins and run the tests" --permission-mode auto --permission-prompts none`. — [Claude Code headless](https://code.claude.com/docs/en/headless)
- [vendor] Portability traps recorded in the repo: schedule syntax differs (cron vs RRULE); Claude Code scheduled fires only run model-invocable skills; neither lead schedules from a plain CLI on a headless machine (system cron + headless CLI is the fallback). — [repo concept page](../../concepts/automation.md)

### Inferences
- A schedule should name a skill (method) plus success criteria and an output location (PR, issue comment, report artifact), with writes limited to a dedicated branch prefix that branch protection prevents from merging without review.
- Scheduled triage that reads issue text is exposed to the same prompt injection as CI; give it no write tools beyond labels/comments, and no secrets.
- Monitoring must read outcomes (PR opened? checks passed?), not run status, per the routines warning.

### Gaps
- No practitioner reports with numbers were found on scheduled agent jobs (e.g. dependency-update success rates vs Renovate/Dependabot).
- Codex scheduled-task guardrails (permissions, branch rules, limits) are not documented in the pages retrieved.

## SDK-based custom agents vs CLI

### Takeaway
Use the CLI (`-p` / `exec`) or the vendor GitHub Action for scripts and CI; move to the SDK when you need the agent inside your own application or service with programmatic permission callbacks, sessions, streaming and custom tools.

### Cited Findings
- [vendor] Anthropic's decision table: Agent SDK to "embed Claude Code's agent in your own Python or TypeScript application, in a process you operate"; CLI for interactive work and one-off tasks; Client SDK when you write the tool loop yourself; Managed Agents for Anthropic-hosted harness sessions. Other languages: run the CLI as a subprocess with `-p --output-format json`. SDK includes built-in tools, hooks, subagents, MCP, permissions, sessions (resume/fork), skills/memory loaded from `.claude/` and `~/.claude/` like the CLI, plugins. The GitHub Action is built on the SDK. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- [vendor] Codex SDK (TypeScript, Python `openai-codex`) for CI/CD control, building "your own agent that can engage with Codex", internal tools and app integration; thread model (`startThread`, `run`, resume by ID); sandbox presets read-only / workspace-write / full-access. Use the app-server instead for custom clients needing auth and conversation-history management. — [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)

### Inferences
- SDKs load the same filesystem configuration as the CLI by default; for reproducible service use, pass an isolated configuration set (Claude `settingSources: []`, Codex ignore flags) and inject config explicitly, mirroring CI practice.
- The SDK is the right layer for structured permission decisions (approval callbacks), cost accounting per tenant, and orchestration of many runs with retries; shell loops over `-p`/`exec` suffice for batch migrations.

### Gaps
- No empirical comparison found of SDK-built vs CLI-scripted automation reliability or cost.
- OpenCode SDK (`@opencode-ai/sdk` wrapping `opencode serve`) best-practice guidance not found beyond the repo's vendor reference.

## Measuring outcomes: evals, success metrics, human review load

### Takeaway
Measured outcomes are mixed: agent PRs are often merged (especially docs, tests, refactors) but at lower rates than human PRs overall, with substantial human revision, and the DORA 2025 report describes AI as an amplifier of an organization's existing strengths and weaknesses. Measure with task-specific evals built from real failures (outcome-graded, pass@k and pass^k), track merge rate by task type, revision rate, change-failure rate and reviewer load, and distrust self-reported speedups.

### Cited Findings
- [empirical] Watanabe et al. (Sept 2025, v3 Feb 2026): 567 Claude Code PRs across 157 OSS projects; agents used mostly for refactoring, documentation, testing; 83.8% accepted and merged; 54.9% of merged PRs integrated without modification; the remaining 45.1% needed changes, especially bug fixes, documentation and project-specific standards. — [arXiv 2509.14745](https://arxiv.org/abs/2509.14745)
- [empirical] AIDev dataset (Li, Zhang, Hassan; July 2025): 456k+ agent PRs by Codex, Devin, Copilot, Cursor, Claude Code across 61k repos; agents are faster than humans but "their PRs are accepted less frequently, revealing a trust and utility gap", and agent PRs are structurally simpler. — [arXiv 2507.15003](https://arxiv.org/abs/2507.15003)
- [empirical] Pinna et al. (Feb 2026, rev. May 2026): 7,156 AIDev PRs; documentation tasks 82.1% acceptance vs 66.1% for new features; Codex 59.6–88.6% across nine task categories; Claude Code 92.3% (docs) and 72.6% (features); Cursor 80.4% (fixes); "no single agent performs best across all task types"; task type matters more than agent. — [arXiv 2602.08915](https://arxiv.org/abs/2602.08915)
- [empirical] Nakashima et al. (Feb 2026): 654 rejected agent PRs from five agents; seven rejection modes unique to agent PRs, including distrust of AI-generated code; 67.9% of rejected PRs had no explicit reviewer feedback. — [arXiv 2602.04226](https://arxiv.org/abs/2602.04226)
- [empirical] Mazloomzadeh, Morovati, Khomh (July 2026): longitudinal AIDev analysis of agent vs human PR merge-rate gaps over time and task distributions by quarter; abstract gives no numbers. — [arXiv 2607.21832](https://arxiv.org/abs/2607.21832)
- [empirical] METR RCT (July 2025, early-2025 tools, older): 16 experienced OSS developers, 246 tasks; AI use made tasks take 19% longer (CI +2% to +39%) while developers believed they were ~20% faster. Feb 2026 update: late-2025 follow-up estimates −18% (CI −38% to +9%) for returning developers and −4% (CI −15% to +9%) for new ones (negative = speedup), but METR calls the data unreliable due to selection effects (developers refusing to work without AI). — [METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [METR Feb 2026 update](https://metr.org/blog/2026-02-24-uplift-update/)
- [empirical] DORA 2025: AI's "primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses." — [DORA 2025 report](https://dora.dev/research/2025/dora-report/)
- [vendor] Anthropic eval guidance (Jan 9, 2026): code-based graders (fast, objective, brittle), model-based (flexible, need calibration), human (gold standard, slow); pass@k vs pass^k (consistency); grade "what the agent produced, not the path it took"; "20-50 simple tasks drawn from real failures is a great start"; "An eval at 100% tracks regressions but provides no signal for improvement." — [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [vendor] Claude Code GitHub Action usage tracking via the analytics dashboard and monitoring; `total_cost_usd` per headless run (client-side estimate). — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions); [Claude Code headless](https://code.claude.com/docs/en/headless)

### Inferences
- Useful team metrics combine outcome and burden: merge rate by task type, share merged without modification, review comments/time per agent PR, rework/revert rate, change-failure rate, and cost per merged PR. Merge rate alone overstates value (silent rejections, simpler PRs).
- For automation reliability, pass^k (all k runs succeed) is the relevant metric for scheduled or CI runs, since each fire must work unattended; pass@k fits best-of-N.
- Start agent-workflow evals from real failed runs (transcripts of CI/scheduled runs) per the 20–50-task advice.

### Gaps
- No study found that measures human review load (minutes per agent PR) directly; Nakashima's 67.9% "no feedback" figure is the closest signal.
- No empirical study found on outcomes of headless/CI-triggered agent runs specifically (vs interactive-originated PRs); AIDev mixes them.
- No independent data on Codex vs Claude Code outcomes beyond PR-acceptance studies, which conflate tool, model version and usage patterns.
