## 1. When is a skill the right tool (vs instruction file, subagent, hook, MCP server, script)?

### Takeaway
A skill is the right tool for a recurring *procedure* or specialized knowledge the model lacks, that is needed only sometimes, and where occasional non-activation is acceptable. Facts needed every turn belong in the instruction file; rules that must hold every time belong in hooks; isolation belongs in subagents; connectivity belongs in MCP; deterministic logic belongs in scripts (usually bundled inside the skill). Measured data shows implicit activation is unreliable, so knowledge the agent must always use is safer as always-loaded context.

### Cited Findings
- **[V]** Claude Code: use a skill when "you keep pasting the same instructions, checklist, or multi-step procedure into chat" or when a section of CLAUDE.md "has grown into a procedure rather than a fact"; skill content loads only when invoked, so "long reference material costs almost nothing until you need it". — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Claude Code: use CLAUDE.md for facts/conventions that apply to every conversation; subagents for tasks needing isolation from conversation history or running in the background; hooks for "rules that must hold every time an event occurs" and guidance that "shouldn't be skipped". — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Claude Code: if Claude stops following a skill mid-session, "move rules into hooks if they must hold every time"; after auto-compaction only the most recent invocation of each skill is re-attached, first 5,000 tokens per skill, 25,000 tokens combined, older skills "may drop entirely". — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Anthropic: "MCP connects to data; Skills teach Claude what to do with that data"; subagents are "specialized employees with their own context and tool permissions" and can use skills; projects/instructions say "here's what you need to know", skills say "here's how to do things" (2026-03-05). — [claude.com/blog/skills-explained](https://claude.com/blog/skills-explained)
- **[V]** Codex: "Prefer instructions over scripts unless you need deterministic behavior or external tooling"; "Keep each skill focused on one job"; use plugins to "bundle two or more skills together, or ship a skill alongside a connector". — [Codex build skills](https://learn.chatgpt.com/docs/build-skills)
- **[V]** agentskills.io: agents "typically only consult skills for tasks that require knowledge or capabilities beyond what they can handle alone. A simple, one-step request like 'read this PDF' may not trigger a PDF skill even if the description matches perfectly." Same statement in Anthropic's skill-creator. — [Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions.md); [Anthropic skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md)
- **[V]** agentskills.io: "if the agent already handles the entire task well without the skill, the skill may not be adding value." — [Best practices](https://agentskills.io/skill-creation/best-practices.md)
- **[E]** Vercel (Jude Gao, 2026-01-27, older): Next.js 16 docs as a skill vs an 8 KB compressed docs index in AGENTS.md. Pass rates: baseline 53%, skill (default) 53%, skill with explicit instructions 79%, AGENTS.md index 100%. "In 56% of eval cases, the skill was never invoked." Recommendation: skills for "vertical, action-specific workflows that users explicitly trigger", AGENTS.md for "general framework knowledge". Model and case counts not published. — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **[E]** SkillsBench (Li et al., arXiv 2602.12670, 2026-02-13; 86 tasks, 11 domains, Claude Code / Codex CLI / Gemini CLI, 7 model configs, 7,308 trajectories): curated skills +16.2 pp average, but +4.5 pp for software engineering vs +51.9 pp for healthcare; 16 of 84 tasks had negative deltas (e.g. taxonomy-tree-merge −39.3 pp). Effect is largest where pretraining coverage is weak. — [SkillsBench](https://arxiv.org/html/2602.12670v1)
- **[E]** SkillsBench: Claude Haiku 4.5 with skills (27.7%) beat Haiku without (11.0%) and matched Opus 4.5 without skills (22.0%). — [SkillsBench](https://arxiv.org/html/2602.12670v1)
- **[P]** Simon Willison (2025-10-16, older): skills are "very token efficient: each skill only takes up a few dozen extra tokens"; contrasts with GitHub's MCP server consuming "tens of thousands of tokens of context"; skills depend "entirely" on filesystem + command execution. — [simonwillison.net](https://simonwillison.net/2025/Oct/16/claude-skills/)
- **[P]** Thariq Shihipar (Anthropic Claude Code team, X post 2026-03-17, via mirror): Anthropic's internal skills cluster into 9 types: library/API reference, product verification, data fetching & analysis, business process automation, code scaffolding, code quality & review, CI/CD & deployment, runbooks, infrastructure operations. Skills can also register "on-demand hooks" (e.g. `/careful` blocking destructive commands) active only while invoked. — [original post](https://x.com/trq212/status/2033949937936085378), [mirror used](https://gitea.maison43.duckdns.org/gilles/claude-code-best-practice/src/branch/main/tips/claude-thariq-tips-17-mar-26.md)

### Inferences
- Decision rule synthesized from the above: always-needed fact → instruction file (`AGENTS.md`); must-never-be-skipped rule → hook; needs isolation/parallelism → subagent (a skill can instruct delegation portably; `context: fork` is Claude Code only per `docs/concepts/skills.md`); external system access → MCP server (plus a skill teaching how to use it); deterministic, repeatable transformation → script bundled in the skill's `scripts/`; recurring, situational procedure or niche knowledge → skill.
- Because implicit invocation is probabilistic (Vercel 56% non-invocation; SkillsBench Codex observation in Q2), anything whose omission causes silent wrong output (e.g. new framework APIs) should get at least a one-line pointer in the instruction file that tells the agent when to load the skill.
- Skills add the least on tasks the model already does well (software engineering +4.5 pp) and can hurt (16/84 negative), so a baseline comparison is needed before adopting a skill.

### Gaps
- No vendor-published, cross-harness data comparing "pointer in AGENTS.md + skill" vs "skill alone" vs "content in AGENTS.md"; Vercel's study is one framework, unnamed models, January 2026.
- No Codex-specific guidance found on skills vs `AGENTS.md` vs hooks (Codex docs page covers skills vs plugins only).

## 2. Writing the description and name so the model triggers correctly

### Takeaway
The description is the only thing in the catalog, so it carries the whole trigger decision: state what the skill does *and* when to use it, front-load the key use case and trigger words, use concrete user-intent vocabulary (including phrasings that do not name the domain), state boundaries against neighboring skills, stay well under 1,024 characters, and do not summarize the workflow. Vendors disagree on grammatical voice (third person vs "Use when…"); both work as long as the triggering conditions are explicit. Under-triggering is the documented default failure.

### Cited Findings
- **[V-std]** Spec: `name` 1–64 chars, lowercase `a-z0-9` and single hyphens, no leading/trailing hyphen, must match the directory name; `description` 1–1,024 chars, "should describe both what the skill does and when to use it" and "include specific keywords". Good: "Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction." Poor: "Helps with PDFs." — [Specification](https://agentskills.io/specification)
- **[V]** Anthropic: description "is critical for skill selection: Claude uses it to choose the right Skill from potentially 100+ available Skills". "Always write in third person. The description is injected into the system prompt, and inconsistent point-of-view can cause discovery problems." Avoid "I can help you…" / "You can use this to…". Avoid vague "Helps with documents". Name rules add: no XML tags, reserved words "anthropic"/"claude" not allowed. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic naming: prefer gerund form (`processing-pdfs`, `analyzing-spreadsheets`); noun phrases (`pdf-processing`) or action forms (`process-pdfs`) acceptable; avoid `helper`, `utils`, `tools`, `documents`, `data`, and inconsistent patterns within one collection. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Codex: "front-load the key use case and trigger words"; write "concise descriptions with clear scope and boundaries"; descriptions "may be shortened when many skills exist". Initial catalog limited to "at most 2% of the model's context window, or 8,000 characters". — [Codex build skills](https://learn.chatgpt.com/docs/build-skills)
- **[V]** OpenAI eval blog: "The name and description matter more than they might seem. They're the primary signals Codex uses to decide whether to invoke the skill at all." — [OpenAI eval-skills](https://developers.openai.com/blog/eval-skills)
- **[V]** OpenAI skill-creator: put all "when to use" information in the description, not the body, because "the body loads only after triggering", making body-based usage guidance ineffective for the decision. — [OpenAI skill-creator](https://raw.githubusercontent.com/openai/skills/main/skills/.system/skill-creator/SKILL.md)
- **[V]** Claude Code: "Put the key use case first"; `description` + `when_to_use` truncated together at 1,536 chars in the listing; if `description` is omitted it defaults to the first non-empty body line. Example: "Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff." — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Claude Code troubleshooting. Not triggering: include "natural keywords users would say", check the skill appears in "What skills are available?", invoke with `/skill-name` to separate content problems from trigger problems. Over-triggering: make the description "more specific and narrow", add `disable-model-invocation: true`, or set `skillOverrides` to `"name-only"`. — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V-std]** agentskills.io: "Use imperative phrasing… 'Use this skill when…' rather than 'This skill does…'"; "Focus on user intent, not implementation"; "Err on the side of being pushy", e.g. "even if they don't explicitly mention 'CSV' or 'analysis'"; "a few sentences to a short paragraph"; to fix false triggers "add specificity about what the skill does *not* do, or clarify the boundary between this skill and adjacent capabilities"; "Avoid adding specific keywords from failed queries — that's overfitting." — [Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions.md)
- **[V]** Anthropic skill-creator: Claude tends to "undertrigger" skills, so descriptions should be "a little bit pushy", e.g. "Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics". Metadata target "~100 words". — [Anthropic skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md)
- **[P]** Thariq (Anthropic): "The description field is for the model": write it as "a description of when to trigger this skill", not a user-facing summary. — [mirror of X post](https://gitea.maison43.duckdns.org/gilles/claude-code-best-practice/src/branch/main/tips/claude-thariq-tips-17-mar-26.md)
- **[P]** Jesse Vincent (obra/superpowers `writing-skills`): "Description = When to Use, NOT What the Skill Does"; start with "Use when…", list triggering conditions and symptoms ("flaky", "race conditions"). Observed failure: "When a description summarizes the skill's workflow, an agent may follow the description instead of reading the full skill content" (a description mentioning "code review between tasks" led agents to do one review where the body specified two). — [superpowers writing-skills](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-skills/SKILL.md)
- **[P/E]** Scott Spence (2026-02-08; 22 standard + 24 hard prompts, Sonnet 4.5, sandboxed `claude -p`, ~250 invocations, $5.59): no-hook activation 55% / 50% across two runs; "when Claude activates, it always picks correctly", so the problem is activation frequency, not selection; explicit keywords gave ~100% activation, conceptual phrasings ~0%. A `UserPromptSubmit` "forced-eval" hook (model must state YES/NO per skill before acting) reached 100% on standard prompts and 75% accuracy with 100% true negatives on hard prompts; an LLM-pre-classifier hook had 80% false positives on non-matching prompts. Small sample, single author. — [scottspence.com](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- **[E]** Vercel: adding explicit invocation instructions raised trigger rate to "95%+", but wording mattered: "You MUST invoke the skill" anchored the agent on the docs and missed project context; "Explore project first, then invoke skill" scored better; "small wording tweaks produce large behavioral swings." — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **[E]** SkillsBench: Codex CLI agents frequently "acknowledge Skills content but often implement solutions independently"; Claude Code showed the highest skill utilization (+13.9 to +23.3 pp). — [SkillsBench](https://arxiv.org/html/2602.12670v1)
- **[V]** Catalog overflow behavior (from this repo's vendor notes): Claude Code budget 1% of context window, drops descriptions of least-invoked skills first, names stay; Codex shortens descriptions first, then omits skills with a warning. — [docs/concepts/skills.md](../../concepts/skills.md)

### Inferences
- Portable description recipe that satisfies all leads: one sentence of *what* (third person, concrete verbs and object types), then "Use when …" with user-intent phrases and file types/tool names, then one clause of boundary ("Not for … — use X instead"), ≤ ~500 chars so truncation in either catalog leaves the trigger words intact. Keep it free of step-by-step workflow.
- The voice conflict (Anthropic: third person; agentskills.io/superpowers: imperative "Use when") is reconcilable: Anthropic's own examples are third-person *what* + "Use when…" *when*. The thing all sources agree to avoid is first/second person ("I can…", "You can…").
- "Pushy" descriptions trade under-triggering for over-triggering; that trade must be measured with near-miss negatives (Q5), not judged by eye.
- Because Codex and Claude Code budgets differ and both truncate, a large shared skill library can silently lose triggers in one harness only. Test triggering per harness.
- Hook-based "forced evaluation" is a Claude Code-side mitigation with weak evidence (one practitioner); it also adds latency (~10.7 s average in Spence's runs).

### Gaps
- No vendor-published trigger-rate numbers per description style.
- No data on how `metadata.short-description` (Codex) or `when_to_use` (Claude Code) affect trigger rates.
- No empirical comparison of gerund vs noun names; naming guidance is convention, not measured.

## 3. Body structure: progressive disclosure, length, degrees of freedom, examples, workflows, scripts

### Takeaway
Keep `SKILL.md` to the essentials (< 500 lines, < ~5,000 tokens; much less for frequently used skills), write only what the model would otherwise get wrong (gotchas first), push detail into one-level-deep `references/` files with explicit "read X when Y" pointers, and move deterministic or repeatedly-reinvented logic into tested `scripts/` with agent-friendly interfaces. Match strictness to fragility per section. Measured data favors focused, moderate-length skills over comprehensive documentation.

### Cited Findings
- **[V-std]** Spec progressive disclosure: metadata ~100 tokens; instructions "< 5000 tokens recommended"; resources as needed; "Keep your main `SKILL.md` under 500 lines"; "Keep file references one level deep from `SKILL.md`"; directories `scripts/` (executed), `references/` (read on demand), `assets/` (templates, images, data). — [Specification](https://agentskills.io/specification)
- **[V]** Anthropic: "The context window is a public good"; "Default assumption: Claude is already very smart"; ask "Does this paragraph justify its token cost?"; keep body under 500 lines. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic: nested references cause partial reads ("Claude might use commands like `head -100`"); keep references one level deep; reference files > 100 lines get a table of contents at the top. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic progressive-disclosure patterns: (1) high-level guide linking `FORMS.md`, `REFERENCE.md`, `EXAMPLES.md`; (2) domain-split references (`reference/finance.md`, `sales.md`…) with a grep hint; (3) conditional details ("For tracked changes: see REDLINING.md"). Name files descriptively (`form_validation_rules.md`, not `doc2.md`); forward slashes only. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic degrees of freedom: high (text heuristics) when many approaches are valid; medium (pseudocode/parameterized script) when a preferred pattern exists; low ("Run exactly this script… Do not modify the command") when operations are fragile; "narrow bridge with cliffs" vs "open field" analogy. Same model in OpenAI's skill-creator. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [OpenAI skill-creator](https://raw.githubusercontent.com/openai/skills/main/skills/.system/skill-creator/SKILL.md)
- **[V]** Anthropic patterns: copyable progress checklist for multi-step workflows; validate→fix→repeat feedback loops; plan-validate-execute with an intermediate `changes.json` validated by a script for "batch operations, destructive changes… high-stakes operations"; templates (strict "ALWAYS use this exact template" vs flexible default); input/output example pairs; conditional workflow branches; "provide a default (with escape hatch)" rather than many options; avoid time-sensitive statements (use an "Old patterns" `<details>` section); consistent terminology. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic scripts: "Solve, don't defer" (handle errors in the script); no "voodoo constants"; state whether to *execute* or *read* a script; pre-made scripts are "more reliable than generated code", save tokens, ensure consistency; only script output consumes context; list required packages; verbose validator messages ("Field 'signature_date' not found. Available fields: …"); MCP tools by fully qualified name (`ServerName:tool_name`). — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V-std]** agentskills.io: "Would the agent get this wrong without this instruction? If the answer is no, cut it"; "Concise, stepwise guidance with a working example tends to outperform exhaustive documentation"; tell the agent *when* to load each reference ("Read `references/api-errors.md` if the API returns a non-200 status code"); "Provide defaults, not menus"; "Favor procedures over declarations"; gotchas section is "the highest-value content in many skills" and belongs in `SKILL.md`, not a reference, because the agent "may not recognize the trigger"; when traces show the agent reinventing the same helper each run, bundle it in `scripts/`. — [Best practices](https://agentskills.io/skill-creation/best-practices.md)
- **[V-std]** agentskills.io scripts for agents: no interactive prompts ("a hard requirement"); `--help` as the interface doc; errors that say what was expected; structured output (JSON/CSV) on stdout, diagnostics on stderr; idempotency; `--dry-run`; distinct exit codes; safe defaults (`--confirm`); predictable output size because harnesses truncate around "10-30K characters"; self-contained deps (PEP 723 + `uv run`, Deno `npm:` imports, Bun, `bundler/inline`); pin versions in one-off commands (`npx eslint@9.0.0`); relative paths from the skill root. — [Using scripts](https://agentskills.io/skill-creation/using-scripts.md)
- **[V]** Codex: "Prefer instructions over scripts unless you need deterministic behavior or external tooling." OpenAI skill-creator: include scripts when code is "repeatedly rewritten or deterministic reliability is needed"; information "should live in either SKILL.md or references files, not both"; do not add README.md, CHANGELOG.md, etc.; use imperative/infinitive form. — [Codex build skills](https://learn.chatgpt.com/docs/build-skills); [OpenAI skill-creator](https://raw.githubusercontent.com/openai/skills/main/skills/.system/skill-creator/SKILL.md)
- **[V]** Claude Code: "Every line is a recurring token cost once the skill loads — state what to do rather than narrating how or why"; content stays in context across turns, so write guidance "as standing instructions, not one-time steps". — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[E]** SkillsBench: "Moderate-length Skills outperform comprehensive ones": detailed +18.8 pp vs comprehensive −2.9 pp; 2–3 skills per task +18.6 pp vs 4+ skills +5.9 pp. — [SkillsBench](https://arxiv.org/html/2602.12670v1)
- **[P]** Thariq (Anthropic): "Don't state the obvious"; "highest-signal content in any skill is the Gotchas section"; "Avoid railroading Claude" (goals and constraints over prescriptive steps); store setup in a `config.json` in the skill; persist data (append-only logs, JSON, SQLite) in `${CLAUDE_PLUGIN_DATA}`; ship scripts so Claude "spend[s] its turns on composition"; "Most of ours began as a few lines and a single gotcha". — [mirror of X post](https://gitea.maison43.duckdns.org/gilles/claude-code-best-practice/src/branch/main/tips/claude-thariq-tips-17-mar-26.md)
- **[P]** superpowers: frequently loaded skills "<200 words total", getting-started workflows "<150 words each"; reference `--help` instead of documenting flags; cross-reference other skills by name ("REQUIRED SUB-SKILL: Use superpowers:test-driven-development"), not `@path` links, which "force-load and burn context". — [superpowers writing-skills](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-skills/SKILL.md)
- **Conflict on emphatic rules.** **[V]** Anthropic skill-creator: "If you find yourself writing ALWAYS or NEVER in all caps… that's a yellow flag"; explain the why. **[V-std]** agentskills.io: "Reasoning-based instructions… work better than rigid directives". But **[V]** Anthropic best practices shows iteration that strengthens wording to "MUST filter", and **[P]** superpowers prescribes prohibition + rationalization table + red-flags list for discipline skills that agents skip "under pressure", with "No nuance clauses". **[E]** Vercel saw "You MUST invoke" backfire. — [Anthropic skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md); [agentskills.io evaluating](https://agentskills.io/skill-creation/evaluating-skills.md); [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [superpowers](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-skills/SKILL.md); [Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **[V]** Anthropic: test with every model you plan to use; what works for Opus "might need more detail for Haiku". — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

### Inferences
- Practical size targets: hard ceiling 500 lines / ~5,000 tokens (spec); in Claude Code the first 5,000 tokens are what survives compaction, so put gotchas and non-negotiable rules near the top.
- Anti-pattern list (consolidated): explaining things the model knows; menus of equal options; nested reference chains; generic "see references/" pointers; workflow summary in the description; time-bound statements; backslash paths; scripts that prompt interactively, dump huge output, or fail without guidance; duplicating content between body and references; extraneous README/CHANGELOG inside the skill; "comprehensive" documentation dumps; harness-specific placeholders (`$ARGUMENTS`, `${CLAUDE_SKILL_DIR}`, `` !`cmd` ``) in skills meant to be portable (see `docs/concepts/skills.md`).
- The emphatic-wording conflict is best resolved per failure type: explain the why by default; use explicit prohibitions only where baseline tests show the agent rationalizing past a rule.

### Gaps
- No controlled study of reference-file layout (one level vs nested) beyond Anthropic's qualitative observation.
- No data on Codex-specific reading behavior of `references/` (e.g. whether it partially reads long files).

## 4. User-invoked vs model-invoked skills; skills replacing slash commands; arguments

### Takeaway
Both leads replaced custom commands with skills. Make a skill user-invoked only (model invocation off) when it has side effects or timing matters (deploy, commit, send message); this also removes its description from the catalog, freeing context. Keep it model-invocable when it encodes knowledge the agent should apply unprompted. Portable skills must not rely on argument placeholders; Codex passes the user's text as part of the message.

### Cited Findings
- **[V]** Claude Code: `disable-model-invocation: true` for "workflows with side effects or timing control — like `/deploy`, `/commit`, or `/send-slack-message`. You don't want Claude deciding to deploy because your code looks ready." `user-invocable: false` for background knowledge "that isn't actionable as a command" (e.g. `legacy-system-context`). With `disable-model-invocation`, "Description not in context". — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Claude Code arguments: `$ARGUMENTS`, `$0`, `$1`, named `$name` via `arguments:`; `allowed-tools` pre-approves tools for the invoking turn only ("Grant clears when you send your next message") and "Doesn't restrict tools". `context: fork` runs the skill in a subagent that "doesn't see your conversation history — skill instructions must stand alone"; it makes sense "for skills with explicit instructions and concrete tasks, not guidelines". — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Codex: explicit invocation via `$` mention or `/skills`; implicit when the task matches the description; `agents/openai.yaml` `policy.allow_implicit_invocation: false` "Requires explicit $invocation". — [Codex build skills](https://learn.chatgpt.com/docs/build-skills)
- **[V]** Repo concept notes: Claude Code merged custom commands into skills (v2.1.3); Codex deprecated `~/.codex/prompts/` ("Use skills for reusable instructions"); Codex skills have no argument substitution; in Claude Code `disable-model-invocation` also blocks the skill from scheduled tasks and subagent preloading, while Codex still runs it when a scheduled prompt names `$name`. — [docs/concepts/commands.md](../../concepts/commands.md), [docs/concepts/skills.md](../../concepts/skills.md)
- **[E]** Vercel: skills work best for "vertical, action-specific workflows that users explicitly trigger". — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **[P]** Thariq (Anthropic): skills can carry session-scoped hooks that activate only when the user calls the skill (`/careful`, `/freeze`); skills can reference other skills by name and the model invokes them if installed. — [mirror of X post](https://gitea.maison43.duckdns.org/gilles/claude-code-best-practice/src/branch/main/tips/claude-thariq-tips-17-mar-26.md)
- **[V]** OpenAI eval blog: before evaluating, "explicitly activate the skill" to surface hidden assumptions about naming, environment dependencies and execution order. — [OpenAI eval-skills](https://developers.openai.com/blog/eval-skills)

### Inferences
- Default decision: side-effecting or externally visible actions → user-invoked only (set both `disable-model-invocation: true` and `policy.allow_implicit_invocation: false` in the same skill folder); knowledge/procedures the agent should find on its own → model-invocable with a strong description; pure background knowledge → model-invocable (Claude Code-only `user-invocable: false` does not generalize).
- Argument handling for portability: write the body to read inputs "from the user's request" (e.g. "The user names the issue number in their message; if missing, ask"), and treat `$ARGUMENTS` as a Claude Code-only enhancement.
- User-invoked skills cost no catalog budget, so migrating rarely used command-like skills to user-invoked frees room for model-invocable ones.
- A user-invoked skill still needs a good description for menus/pickers and for the Codex `/skills` list, even though the model never matches on it.

### Gaps
- No vendor guidance on designing argument conventions for Codex skills beyond "text after `$name` is part of the message".
- No data on whether user-invoked skills are followed more faithfully than model-invoked ones.

## 5. Testing and evaluation (trigger evals, behavior evals, iteration, regression, tooling)

### Takeaway
Evaluate two things separately: (a) triggering — a labeled set of ~20 realistic prompts (half should-trigger, half near-miss should-not-trigger), each run ~3 times, scored by trigger rate, with a train/validation split to avoid overfitting the description; (b) behavior — 2–3 starter cases growing to 10–20, run with and without the skill (or against the previous version) in fresh contexts, graded by deterministic checks first and model-graded rubrics second, plus human review of outputs and traces. Write evals before the skill body. Tooling exists in both leads: Anthropic `skill-creator` and `claude plugin eval`; Codex `skill-creator` plus `codex exec --json` traces.

### Cited Findings
- **[V]** Anthropic "evaluation-driven development": run Claude on representative tasks without a skill, document failures, build three scenarios, measure baseline, "Write minimal instructions" to pass, iterate. Eval JSON shape: `skills`, `query`, `files`, `expected_behavior[]`. Checklist: "At least three evaluations created", "Tested with Haiku, Sonnet, and Opus", "Tested with real usage scenarios". The page still says "There is not currently a built-in way to run these evaluations" — outdated given the tools below. — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic "Claude A / Claude B": one instance helps write/refine, a fresh instance with the skill does real tasks; observe "unexpected exploration paths", "missed connections", "overreliance on certain sections", "ignored content" (never-read bundled files may be unnecessary). — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- **[V]** Anthropic Engineering (2025-10, older): "Start with evaluation"; "Think from Claude's perspective"; "Iterate with Claude". — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- **[V]** Claude Code baseline: collect realistic prompts, run each in a fresh session with the skill, then with it off (`skillOverrides: "off"`), compare; "a fresh session is crucial to avoid authoring-context bias". skill-creator plugin stores cases in `evals/evals.json`, runs isolated subagents, grades assertions, compares with/without, runs blind A/B between versions, renders an HTML report. Validate syntax with `claude plugin validate .claude/skills` (v2.1.233+). `/skill-doctor` reports per-skill context cost, invocation frequency, never-invoked skills (v2.1.252+). — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** `claude plugin eval` (v2.1.269+; works on plugins and "skills-directory plugins"): one case dir per prompt with `prompt.md` and `graders/*.md`; grader types `regex`, `tool_used`, `tool_order`, `file_exists`, `llm` (judge votes PASS in ≥2 of 3), `baseline` (vs reference transcript). Trigger check: `tool_used` with `tool: Skill` and `input_match` on the skill name; must-not-trigger check: `min: 0`, `max: 0`, `arm: both`. Each case runs 3 times by default per arm, with-plugin vs no-plugin arm reports `Δ`; `--threshold` default 1.0, exit 1 below threshold for CI; pin `--model` "so a model rollout isn't mistaken for a plugin regression"; runs use a temp home and load nothing personal (no CLAUDE.md, other skills, MCP). "The most common first finding is a `Δ` near zero with the case's `tool_used: Skill` grader failing", meaning the description doesn't trigger on natural phrasing. — [Claude Code plugin evals](https://code.claude.com/docs/en/plugin-evals)
- **[V-std]** Trigger evals (agentskills.io): ~20 queries, 8–10 should-trigger and 8–10 should-not; vary phrasing, explicitness, detail, complexity; most useful positives are ones where "the connection isn't obvious"; most valuable negatives are "near-misses" sharing keywords; include realistic file paths, typos, personal context. Run each ≥3 times; pass if trigger rate > 0.5 (should) or < 0.5 (should not). Split ~60% train / ~40% validation, keep fixed, choose the best iteration by validation pass rate; "Five iterations is usually enough"; confirm with 5–10 fresh queries. Example harness: `claude -p "$query" --output-format json` + `jq` for a `Skill` tool_use. — [Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions.md)
- **[V-std]** Behavior evals (agentskills.io): start with 2–3 cases in `evals/evals.json` (`prompt`, `expected_output`, `files`, later `assertions`); run each with and without the skill (or `old_skill` snapshot) in clean contexts; record `total_tokens`, `duration_ms`; grade assertions with evidence ("Require concrete evidence for a PASS"); prefer scripts for mechanical checks; blind LLM comparison between versions; aggregate pass rate/time/tokens with mean and stddev into `benchmark.json`; drop assertions that always pass in both arms; high stddev → ambiguous instructions; human feedback per case; give failed assertions + human feedback + transcripts to an LLM to propose changes, with "Generalize from feedback" and "Keep the skill lean". — [Evaluating skills](https://agentskills.io/skill-creation/evaluating-skills.md)
- **[V]** Anthropic skill-creator implements both loops: spawn with-skill and baseline subagents "in the same turn"; baseline is "no skill at all" for new skills, "the old version" for edits; description optimization uses 20 queries, 60/40 split, "iterating up to 5 times". — [Anthropic skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md)
- **[V]** OpenAI (Codex) eval method: define success first in four categories — outcome, process (right skill and tools), style, efficiency ("Keep this list small and focused on must-pass checks"); 10–20 prompts in a CSV covering explicit (`$skill`), implicit, contextual, and "at least one `should_trigger=false` case"; capture JSONL traces with `codex exec --json --full-auto "<prompt>"` and check commands/files deterministically; add model-graded rubric via a second `codex exec` with `--output-schema`; grow the CSV from real misses; later add command-count/thrashing, token usage, build and smoke tests; "start small, then layer in deeper checks only where they add real confidence." — [OpenAI eval-skills](https://developers.openai.com/blog/eval-skills)
- **[V]** OpenAI skill-creator: init with `init_skill.py`, validate with `scripts/quick_validate.py`, iterate on real usage. Spec reference validator: `skills-ref validate ./my-skill`. — [OpenAI skill-creator](https://raw.githubusercontent.com/openai/skills/main/skills/.system/skill-creator/SKILL.md); [Specification](https://agentskills.io/specification)
- **[E]** SkillsBench: self-generated skills averaged −1.3 pp vs no skill; "models cannot reliably author the procedural knowledge they benefit from consuming". — [SkillsBench](https://arxiv.org/html/2602.12670v1)
- **[V-std]** agentskills.io: LLM-generated skills without domain context produce "vague, generic procedures"; ground skills in a real hands-on task or project artifacts (runbooks, review comments, incident reports, fix history). "Read agent execution traces, not just final outputs." — [Best practices](https://agentskills.io/skill-creation/best-practices.md)
- **[P]** superpowers: "NO SKILL WITHOUT A FAILING TEST FIRST": RED = run pressure scenarios with subagents without the skill and record rationalizations; GREEN = minimal skill addressing those; REFACTOR = close loopholes, re-test. — [superpowers writing-skills](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-skills/SKILL.md)
- **[P]** Scott Spence: sandboxed (Daytona) `claude -p` runs to measure activation; baseline varied 5 points between identical runs, so single runs mislead. — [scottspence.com](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- **[P]** Thariq (Anthropic): log skill invocations with a `PreToolUse` hook to find popular and under-triggering skills in real use. — [mirror of X post](https://gitea.maison43.duckdns.org/gilles/claude-code-best-practice/src/branch/main/tips/claude-thariq-tips-17-mar-26.md)

### Inferences
- Minimal portable test kit per skill: `evals/trigger_queries.json` (20 labeled prompts incl. near-misses), `evals/evals.json` (2–3 → 10–20 behavior cases with assertions), a runner per harness (`claude -p --output-format json` detecting the `Skill` tool; `codex exec --json` detecting the skill's `SKILL.md` read or `$name` load), ≥3 runs each, a pinned model, and a baseline arm. Note that `claude plugin eval` and skill-creator use different case formats ("neither tool reads the other's case files"), so a team must pick one per harness or write an adapter.
- Regression testing: re-run the suite on every skill change and on every model upgrade (pin model in CI; re-baseline on intentional model change).
- Because self-authored skills don't help on average, the human-provided domain content (gotchas, conventions) is the value; LLMs are useful for structure and iteration, not as the knowledge source.

### Gaps
- How to detect implicit skill loads in Codex traces (which JSONL event marks a skill load) is not documented in the sources read.
- AEVAL (arXiv 2607.16345) and Phil Schmid's "testing skills" guide appeared in search but were not read; their claims are not included.
- No published guidance on statistical sample sizes beyond "3 runs" and "0.5 threshold" defaults.

## 6. Organization and distribution (scopes, cross-harness sharing, versioning, catalog budget)

### Takeaway
Start with project-scope skills committed in the repo, promote shared ones to a plugin/marketplace, and keep personal ones in user scope (not visible to cloud runs). For Claude Code + Codex, keep one canonical copy (e.g. `.agents/skills/<name>/`) and symlink it into `.claude/skills/`. Keep the library small and curated: catalog budgets are 1–2% of context, both leads truncate, and benchmark data shows diminishing returns past 2–3 relevant skills. Versioning practice is thin; use git, plugin versions, and pinning.

### Cited Findings
- **[V]** Claude Code: commit `.claude/skills/` for the team; plugins (`skills/` dir) via marketplace; organization-wide via managed settings; claude.ai-synced skills restricted to spec fields (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`). — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Codex: `.agents/skills` for repo-scoped workflows; plugins to bundle skills or a skill plus connector; `$skill-installer` for curated installs. — [Codex build skills](https://learn.chatgpt.com/docs/build-skills)
- **[V]** openai/skills repo (`.system`, `.curated`, `.experimental` tiers) is now marked deprecated; OpenAI points to its Plugins repo and "Build Plugins" guide. Codex needs a restart after installing. — [openai/skills](https://github.com/openai/skills)
- **[V]** Repo concept notes: leads share no skill directory; canonical copy + symlink works because Claude Code allows symlinked skill folders and Codex follows them in repo/user/admin scopes; OpenCode reads both dirs and may see duplicates (`OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1`); Claude Code cloud sessions ignore `~/.claude/skills`; `$skill-installer` writes to the deprecated `$CODEX_HOME/skills`; portable frontmatter is `name` + `description` (+ `license`, `compatibility`, `metadata`); Claude-only keys cause hard errors on claude.ai/Skills API upload. — [docs/concepts/skills.md](../../concepts/skills.md)
- **[V-std]** Spec: `metadata` is a string→string map, example `version: "1.0"`, `author`; use reasonably unique keys; `compatibility` (≤500 chars) only when the skill has real environment requirements. — [Specification](https://agentskills.io/specification)
- **[V]** Codex catalog: ≤2% of context window or 8,000 chars; descriptions shortened when many skills are installed. — [Codex build skills](https://learn.chatgpt.com/docs/build-skills)
- **[V]** Claude Code: `/skill-doctor` shows context cost and never-invoked skills to prune; `skillOverrides` can set skills `off` or `name-only`. — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[E]** SkillsBench: 2–3 skills per task +18.6 pp vs 4+ skills +5.9 pp. — [SkillsBench](https://arxiv.org/html/2602.12670v1)
- **[V-std]** agentskills.io: design skills as "coherent units": too narrow forces several skills to load with "conflicting instructions"; too broad becomes "hard to activate precisely". — [Best practices](https://agentskills.io/skill-creation/best-practices.md)
- **[P]** Thariq (Anthropic): small teams check skills into `.claude/skills`; at scale use an internal plugin marketplace; new skills start in a sandbox folder, get promoted via PR after traction; "Curation prevents skill redundancy". Anthropic has "hundreds of them in active use". — [mirror of X post](https://gitea.maison43.duckdns.org/gilles/claude-code-best-practice/src/branch/main/tips/claude-thariq-tips-17-mar-26.md)
- **[P]** Third-party: Vercel's `npx skills` CLI installs skills into agent-specific folders for 50+ agents (e.g. `.claude/skills/`, `.codex/skills/`, `.cursor/skills/`) and is described as the de facto package manager. Note: writing to `.codex/skills/` contradicts Codex's documented `.agents/skills` project root. — [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/05/31/codex-cli-vercel-skills-cli-npx-skills-open-agent-skills-ecosystem/)
- **[V]** Anthropic: gather team feedback ("Does the Skill activate when expected?"). — [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

### Inferences
- Scope choice: project scope for anything tied to a repo or needed by CI/cloud runs; user scope for personal workflow; plugin for anything shared across repos or teams (gives versioned, reviewable releases and namespacing); managed/admin for policy-like skills.
- Budget hygiene: count catalog characters across all installed skills per harness; with Codex's 8,000-char floor, ~16 skills at 500 chars already fill it. Turn rarely needed skills into user-invoked ones (no catalog entry) and prune never-invoked skills.
- Versioning: no vendor defines skill-level semantic versioning; practical options are git tags/plugin versions, `metadata.version` as an informational field, and hash pinning for third-party skills (Q7).

### Gaps
- No vendor guidance on skill versioning, deprecation, or changelog practice (OpenAI skill-creator explicitly says not to put CHANGELOG.md in a skill).
- No data on how many installed skills degrade trigger accuracy in either lead (SkillsBench measures skills per task, not catalog size).
- Whether OpenCode deduplicates symlinked duplicates is unrecorded.

## 7. Security: skills with scripts as supply-chain risk; reviewing third-party skills

### Takeaway
Treat a third-party skill like an unreviewed dependency that runs with your privileges: its natural-language instructions are a prompt-injection surface and its scripts are code. Measured marketplace studies find a substantial share of vulnerable skills and a smaller but real set of confirmed malicious ones (estimates vary widely by method). Install only from trusted sources, read every file, pin versions/hashes, restrict pre-approved tools, and run evals of untrusted skills in isolation.

### Cited Findings
- **[V]** Anthropic: install "only from trusted sources" and audit bundled code, dependencies, and external network connections before deployment. — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- **[V]** Anthropic skill-creator: "A skill's contents should not surprise the user in their intent if described." — [Anthropic skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md)
- **[V]** Claude Code: project skills can grant broad tool access via `allowed-tools`; "Workspace trust doesn't gate `allowed-tools` — a project skill applies even in `-p` runs in untrusted folders"; review `allowed-tools` in unfamiliar repos; admins can set `allowManagedPermissionRulesOnly` to ignore skill `allowed-tools`; `disableSkillShellExecution` turns off `` !`cmd` ``; claude.ai-synced skills never run injected commands (v2.1.228+). — [Claude Code skills](https://code.claude.com/docs/en/skills)
- **[V]** Claude Code plugin evals: evaluating a plugin "is the same trust decision as `claude --plugin-dir`"; with hooks or real MCP servers you didn't write, "treat its scores as advisory unless you ran it in an isolated environment such as a container or CI runner". — [Claude Code plugin evals](https://code.claude.com/docs/en/plugin-evals)
- **[V]** Codex gates skill scripts via `approval_policy.granular.skill_approval` (repo concept notes). — [docs/concepts/skills.md](../../concepts/skills.md)
- **[E]** "Agent Skills in the Wild" (arXiv 2601.10338, 2026-01-15): 31,132 skills from two marketplaces; 26.1% had ≥1 vulnerability across 14 patterns (prompt injection, data exfiltration 13.3%, privilege escalation 11.8%, supply chain); 5.2% high-severity patterns suggesting malicious intent; SkillScan detector 86.7% precision / 82.5% recall. — [arXiv 2601.10338](https://arxiv.org/abs/2601.10338)
- **[E]** "Do Not Mention This to the User" (Liu et al., arXiv 2602.06547, rev. 2026-06-10): 98,380 skills; 157 confirmed malicious with 632 vulnerabilities across 13 techniques; dominant patterns are credential theft via code execution and covert adversarial instructions in documentation files; average 4.03 vulnerabilities per malicious skill; all 157 removed after reporting. — [arXiv 2602.06547](https://arxiv.org/abs/2602.06547)
- **[E]** Snyk ToxicSkills (scan of 3,984 skills from ClawHub and skills.sh, 2026-02-05): 13.4% (534) with ≥1 critical issue; 36.82% with any flaw; critical issues: command injection 45%, privilege escalation 32%, data exfiltration 23%; 2.9% of ClawHub skills fetch and execute remote content at runtime (`curl … | source`); instruction-level attacks hidden mid-`SKILL.md`, base64 payloads piped to bash. — [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)
- **[E] Conflicting estimate.** Holzbauer et al. (arXiv 2603.16572, rev. 2026-06-01; 238,180 skills): marketplace scanners flagged up to 46.8% as potentially malicious, but with repository context only 0.52% remained suspicious, so "isolated scanning significantly overestimates risk"; documents hijacking of skills hosted in abandoned GitHub repositories. — [arXiv 2603.16572](https://arxiv.org/abs/2603.16572)
- **[V-std]** OWASP Agentic Skills Top 10 (incubator, v0.0.0, March 2026), AST01 Malicious Skills, rated Critical; cites ClawHavoc (January 2026, 1,184 malicious skills). User checklist: verify publisher trust, install count and scan status; "Reject auto-execution of Prerequisites sections without explicit review"; "Hash-pin installed skills and monitor for unauthorized modifications"; review permission requirements; install only from verified sources. Registry checklist: ed25519 signatures, behavioral scanning, sandboxed execution, audit logging. — [OWASP AST01](https://owasp.github.io/www-project-agentic-skills-top-10/ast01)
- **[P]** Simon Willison: "We really need to figure out how best to sandbox these environments such that attacks such as prompt injections are limited to an acceptable amount of damage." — [simonwillison.net](https://simonwillison.net/2025/Oct/16/claude-skills/)

### Inferences
- Review checklist for a third-party skill (synthesized): read every file, not just `SKILL.md` (the harness only lists name/description); search prose for hidden directives ("do not mention", "ignore previous", instructions to fetch/run remote content, base64); inspect `scripts/` for network calls, credential/file access, `curl | sh`, package installs; check Claude Code `allowed-tools`, `hooks`, `` !`cmd` `` and Codex `agents/openai.yaml` `dependencies.tools` (MCP); check the source repo is maintained (abandoned-repo hijacking); pin by commit/hash; re-review on update; run first in a sandbox/container.
- For own skills: least privilege in `allowed-tools`; scripts with `--dry-run` and explicit `--confirm` for destructive actions; user-invoked only for side-effecting skills (Q4).
- The prevalence numbers are not comparable (different corpora, definitions of "vulnerable" vs "malicious", scanner vs context-aware analysis); reasonable summary: confirmed malicious skills are a small fraction of large registries, but low-quality/vulnerable skills are common, and open marketplaces carry more risk than curated ones.

### Gaps
- No vendor-provided signing or provenance mechanism for skills was found in Claude Code or Codex docs.
- OWASP Top 10 items AST02–AST10 were not read.
- Cloud Security Alliance note on skill-scanner bypass (June 2026) appeared in search but was not read.
