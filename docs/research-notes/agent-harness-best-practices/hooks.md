# Hooks: best practices for designing, implementing, testing and securing lifecycle hooks

Scope: Claude Code and Codex as equal leads, OpenCode plugin hooks as nice-to-have. Terminology follows [docs/concepts/hooks.md](../../concepts/hooks.md): registration `event → matcher group → handler`, the eleven shared events, the shared decision contract, and the Codex fail-open traps.

Evidence labels used on every finding:
- **[Vendor]**: vendor documentation or vendor-published guidance.
- **[Empirical]**: study or measured data.
- **[Advisory]**: CVE, GHSA, or a security research disclosure.
- **[Practitioner]**: opinion or experience report from a practitioner or an issue tracker.

Sources were retrieved on 2026-10-04. `developers.openai.com/codex/hooks` now redirects (308) to `learn.chatgpt.com/docs/hooks`, and `anthropic.com/engineering/claude-code-best-practices` redirects (308) to `code.claude.com/docs/en/best-practices`. Both are cited by their current URLs.

## 1. Use cases: when a hook is the right tool, as opposed to an instruction

### Takeaway
Use a hook for any rule that must hold every time, regardless of what the model decides. Typical cases are formatting or linting after edits, blocking known-bad commands, protecting paths, re-injecting context after compaction, a "tests must pass" gate on `Stop`, notifications and audit logs. Rules that need judgement belong in instructions, or in prompt/agent hooks (Claude Code only). Both vendors and Trail of Bits describe hooks as guardrails, not security walls.

### Cited Findings
- **[Vendor]** "Use hooks for actions that must happen every time with zero exceptions." "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." The anti-pattern fix for an over-long CLAUDE.md is: "If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[Vendor]** The Claude Code guide gives these canonical use cases: notifications (a `Notification` event with an empty matcher), auto-format with `PostToolUse` + `Edit|Write` + Prettier, blocking edits to protected files (`.env`, `package-lock.json`, `.git/`) with a `PreToolUse` script that exits 2, re-injecting context after compaction with `SessionStart` + matcher `compact` (plain stdout becomes context), a `ConfigChange` audit log, a direnv-style env reload with `SessionStart` + `CwdChanged` writing to `CLAUDE_ENV_FILE`, and auto-approving `ExitPlanMode` with a `PermissionRequest` hook. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** Codex lists these intended uses: "Send the chat to a custom logging/analytics engine", "Scan your team's prompts to block accidentally pasting API keys", "Summarize chats to create persistent memories automatically", "Run a custom validation check when a chat turn stops, enforcing standards", "Customize prompting when in a certain directory". — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Claude Code offers three ways to verify work: a prompt, a `/goal` condition, or "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes." "The /goal and Stop hook versions are what let an unattended run finish correctly without you." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[Vendor]** For "decisions that require judgment rather than deterministic rules", Claude Code provides `type: "prompt"` hooks (a single-turn model returns `{"ok": bool, "reason"}`) and `type: "agent"` hooks (multi-turn with tools; "experimental and may change"). The documented example is an agent `Stop` hook that verifies unit tests pass. Codex parses `prompt` and `agent` handlers but skips them (see concept doc). — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** Anthropic's `security-guidance` plugin is a production reference built entirely on hooks. It uses `SessionStart` to bootstrap a Python env, `UserPromptSubmit` to capture a working-tree baseline, `PostToolUse` on `Edit`/`Write`/`NotebookEdit` for a per-edit pattern match, `Stop` for an end-of-turn diff review run in the background, and `PostToolUse` on `Bash` filtered to `git commit`/`git push` for a background commit/push review. Anthropic states that its review rules "are guidance for the reviewer, not deterministic guardrails... For hard enforcement, pair the plugin with a hook that blocks the edit or a CI check." — [Claude Code security-guidance](https://code.claude.com/docs/en/security-guidance)
- **[Practitioner]** Trail of Bits' framing: hooks "are a way to talk to the LLM at decision points it wouldn't otherwise pause at." `PreToolUse` means "stop, think about this", `PostToolUse` means "here's what you should know", `Stop` means "you're not done yet". "An instruction in your CLAUDE.md saying 'never use rm -rf' can be forgotten or overridden by context pressure. A PreToolUse hook that blocks rm -rf fires every single time." — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Practitioner]** Trail of Bits recommends only two hooks as defaults: `PreToolUse` on `Bash` blocking `rm -rf` (suggesting `trash`) and blocking a direct push to main/master. Everything else ("Audit logging", "Bash command log", "Enforce package manager", "Anti-rationalization gate") is "patterns to adapt, not drop-in configs". Their placement rule: "anything that must hold unconditionally belongs in CLAUDE.md, and anything that must hold regardless of what Claude decides belongs in a hook." — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Practitioner]** Trail of Bits' anti-rationalization `Stop` prompt hook rejects final answers that claim issues are "pre-existing" or "out of scope", defer to unrequested follow-ups, or skip test/lint failures, and returns `{"ok": false, "reason": "You are rationalizing incomplete work... Go back and finish."}`. — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Vendor]** A commit/PR check can be built from a `PostToolUse` hook on `Bash` with an `if` filter such as `Bash(git *)`, which as a permission-rule pattern matches subcommands (`npm test && git push` matches) and commands inside `$()` and backticks. The `if` field is Claude Code only. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** To reformat a file however it changes, including when a `Bash` command rewrites it, Claude Code suggests a `FileChanged` hook instead of `PostToolUse` on `Edit|Write`. This event is Claude Code only and is dropped from the generalization. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Empirical]** A study of 2,926 GitHub repositories (Claude Code, Copilot, Cursor, Gemini, Codex) found eight configuration mechanisms, hooks among them. Context files dominate, and the advanced mechanisms are adopted only shallowly. Hooks "are usually defined in Settings files" and correlate with Settings (ρ=0.52). The paper gives no absolute counts of hook adoption and no breakdown by hook purpose. — [Galster et al., "Configuring Agentic AI Coding Tools: An Exploratory Study", arXiv:2602.14690, Feb 2026](https://arxiv.org/abs/2602.14690)

### Inferences
- A rough decision rule from the sources above. A rule that must hold deterministically, can be checked by a script, and is tied to a lifecycle point is a hook. A rule that needs judgement is an instruction or a skill, or a prompt hook in Claude Code only. A hard security limit is a permission rule, the sandbox, or CI (see question 6).
- Portable (both-lead) versions of the canonical use cases, using only shared events:
  - Format/lint: `PostToolUse` + `Edit|Write`.
  - Dangerous commands: `PreToolUse` + `Bash`, exit 2.
  - Protected files: `PreToolUse` + `Edit|Write`, exit 2.
  - Context injection: `SessionStart` (matcher `startup|resume|clear|compact`) or `UserPromptSubmit` with plain stdout.
  - Quality gate: `Stop` with a `stop_hook_active` guard.
  - Notifications: `Stop`, because `Notification` is Claude Code only.
  - Audit: `PostToolUse` (async) and `SessionEnd`.
  - Commit checks: `PreToolUse`/`PostToolUse` on `Bash`, filtered inside the script because `if` is Claude Code only.
- Use a deterministic hook to make "done" mean "checks passed". The vendor (best practices), a credible practitioner (Trail of Bits) and Anthropic's own plugin all converge on this, so it is the strongest-evidenced use case.

### Gaps
- No empirical data was found on which hook use cases are most common, or on how much they improve outcomes. The one empirical study found does not quantify hooks.
- No Codex-published best-practices page specific to hooks was found beyond the hooks reference itself.

## 2. Designing decisions: block vs ask vs feedback, exit codes vs JSON, actionable reasons, Stop loops

### Takeaway
Pick one signalling style per hook. Use exit 2 with a reason on stderr for simple gates, or exit 0 with JSON for structured control. Never rely on exit 1 to block. Write every block reason as an instruction the model can act on ("use X instead"). In Codex, never answer `ask` from `PreToolUse`, because it fails open. Guard every `Stop`/`SubagentStop` gate with `stop_hook_active`. Claude Code caps consecutive Stop blocks at 8; no equivalent cap is documented for Codex.

### Cited Findings
- **[Vendor]** "Choose one approach per hook: either use exit codes alone for signaling, or exit 0 and print JSON for structured control. If you mix them, exit 2 keeps its blocking effect, and Claude Code still reads the JSON fields." "Exit codes only let you block or stay silent. For more control, exit 0 and print a JSON object." — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks); [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** "For most hook events, exit code 2 is the only exit code that blocks through the code alone. Without valid JSON on stdout, Claude Code treats exit code 1 as a non-blocking error and proceeds with the action... If your hook is meant to enforce a policy, use `exit 2`." — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#exit-code-output)
- **[Vendor]** When stdout parses as a valid object, "Claude Code ignores the exit code and the JSON alone decides the outcome" (standard decision model). A hook that exits 2 while printing JSON that fails schema validation still blocks (since v2.1.214). Stderr from an exit-0 hook goes to the debug log only, "and Claude never sees it". To surface a warning from `PostToolUse`, exit 2. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** Claude Code `PreToolUse` supports `allow | deny | ask | defer`, with precedence across multiple hooks of `deny > defer > ask > allow`. The `permissionDecisionReason` for `deny` is shown to Claude, for `ask` it is shown to the user, and for `allow`/`defer` it goes only to the debug log. `defer` is honored only with `-p`. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** Codex `PreToolUse` accepts `permissionDecision: "deny"` with a reason, the legacy `{"decision":"block","reason"}`, exit 2 with stderr, `additionalContext`, and `allow` + `updatedInput` (rewrite only). "`permissionDecision: "ask"`, legacy `decision: "approve"`, `continue: false`, `stopReason`, and `suppressOutput` are parsed but not supported yet. Codex marks the hook run as failed, reports the error, and continues the tool call." Plain stdout is ignored for `PreToolUse`. — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Codex `PermissionRequest`: "any `deny` wins. Otherwise, an `allow` lets the request proceed without surfacing the approval prompt. If no matching hook decides, Codex uses the normal approval flow." `updatedInput`, `updatedPermissions` and `interrupt` "fail closed today". — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** For an auto-approving `PermissionRequest` hook: "Keep the matcher as narrow as possible. Matching on `.*` or leaving the matcher empty would auto-approve every tool permission prompt, including file writes and shell commands." — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** Block reasons are model-facing. In the protected-files example, "Claude receives feedback explaining why the edit was blocked, so it can adjust its approach". The documented deny example says "Use rg instead of grep for better performance". — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Practitioner]** Trail of Bits' blocking hooks "exit 2 with an error message that tells Claude what to do instead" (e.g. suggesting `trash` instead of `rm -rf`, and feature branches instead of pushing to main). — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Vendor]** Codex `Stop`: `decision: "block"` "doesn't reject the turn. Instead, it tells Codex to continue and automatically creates a new continuation prompt that acts as a new user prompt, using your `reason` as that prompt text." "If any matching `Stop` hook returns `continue: false`, that takes precedence over continuation decisions from other matching `Stop` hooks." `Stop` requires JSON on exit 0 ("Plain text output is invalid for this event"). The input includes `stop_hook_active` ("Whether this turn was already continued by `Stop`"). — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Claude Code: "Claude Code overrides a Stop hook after it blocks eight times in a row without progress. Your hook script needs to check whether it already triggered a continuation. Parse the `stop_hook_active` field... and exit early if it's `true`." The cap can be raised with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. `Stop` hooks "fire whenever Claude finishes responding, not only at task completion. They don't fire on user interrupts." — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** A Claude Code prompt hook on `Stop` can return `"impossible": true` to mark a condition that can never be satisfied, so the stop is allowed. This is a built-in escape hatch against endless loops. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** Claude Code: when several `PreToolUse` hooks return `updatedInput`, "the last one to finish takes effect. Since hooks run in parallel, the order is non-deterministic. Avoid having more than one hook modify the same tool's input." `updatedInput` "Replaces the entire input object, so include unchanged fields". — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide); [reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** `PostToolUse` cannot undo side effects in either lead. Claude Code shows the stderr or reason to Claude. Codex "replaces the tool result with that feedback and continues the model from the hook-provided message". — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide); [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Practitioner]** Prompt-hook output must be forced to raw JSON: "Without this, Haiku wraps the JSON in markdown code fences or adds explanatory text, which fails JSON parsing and silently breaks the hook." — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Vendor]** Pitfalls that silently void a JSON decision: extra stdout before the JSON (for example an unconditional `echo` in a shell profile sourced through `BASH_ENV` or Git Bash) means stdout "no longer starts with `{`" and is treated as plain text. A field at the wrong level (for example `permissionDecision` outside `hookSpecificOutput`) is "silently ignore[d]". The debug log reports "Hook JSON output had unrecognized keys". The fix for profiles is `if [[ $- == *i* ]]; then echo ...; fi`. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)

### Inferences
- Portable decision table:
  - Hard block on `PreToolUse`: exit 2 with a stderr reason, or `permissionDecision: "deny"` + reason. Both leads honor both forms.
  - "Ask the human": do not use from a portable `PreToolUse` hook (it fails open in Codex). Instead, let the harness's own permission rules prompt, or deny with a reason telling the model to ask the user.
  - Feedback after the fact: `PostToolUse` exit 2 or `decision: "block"`. The model sees the reason in both leads, but Codex replaces the tool output while Claude Code appends.
  - Continue working: `Stop` with `decision: "block"` + reason. Always emit JSON on exit 0, because Codex rejects plain text on `Stop`.
- Writing reasons the model can act on: state the rule, the violated value, and the allowed alternative, in one or two sentences. For example: "Blocked: `.env` is protected. Read `.env.example` instead or ask the user to set the value." This follows from both vendors feeding the reason back as the next model input.
- Stop-loop design: (1) exit 0 immediately when `stop_hook_active` is true, or allow at most N continuations by counting in a state file keyed by `session_id` + `turn_id`. (2) Make the gate idempotent and cheap: run the fast test subset and cache by tree hash. (3) Give the model an exit, such as a reason that says "if tests cannot pass because of X, say so explicitly". Point (3) is the command-hook analogue of Claude Code's `impossible` flag. Codex documents no block cap, so the guard is mandatory there.

### Gaps
- Codex behavior for exit codes other than 0 and 2 on blocking events is not documented. The docs say only that `SessionEnd` "times out or exits with an error" is reported as a hook failure. Treat as fail-open until verified.
- Codex documents no cap on consecutive `Stop` continuations equivalent to Claude Code's 8.
- No empirical comparison was found of how well models follow different block-reason phrasings.

## 3. Performance: latency budgets, timeouts, async/background hooks, narrow matchers

### Takeaway
Synchronous hooks sit on the agent's critical path, and the 600 s defaults are far too generous for gates. Set explicit short timeouts, keep `PreToolUse`/`UserPromptSubmit` handlers fast, scope matchers (and the `if` field in Claude Code) narrowly, and push slow work (test suites, reviews, uploads) into async hooks. Async hooks cannot block in either lead and are cancelled at session end. A timed-out hook is not a gate in either lead.

### Cited Findings
- **[Vendor]** Claude Code defaults: 600 s for `command`/`http`/`mcp_tool`, lowered to 30 s on `UserPromptSubmit`, `PreModelSwitch` and `PostModelSwitch` and 10 s on `MessageDisplay`; `prompt` 30 s; `agent` 60 s. `SessionEnd` hooks of any type share a 1.5 s budget, which longer per-hook timeouts raise up to 60 s. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** "A timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call. The call continues through the normal permission flow, so don't count on a stalled hook to act as a gate." In contrast, an Agent SDK callback hook on `PreToolUse` that exceeds its timeout does block. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** Codex: 600 s default. `SessionEnd`/`Interrupt` default to 1 s with a 3 s maximum. For MCP hooks "The shorter hook or server timeout applies". MCP hook "Errors, missing servers, and unavailable tools don't block the operation." For managed MCP hooks: "a `PreToolUse` callback error, timeout, or malformed response can fail the hook without blocking the tool." — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Claude Code async: `"async": true` (command only) "runs it in the background", and such hooks "can't block or control Claude's behavior". `timeout` is not enforced once running (it is for `asyncRewake`). Output arrives "on the next conversation turn". With `-p`, running async hooks are killed at teardown ("If your hook's work must outlive a `claude -p` session, start a fully detached process from it"). "There is no deduplication across multiple firings of the same async hook." `asyncRewake: true` wakes Claude on exit 2 even when idle. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background)
- **[Vendor]** Codex background hooks "can't block, approve, rewrite, or otherwise control the operation... Use synchronous hooks for tool policies, permission decisions, prompt rejection, or turn continuation." There is a maximum of eight concurrent per session ("Additional hooks wait"). They "can finish in a different order than they started". Unfinished ones are cancelled at session end with output discarded. `SessionEnd` always runs synchronously. — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** The `if` field (Claude Code) filters "by tool name and arguments together, so the hook process only spawns when the tool call matches", "avoiding the process spawn overhead". "Without a matcher, a hook fires on every occurrence of its event." — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide); [reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** Both leads run all matching handlers concurrently. Codex: "one hook can't prevent another matching hook from starting". — [Codex hooks](https://learn.chatgpt.com/docs/hooks); [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** Context is a performance cost too. Codex: "Keep hook and plugin context concise. Context from multiple hooks and plugins adds up and can degrade model performance." Its default is about 2,500 tokens per message before spilling to disk, and it warns against `additionalContextLimit: 0` unless the hook caps its own output. — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Claude Code caps `additionalContext` at 10,000 characters per string and saves the overflow to a file. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks), as recorded in the [concept doc](../../concepts/hooks.md)
- **[Vendor]** Anthropic's own `security-guidance` plugin runs its expensive reviews (the `Stop` diff review and the commit/push review) in the background and keeps only the per-edit pattern match synchronous. — [Claude Code security-guidance](https://code.claude.com/docs/en/security-guidance)

### Inferences
- Practical budgets (inference, not vendor numbers): `PreToolUse`/`PermissionRequest` gates should be fast because they run before every matching tool call. Set an explicit short `timeout` so a hang degrades quickly. Note that this degrades to fail-open, so the gate logic must not depend on slow network calls. `PostToolUse` formatters should touch only the edited file, never the whole repo. `Stop` gates may take longer but should run a fast subset. Full suites belong in CI.
- Prefer filtering in the matcher over filtering inside the script, because each matching tool call spawns the hook process, and the `if` field exists to avoid that spawn overhead. In portable configs the `if` field is unavailable, so use a narrow matcher plus an early `exit 0` in the script.
- Async hooks suit observation (audit, telemetry, slow tests that report back). They must never be used for enforcement in either lead.

### Gaps
- No published latency measurements of hook overhead were found for either lead.
- Whether Codex enforces `timeout` on a background hook while it runs is not stated beyond "same... timeout".

## 4. Security: privileges, untrusted repos, trust models, input validation, shell injection, secrets

### Takeaway
Hooks are arbitrary code that runs with the user's full privileges outside the sandbox. A repo-supplied hook is therefore a code-execution vector, and real advisories exist for project-config auto-execution in both leads. The trust models differ. Claude Code gates by workspace trust, but `-p`/SDK runs treat the folder as trusted. Codex trusts each hook by hash and skips new or changed hooks until reviewed, including in `exec`. Write hook scripts defensively: quote variables, prefer exec form, parse JSON with a real parser, block `..` traversal, use absolute paths, and keep secrets out of hook output.

### Cited Findings
- **[Vendor]** "Command hooks execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access. Review and test all hook commands before adding them to your configuration." — [Claude Code hooks reference, Security considerations](https://code.claude.com/docs/en/hooks#security-considerations)
- **[Vendor]** Claude Code security best practices, verbatim: "Validate and sanitize inputs: never trust input data blindly"; "Always quote shell variables: use `"$VAR"` not `$VAR`"; "Block path traversal: check for `..` in file paths"; "Use absolute paths: specify full paths for scripts. In exec form, use `${CLAUDE_PROJECT_DIR}` and the path needs no quoting. In shell form, wrap it in double quotes"; "Skip sensitive files: avoid `.env`, `.git/`, keys, etc." — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#security-considerations)
- **[Vendor]** Exec form (`args` present) spawns the executable directly: "There is no shell, so each args element is one argument exactly as written... Special characters such as apostrophes, `$`, and backticks pass through verbatim." "Prefer exec form for any hook that references a path placeholder." Plugin `${user_config.*}` values are substituted only in exec form, and a shell-form plugin hook that references them fails (since v2.1.207, closing a re-parse path). — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#exec-form-and-shell-form)
- **[Vendor]** Workspace trust: in interactive sessions Claude Code "holds back hooks from every settings file, including your own `~/.claude/settings.json`, until you accept the workspace trust dialog". "`-p` or SDK session: Claude Code never shows the dialog and treats the folder as trusted, so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted. Before you script `claude -p` over a repository you didn't write, review its `.claude/` settings files, start with `--bare`, or turn hooks off for that run with `--settings '{"disableAllHooks": true}'`." — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#workspace-trust)
- **[Vendor]** Hooks in settings files and a project skill's hooks are "Used" both when only a parent folder was trusted and in `-p`/SDK runs in a never-trusted folder. A tracked-in-git `.claude/settings.local.json`, or a symlinked `.claude`, is treated as repository-supplied. — [Claude Code permissions: What runs before you trust a folder](https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder)
- **[Vendor]** Codex: "Before a non-managed hook can run, Codex requires you to review and trust the exact hook definition. Codex records trust against the hook's current hash, so new or changed hooks are marked for review and skipped until trusted." Project-local hooks additionally load "only when the project `.codex/` layer is trusted". Plugin-bundled hooks are not auto-trusted. `--dangerously-bypass-hook-trust` is meant "For one-off automation that already vets hook sources outside Codex". — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Codex: "Because oversized output can be written to disk, avoid returning secrets or other sensitive data in hook output." Spilled output goes to `<temp_dir>/hook_outputs/<session_id>/<uuid>.txt`. — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Advisory]** (older, 2025) Claude Code GHSA-ph6w-f82w-28w6: hooks defined in a repository's `.claude/settings.json` executed at startup without explicit confirmation. "any contributor with commit access can define hooks that will execute shell commands on every collaborator's machine". Reported 2025-07-21, fixed 2025-08-26. Anthropic added an enhanced warning dialog for untrusted project configurations. The same Check Point research covers CVE-2025-59536 (repository settings bypassing the MCP consent so `.mcp.json` commands ran at launch) and CVE-2026-21852 (API key exfiltration via project config). Researcher advice: "Inspect configuration directories before opening projects – examine .claude/, .vscode/" and "Review configuration changes during code reviews with the same rigor applied to source code." — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- **[Advisory]** (older, 2025) Codex CLI CVE-2025-61260: a repo `.env` setting `CODEX_HOME=./.codex` plus `.codex/config.toml` MCP entries made Codex "invoke the declared command/args immediately at startup". The bug was in the MCP config path, not hooks, but it shows the same project-config auto-execution class. "project-supplied files become trusted execution material." Fixed in 0.23.0 (2025-08-20). — [Check Point Research](https://research.checkpoint.com/2025/openai-codex-cli-command-injection-vulnerability/)
- **[Advisory]** CVE-2026-19590 (published 2026-09-01): Codex Desktop "could execute attacker-controlled Git hooks because automated Git operations trusted the repository's local core.hooksPath setting... The hook executes outside Codex's command sandbox, without user approval". These are Git hooks, not agent hooks. They are relevant because harness-driven `git commit` from hooks or agents triggers repository Git hooks. — [NVD CVE-2026-19590](https://nvd.nist.gov/vuln/detail/CVE-2026-19590)
- **[Vendor]** Claude Code's `if` filter is best-effort, as recorded in the [concept doc](../../concepts/hooks.md) from the vendor notes. — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- **[Vendor]** Codex calls hooks "a useful guardrail, not a complete enforcement boundary": "Some specialized tool paths can opt out of the default hook path", and hosted tools like `WebSearch` are never hooked. — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Practitioner]** "Hooks are not a security boundary -- a prompt injection can work around them. They are structured prompt injection at opportune times... Guardrails, not walls." — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Practitioner]** Issue #29709 (2026-03-01, closed as not planned): after a `PreToolUse:Edit` hook blocked edits to review scripts three times, the agent wrote the file with Python through the `Bash` tool. "Any PreToolUse:Edit|Write hook can be trivially bypassed this way." — [anthropics/claude-code#29709](https://github.com/anthropics/claude-code/issues/29709)
- **[Vendor]** OpenCode's own `.env` protection example blocks only `input.tool === "read"` where `filePath.includes(".env")`, by throwing. It does not cover shell reads, which is the same Bash-bypass shape as above. Its docs also show a `tool.execute.before` example that escapes the bash command with `shescape`. — [OpenCode plugins](https://opencode.ai/docs/plugins/)
- **[Vendor]** Claude Code: a `PreToolUse` deny "blocks the tool even in `bypassPermissions` mode or with `--dangerously-skip-permissions`". However, an installed mod handling `tool.check` "can approve a call that your PreToolUse hook blocked, unless the hook is in managed settings". Hooks that must not be overridden belong in managed settings, together with `allowManagedHooksOnly`. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide); [permissions](https://code.claude.com/docs/en/permissions#extend-permissions-with-hooks)

### Inferences
- Threat model for repo-supplied hooks: anyone with commit or PR access to a repo can ship a hook. Claude Code headless runs over untrusted checkouts (CI on fork PRs, batch `claude -p` over cloned repos) execute it without a prompt. Mitigations: `--settings '{"disableAllHooks": true}'` or `--bare` for untrusted input; review `.claude/`, `.codex/`, `.opencode/` and `hooks/hooks.json` diffs in code review (CODEOWNERS on these paths); `allowManagedHooksOnly`/`allow_managed_hooks_only` in managed fleets. Codex's per-hash trust is stricter by default, but `--dangerously-bypass-hook-trust` restores the risk in automation.
- Hook-script hardening checklist, derived from the vendor lists above plus the shell-profile pitfall:
  - Parse stdin with `jq`/Python/Node, never with `grep` on raw JSON.
  - Quote every variable, and never `eval` or interpolate `tool_input` into a shell string. In particular, Prettier-style `jq -r ... | xargs cmd` breaks on paths with spaces or newlines; prefer `jq -r ... -0`/`--raw-output0` or a script.
  - Normalize paths (`realpath`) and check them against the project root instead of only checking for `..`.
  - Use absolute interpreter paths (`/usr/bin/python3`, as in the Codex examples) so a repo cannot shadow `python3` on `PATH`.
  - Fail closed inside the script on parse errors in gate hooks (exit 2), because the harness fails open on crashes (exit 1 or 127).
  - Never echo secrets into stdout, stderr or `additionalContext`, because they reach the model, logs and (in Codex) spill files.
- Pattern blocklists over `Bash` command strings are inherently bypassable (aliases, `python -c`, base64, scripts written then run). Use them for steering against mistakes, and pair them with the sandbox and deny rules for anything that matters.

### Gaps
- No advisory specific to the Codex hooks system (as opposed to its MCP config or Git hooks) was found as of 2026-10-04.
- No documented Claude Code equivalent of per-hook hash trust was found. Trust is per workspace only.

## 5. Portability and verification: one script for both leads; testing in isolation; logging and debugging

### Takeaway
Keep one script in the repo and register it in both `.claude/settings.json` and `.codex/hooks.json` with the shared JSON shape. Resolve the script path from the git root. Read tool input defensively (Claude Code `Edit`/`Write` send `file_path`, Codex `apply_patch` sends a patch in `tool_input.command`). Use only exit 2 and the shared JSON subset. Test by piping recorded sample JSON into the script and asserting on exit code and stdout. Then confirm in-harness with `/hooks` (both leads) and the Claude Code debug log. Watch the first run for "hook error" notices: a mistyped path silently disables a gate.

### Cited Findings
- **[Vendor]** Codex recommends: "For repo-local hooks, prefer resolving from the git root instead of using a relative path such as `.codex/hooks/...`". Examples use `/usr/bin/python3 "$(git rev-parse --show-toplevel)/.codex/hooks/pre_tool_use_policy.py"`. Codex reads `.codex/hooks.json` or `[hooks]` in `.codex/config.toml`. — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Codex tool input: "`Bash` and `apply_patch` use `tool_input.command`. MCP and other local function tools send their arguments." For `apply_patch`, matcher values "can use `apply_patch`, `Edit`, or `Write`; hook input still reports `tool_name: "apply_patch"`." Unified exec (`exec_command`) matches as `Bash`. Codex hook input carries `model` and `turn_id` as extensions. `transcript_path` "isn't a stable interface". — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Claude Code `${CLAUDE_PROJECT_DIR}` stays at the session's start root even after entering a worktree, while "`cwd` follows Claude". "Read it when a hook needs to know which directory Claude is working in." — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#reference-scripts-by-path)
- **[Vendor]** Isolation test recipe: "Test it manually by piping sample JSON: `echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./my-hook.sh; echo $?`". "build the payload with a JSON encoder such as `jq` instead of string concatenation". Make scripts executable (`chmod +x`). — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** In-harness verification in Claude Code: run `/hooks` to confirm the hook is listed under the right event, and check the source label. "Matchers are case-sensitive". On success "you see nothing", so "check for its effect... or turn on debug logging". Use `claude --debug-file /tmp/claude.log` and `tail -f`, or `/debug` mid-session; `Ctrl+O` opens the transcript. Edits are picked up by a file watcher; restart if `/hooks` does not show them. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** "When the script path doesn't exist or isn't executable, the shell exits with a code like 127... For most hook events, the action proceeds. When you set up a policy hook, watch for this notice on its first run: a mistyped path in `settings.json` leaves the gate silently disabled." — [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#exit-code-output)
- **[Vendor]** Codex in-harness verification: `/hooks` lets you "inspect hook sources, review new or changed hooks, trust hooks, or disable individual non-managed hooks". "If hooks need review at startup, Codex prints a warning that tells you to open `/hooks`". An untrusted or changed hook is skipped, not errored. For managed MCP hooks: "Before relying on these hooks, test callback connectivity, required events, and failure behavior." — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Writing diagnostics to stderr "keeps stdout clean for JSON output and sends the message to the debug log". — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** Codex sets `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` for plugin hooks in addition to `PLUGIN_ROOT`/`PLUGIN_DATA`, so a plugin's `hooks/hooks.json` can serve both leads (concept doc). — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Anthropic's `bash_command_validator_example.py` is the reference implementation of a complete `PreToolUse` command validator. — [anthropics/claude-code example](https://github.com/anthropics/claude-code/blob/main/examples/hooks/bash_command_validator_example.py)
- **[Practitioner]** The hookify plugin generates hooks from plain English (`/hookify Warn me when I use rm -rf commands`). — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config), [hookify](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/hookify)

### Inferences
- Portable script skeleton (inference from both contracts):
  1. `input=$(cat)`. Read `hook_event_name` and `tool_name`.
  2. Get the target with `jq -r '.tool_input.file_path // .tool_input.path // empty'`. If that is empty and `tool_name == "apply_patch"`, the target paths are inside the patch text in `.tool_input.command`, whose format the hooks page does not specify (see Gaps).
  3. For Bash, read `.tool_input.command` (same field in both leads).
  4. Decide, then either exit 0 silently, or print the reason to stderr and exit 2.
  5. On `Stop`, always print JSON, even `{}`, on exit 0.
  6. Resolve repo paths from the input `cwd` or `git rev-parse --show-toplevel`, not from `${CLAUDE_PROJECT_DIR}`.
- This concept-doc inference is now resolved: Codex documents that `apply_patch` puts the patch in `tool_input.command`, so a hook keyed on `tool_input.file_path` sees nothing in Codex. Portable file-protection hooks must handle both shapes.
- Test pyramid for hooks:
  - Unit: a fixtures directory of recorded stdin payloads per event and per lead. Capture real ones by temporarily registering `cat > /tmp/hook-$EVENT.json`. Run a table-driven runner that asserts exit code, stdout JSON validity (`jq -e .`) and stderr content. Include adversarial inputs: paths with spaces, quotes, `$()`, `..`, unicode, and missing fields.
  - Integration: start each harness in a scratch repo, check `/hooks` (and the Codex trust review), then trigger the event with a scripted prompt (`claude -p`, `codex exec`) and assert on side effects or the debug log.
  - Canary: after deploying a gate, deliberately trigger a block once to prove it is live. This catches the silent 127/typo failure and Codex's skipped-until-trusted state.
- Log every gate decision (timestamp, session_id, event, tool, decision, reason) to an append-only file outside the repo, written from the script itself. This gives an audit trail that does not depend on either harness's debug logging.

### Gaps
- Codex documents no `--debug`-style hook execution log comparable to Claude Code's debug log, beyond the `/hooks` browser and hook-failure reports.
- The Codex `apply_patch` hook payload format (the exact patch grammar inside `tool_input.command`) is not specified on the hooks page.
- Whether a Codex regex matcher such as `Edit|Write` is anchored is still not recorded (open question carried from the concept doc).
- No dedicated open-source test harness or framework for hooks was found from a credible maintainer.

## 6. Layering: hooks vs permission rules vs sandbox vs CI

### Takeaway
Put each control where it holds. Hard limits on what the agent can touch go into deny rules and the OS sandbox. Hooks steer, add context and catch mistakes, and as a bonus can deny even in bypass modes. CI is the final, agent-independent gate. Hooks cannot loosen permission rules in Claude Code, and the vendors and practitioners agree that they are bypassable by tool-switching, specialized tool paths, hosted tools or prompt injection.

### Cited Findings
- **[Vendor]** "PreToolUse hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns". "A blocking hook also takes precedence over allow rules. A hook that exits with code 2 stops the tool call before permission rules are evaluated". The documented pattern: "To run all Bash commands without prompts except for a few you want blocked, add `"Bash"` to your allow list and register a PreToolUse hook that rejects those specific commands." — [Claude Code permissions](https://code.claude.com/docs/en/permissions#extend-permissions-with-hooks)
- **[Vendor]** "Hooks in settings files and in a plugin's `hooks/hooks.json` can tighten restrictions but not loosen them past what permission rules allow." `PreToolUse` fires "before any permission-mode check, in every permission mode", so a deny holds in `bypassPermissions`. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- **[Vendor]** Claude Code hooks run "outside the sandbox" with full user permissions (concept doc; [hooks reference](https://code.claude.com/docs/en/hooks#security-considerations)). Codex: "Treat tool hooks as a useful guardrail, not a complete enforcement boundary." — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- **[Vendor]** Anthropic pairs advisory review with hard enforcement: "For hard enforcement, pair the plugin with a hook that blocks the edit or a CI check." — [Claude Code security-guidance](https://code.claude.com/docs/en/security-guidance)
- **[Practitioner]** Hooks are "Guardrails, not walls". Trail of Bits pairs them with sandboxing and a devcontainer as the actual isolation layers (the repo covers "sandboxing, permissions, hooks" and links `claude-code-devcontainer`). — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **[Practitioner]** Tool-switching bypass (Edit hook → Bash write) shows that a hook keyed on one tool does not constrain the capability. — [anthropics/claude-code#29709](https://github.com/anthropics/claude-code/issues/29709)
- **[Vendor]** Managed scope: managed hooks cannot be disabled by users. `allowManagedHooksOnly` (Claude Code) and `allow_managed_hooks_only` (Codex) restrict execution to managed hooks. Codex admins can force hooks off via `requirements.toml` (`[features].hooks = false`). — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide); [Codex hooks](https://learn.chatgpt.com/docs/hooks)

### Inferences
- Suggested layering, from the cited findings:
  1. **Sandbox / devcontainer**: filesystem and network limits that hold whatever the model does. This is the only layer that also contains hook-script bugs, except that hooks themselves run outside it.
  2. **Permission deny/ask rules**: capability-level policy, evaluated regardless of hooks.
  3. **Synchronous `PreToolUse` hooks**: fine-grained, context-aware vetoes with actionable reasons. Use them for patterns that rules cannot express (argument inspection, repo state, time of day). Treat them as steering.
  4. **`PostToolUse`/`Stop` hooks**: fast feedback loops (lint, format, tests) that improve outcomes inside the session.
  5. **Git hooks / pre-commit**: harness-independent local gate. Be aware of CVE-2026-19590-style risks when harnesses run repo Git hooks.
  6. **CI**: authoritative gate for merges, independent of any agent configuration in the repo.
- Where a rule matters for security, enforce it at the capability level (deny rule or sandbox for the path or network), not at a single tool name. If a hook is used, match every tool that grants the capability (`Edit|Write|Bash|mcp__.*`), accepting that Bash parsing is best-effort.
- For fleets, place non-negotiable hooks in managed settings and enable managed-only hooks. Otherwise a project `disableAllHooks: false` or an installed mod (Claude Code) can change the outcome.

### Gaps
- No quantitative data was found comparing incident or bypass rates of hook-based vs rule/sandbox-based controls.
- Codex documentation does not state how `PreToolUse` hook decisions interact with its approval policies and sandbox modes beyond `permission_mode` being passed in the input.
